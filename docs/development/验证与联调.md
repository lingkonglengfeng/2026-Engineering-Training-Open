## 环境准备

| 用途 | 当前工程依据 | 准备方式 |
| --- | --- | --- |
| 固件构建 | `.uvprojx` 配置 ARM Compiler 5.06 update 5，器件包 `Keil.STM32H7xx_DFP.4.1.3` | 用 Keil 打开 [工程文件](../../MDK-ARM/Engineering_Training_Project.uvprojx)，选择 `Engineering_Training_Project` 目标构建；换编译器需单独验证 |
| PC 视觉 | Python 3.10～3.13，依赖见 [requirements.txt](../../vision/pc_vision/requirements.txt) | 可用根目录启动器管理的环境，或自己的 Python 环境 |
| 固件离线回归 | `arm-none-eabi-gcc` 在 PATH；`unicorn`、`pyelftools` | 安装交叉编译工具链和 [测试依赖](../../tools/tests/requirements.txt)，驱动器运行器还使用 PC 视觉依赖 |
| 现场联调 | 当前固件、PC 源码、CAM1/CAM2 应用及现场标定 | 记录各端版本和 Git 提交，再按照下文联调 |

下面的 `python` 必须是已安装相应依赖的解释器。首次安装：

```powershell
python --version
python -m pip install -r vision/pc_vision/requirements.txt
```

需要执行固件离线回归时再准备：

```powershell
arm-none-eabi-gcc --version
python -m pip install -r tools/tests/requirements.txt
```

上位机启动器的独立解释器位于 `%LOCALAPPDATA%/EngineeringTrainingPcVision/venv/Scripts/python.exe`。缺少工具应记录为“环境未就绪/未执行”，不能记为测试通过。

### 转向 PID 与波形组

```powershell
python -m unittest discover -s tools/tests -p test_turn_commands.py
python -m unittest discover -s tools/tests -p test_turn_trace.py
python -m unittest discover -s tools/tests -p test_turn_panel.py

```

第一条检查固件侧 `&pid/&tstat/&ttrace` 的白名单、双入口分发、`[TURNW]` 字段、PID 上电装载与版本标记；
第二条检查上位机 `TurnTrace` 解析、波形样本缓存与参数来源字段；第三条检查转向页“未应用调参拦截/来源显示”；
第四条复核蓝牙 tokenizer 的前提没被改写。
改 `zdt_motor.c` / `bt_button.c` / `pid_storage.c` / `chassis_motor.c` 或上位机转向页时都要跑。
实车需另核对：`&EN` 后 IMU 零漂就绪、`[PID] BOOT source=` 是否出现且来源正确、转向超调与耗时、
以及打开波形时的串口带宽（约 40 Hz，仅调参时开）。

## 现场联调顺序

1. **确认版本组合**：记下 Git 提交、固件版本、PC 版本/提交、CAM1 与 CAM2 应用版本。本基线是 V195 + CAM1 桥 1.3.0 + CAM2 桥 1.4.0，PC 使用对应源码；若某端沿用旧版，写明原因。
2. **先确认图像与角色**：电脑和两相机处于可互通的同一热点；CAM1、CAM2 分别扫描各自角色。图像 TCP 9000、通信 TCP 9001、发现 UDP 9002。只看图使用根目录 `一键图传检查.cmd`，完整按钮说明见 [PC README](../../vision/pc_vision/README.md)。
3. **确认主控联动**：使用 `视觉上位机.cmd` 的双路运行入口，识别任务跟随主控 SET；需要日志时单独连接调试串口，串口号按自己的电脑选择，同一端口只由一个程序占用。
4. **赛前准备与启动**：V244决赛发送统一 `&prepare`，等待零漂和机械臂READY，此时不绑定起点；摆正放稳后PD1短按松开选1号区，长按满1秒松开选2号区并发车。非正式调试可用 `&OK 1` / `&OK 2`，裸OK默认1号；接受发车时才确认坐标。旧初赛V237仍用 `&prepare 1|2 → READY → OK`。连接上位机本身不等于启动机器人。
5. **只验证本次改动及相关流程**：抓取提速记录完整周期和成功次数；避障记录净距、速度、障碍位置、落图和绕行结果；V195 原生升降先核对 3200 脉冲/圈与实机行程，不能靠改抓放高度掩盖比例差异。
6. **保存证据并交接**：使用相同条件的前后数据，提供原图、标注图、串口日志或 CSV 的必要片段，在 PR/Issue 写明结论与未完成项。

串口日志按每次比赛运行分开保存。排查先读取`vision/pc_vision/logs/日期/serial/runs/latest.json`，只打开它指向的本轮文件，避免把同一串口连接中的多次比赛混在一起读取。旧版会话尚未分轮时，使用[末尾提取工具](../../tools/extract_latest_match_run.py)反向定位最后一次启动，提取后只分析该轮；保存边界及索引详见[PC2.5.5说明](../electrical/2026-10-28_按轮日志与三次漏下降核对_PC2.5.5.md)。

保持当前速度与既有工序，新增或改变停机保护前先告知车主。正常避障会暂停当前运动段后重规划；`NO_PATH` 保持避障暂停并打印原因，不新增 `MATCH FAULT`、不伪报工位完成。`vobs retry` 与手动清障只用于非正式调试或赛前/赛后，正式比赛中的操作限制见 [V194 与规则原件](../electrical/2026-10-27_CAM2障碍融入比赛流程_V194.md#无路及比赛规则)。

当前 `[MATCH TIME]` 的结束点为返回起始区待停车位置，带有 `final parking pending`，不能称为最终视觉停车完成时间。

## 结果怎么记录

| 证据 | 能说明什么 | 记录内容 |
| --- | --- | --- |
| Keil 编译 | 当前目标可以生成固件 | 提交、工具链、目标、错误/警告数 |
| PC / Cortex-M 离线检查 | 当前输入与模型下的程序行为 | 命令、解释器/工具链、通过/失败数量和首个失败 |
| 图片或日志回放 | 给定样本上的识别/协议行为 | 原始样本、配置、输出、比较口径 |
| 实车联调 | 指定硬件和现场条件下的表现 | 版本组合、负载、速度、成功/总次数、耗时、照片/日志 |

未执行写“未执行”；没有实车写“未实测”。基线旧结果只能作为引用，不能计入本次新验证。

运行配置、现场 `calibration.json`、截图与日志保留在本机，不提交账号凭据或个人配置。必要的回归样本放入 [test_data](../../vision/pc_vision/test_data/)并说明来源；发布固件和较大日志使用 Release 或单独文件，源码 PR 中给出链接与对应提交。
