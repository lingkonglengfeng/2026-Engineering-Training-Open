# 任务架构检查与运行实现方案

日期：2026-10-03。依据当前 `Core/Src`、`Core/Inc`、`freertos_task/` 和电控架构文档进行静态检查；本次没有修改固件、编译、烧录或测量实车时序。下文周期和优先级为实现建议，不能视为已验证的实时性指标。

## 1. 判断

“FreeRTOS 并发任务 + 比赛主状态机 + 动作子状态机”的总体方向适合本项目。可以复用底盘运动学、转向控制、栅格规划、已有非阻塞导航、达妙驱动和舵机驱动。主要缺口是应用层编排、设备所有权、可靠的动作结果通道和统一安全管理。

任务应按长期职责划分。读码、去原料区、抓第一个料、码垛等是比赛状态和动作请求，不需要每个步骤新建一个线程。各线程在上电时创建，比赛前等待就绪/启动，比赛中按事件或周期推进，结束后回到等待或锁存停止状态。

当前三块硬件板的已记录方案由同一 STM32 主控调度；板卡数量不等于 MCU 或 RTOS 调度器数量。本方案针对当前 H723 主控的软件架构。

## 2. 当前程序实际如何运行

启动链：`main()` 初始化外设与视觉 DMA → `osKernelInitialize()` → `MX_FREERTOS_Init()` → `osKernelStart()`。

`Core/Src/freertos.c` 目前创建三个线程：

| 线程 | 实际工作 | 调度方式 |
| --- | --- | --- |
| `zdtMotorTask` | 初始化 FDCAN2，随后处理命令、蓝牙按钮、运动脚本、底盘控制、IMU 日志、里程反馈与导航 | `ZDT_Motor_Poll()` 后 `osDelay(1)`；优先级 Normal=24；栈 8192 B |
| `armTask` | 达妙转盘周期维护、失联及总线故障处理 | 服务后 `osDelay(10)`；Normal3=27；栈 2048 B |
| `defaultTask` | IPS200 初始化及地图、PID、IMU 状态刷新 | 刷新后 `osDelay(50)`；BelowNormal=16；栈 8192 B |

因此当前 armTask 优先级高于 zdtMotorTask；`freertos.c` 中“比 zdtMotorTask 低”的注释与属性值相反。任务栈合计 18 KiB，是否可压缩要看栈水位。

规划中的消息队列、事件组、MatchTask、SafetyTask 等还未在此创建函数中落地。`freertos_task_pseudocode.c` 明确只是设计伪代码，不能直接加入 Keil 构建。

## 3. 需要先修正的边界

### 3.1 控制与日志混在一起

`zdt_motor.c:5052` 的轮询函数将底盘控制、导航、输入解析与日志串行执行。`chassis_motor.h` 的发送节拍是 4 ms，但实际更新依赖此轮询循环。

`ZDT_Console_WriteBytes()` 使用阻塞 `HAL_UART_Transmit()`。按当前初始化提示的 9600、8N1，100 字节单纯在线上传输就约需 104 ms，尚未计入等待和软件开销。`osDelay(1)` 只表示本轮执行完以后延迟，不能保证轮询或控制每 1 ms 执行。

建议把控制计算、CAN 发送与日志分开。实时线程只发布日志记录，TelemetryTask 独占 UART4 发送，队列满时丢低优先级日志并计数，不能让控制任务等待。

### 3.2 视觉与 IMU 仍在中断中解析

`vision.c` 的 DMA HT/TC 回调和 USART IDLE 路径调用 `Vision_DmaPump()`，再调用视觉逐字节解析或 `HWT101_OnDmaData()`。这与设计文档中的“ISR 只搬运/通知”不一致。

建议 ISR 只记录接收位置或复制到有界缓冲并唤醒任务。PerceptionTask 解析相机数据；传感器服务解析 IMU 数据，再发布快照。若只通知 DMA 环形缓冲的位置，必须检测消费者是否落后超过一圈，避免把已被 DMA 覆盖的数据当成完整帧。

### 3.3 设备所有权需要收口

当前 zdtMotorTask 还能通过 `DM_Console_ProcessCommand()` 操作达妙实例，而 armTask 同时服务该实例。独立 CAN 控制器可以并行使用，但同一驱动实例不能由任意任务并发修改。

正式实现建议：MatchTask 只发请求；MotionTask 只发布底盘目标；ActuatorTask 独占机构动作状态；CommsTask 独占普通 CAN 发送与反馈分发。调试命令也走相同请求入口。

迁移期间可以暂时保留“底盘服务独占 CAN2、机构服务独占 CAN1”，但必须明确它与最终统一 CommsTask 是两个阶段，不要一边保留直接发送，一边新增第二个发送所有者。

### 3.4 安全接口存在，安全链尚未闭合

目前有局部紧停、达妙失联处理，但没有统一 SafetyTask。PA1 已配置 EXTI1，项目业务源码中未找到实现停机行为的 `HAL_GPIO_EXTI_Callback()`；HAL IWDG 模块目前也未启用。

现有 `ChassisMotor_EmergencyStop()` 会调用电机发送及转盘紧停，后者还可能记录日志，不能直接放入急停 ISR。

建议急停中断立即锁存停止，并在具备硬件条件时关断危险输出；再通知 SafetyTask/CommsTask 完成软件停止。发送端必须先检查停止锁存，撤销待发普通运动目标，防止急停后旧命令重新使机构运动。STOP 软件链的完成不代表板上已经有硬件断使能通路。

## 4. 各任务的运行方式

优先级采用 8 月 19 日《FreeRTOS任务安排与设计》的较新表，替代 8 月 18 日旧表；特别是 CommsTask 不应低于会依赖它的普通流程线程。以下先作为预算，实际执行时长、周期和栈必须测量。

| 任务 | 唤醒方式/建议周期 | 优先级 | 每次处理与输出 |
| --- | --- | --- | --- |
| SafetyTask | 急停/故障通知，10 ms 巡检 | 48 | 启动消抖、就绪门禁、故障锁存、关键任务时间戳检查；统一停止，健康时喂狗 |
| ControlTask | 专用控制定时器通知 | 40 | 读取最新运动与传感器快照，算航向修正、限幅及轮速；发布最新输出，不发送 CAN、不打印 |
| SensorFusionTask | 5 ms | 34 | 处理 IMU 与可用的轮端反馈，发布姿态/位置及质量；没有实际光流时不把光流有效当作启动条件 |
| CommsTask | CAN RX/紧急通知，4–5 ms 输出刷新 | 33 | 先紧停、再限量处理 RX/普通 TX；底盘四轮按一个批次加同步触发提交；发布带时间戳反馈 |
| MotionTask | 请求，10 ms 推进 | 32 | 启动规划、执行路径段、处理障碍物、视觉精定位；输出速度目标和请求结果 |
| ActuatorTask | 请求，10 ms 推进 | 27 | 转盘、升降、伸缩、夹爪及载物台动作；步骤进入时下发一次，随后验证反馈和超时 |
| PerceptionTask | UART 数据通知，最长约 10 ms 检查一次有效期 | 26 | 解析二维码/颜色/圆环/障碍物，校验序号和年龄，发布快照与事件 |
| MatchTask | 比赛事件，10 ms 超时检查 | 24 | 唯一修改比赛阶段，发一次动作请求，匹配完成回报后进入下一阶段 |
| DisplayTask | 消息，50–100 ms 合并刷新 | 11 | 独占显示输出，消费状态模型，避免直接遍历别的任务正在修改的导航内部数据 |
| TelemetryTask | 日志通知，100 ms 统计 | 8 | UART4 日志、栈水位、队列溢出、执行时间和故障记录；比赛模式关闭运动命令入口 |

ControlTask 的 1 kHz 是原设计目标，并非当前代码已实现的节拍。现有电机内部闭环加底盘 4 ms 更新可以作为迁移基线；是否需要上层 1 kHz 要由控制带宽、反馈更新率和实测收益决定。最终采用 1 kHz 时，另选空闲定时器，保留 TIM7 的 HAL 时间基准和 TIM4 的舵机 PWM。

硬件节拍也不能自动保证截止期；仍须检查任务延迟、中断负载和最长执行时间。线程标志会合并重复置位，不能靠一个 tick 位准确统计漏拍；应另记录中断计数/时间戳，发现超期时采用明确的降级或停机策略。

## 5. 一次比赛动作如何跨任务运行

示例：去粗加工区并放置一个料。

1. MatchTask 进入“移动到粗加工区”，生成 request_id=101，发送 `MotionRequest`，记录 deadline。
2. MotionTask 接收 101，调用已有栅格规划和导航状态机逻辑，持续发布最新底盘目标。
3. ControlTask 计算轮速；CommsTask 在自己的发送节拍提交最新轮速。期间 PerceptionTask、SafetyTask、显示和机构服务仍可调度。
4. MotionTask 通过位置、反馈质量和必要的视觉对准判定到站，先发布停止目标，再发送 `{MOTION_DONE, 101, OK}`。
5. MatchTask 只接受与当前请求、动作类型及当前阶段匹配的结果，进入放置状态，发送 `ActuatorRequest` 102。
6. ActuatorTask 按“安全接近→转盘/轴到位→释放→放置确认→收回安全姿态”推进，成功后回报 102。
7. MatchTask 更新统计并下发下一动作。任一步失败、超时或被取消，都通过统一结果和安全路径处理。

等待完成不会让整台 MCU 停住：MatchTask 等队列时处于阻塞态，调度器运行其他就绪线程。每个业务线程保留循环，但循环只做有界的一次服务，随后等事件或下一周期；不能高优先级空转。

公共动作契约至少包含：`request_id / action / parameters / timeout / result`。停止或新一轮运行后旧请求全部失效，必要时增加 generation。完成结果不能静默丢弃：若事件队列满，保留待上报结果并重试，或走独立故障通道；MatchTask 保留截止时间兜底。

短期可以包装现有私有 `ZDT_Nav_Start/Service/Cancel` 为结构化 `Motion_Start/Poll/Cancel` 接口，再逐步抽出模块。正式流程不要通过拼接 `&goto` 等调试字符串驱动导航，也不要直接跨线程调用原来依赖单线程状态的函数。

## 6. 现有伪代码落地前必须修的细节

1. **队列超时会留下旧事件。**MatchTask 当前忽略 `osMessageQueueGet()` 返回值，可能重复处理上次成功取出的事件。每轮先设 `ME_NONE`，仅在返回 `osOK` 时处理事件；超时只做状态期限检查。
2. **同色到位要确认本次动作。**一个长期置位的 `EV_PAYLOAD_ON_PLATFORM` 不能证明第二件料已到台。维护三槽占用/颜色，并用带 request_id、槽号的本次确认更新它。
3. **跨区域搬运必须包含底盘动作。**当前 `REQUEST_TRANSFER_PROCESSING_TO_TEMP()` 把跨区域步骤抽象成一个机构请求，边界过粗。主流程应展开成“粗加工放置→再取回并装台→机械臂收回→移动暂存区→卸料”。第二批放置后也必须有再取回/装台确认再去码垛，不能省掉运输载荷过程。具体工艺顺序以队伍冻结的比赛需求为准。
4. **需要显式到达读码区和原料区。**伪代码从启动直接读码、读码后直接抓料；若它们不在启动位置，必须加入相应移动和对准状态。
5. **停止分支不能忙等。**MotionTask/ActuatorTask 的 stop 分支直接 `continue` 会跳过循环末尾延迟；落地时须保持阻塞/周期等待，结果只回报一次，避免占满 CPU 和重复上报。
6. **快照读写不能只靠 volatile。**多字段结构用极短、覆盖读写复制的临界区或有界的双缓冲协议，控制读取失败时保留已验证旧值并检查年龄。不要让高优先级读者无限重试一个被它抢占的低优先级写者。
7. **区分接收时间与测量时间。**视觉/导航结果带接收时间、序号、质量；消费者也检查有效期。当前 `Vision_Get*()` 返回 valid 并不自行拒绝陈旧数据。
8. **周期等待要处理超期。**固定周期用绝对节拍的 `osDelayUntil()`，检查返回状态/超期并重新同步，避免遗漏截止期后连续快速补跑。当前 1 kHz tick 下 ticks 与 ms 数值相同，接口仍应明确单位。
9. **心跳用各自期限。**采用每个关键服务 last_progress_tick，按其实际周期和最坏阻塞时间检查；不能要求所有线程每 10 ms 都更新，包括 100 ms 服务。空闲等待也要有明确健康定义。
10. **启动先等就绪。**先建好所有队列/通知对象和任务句柄，再启动接收/控制通知源；电机先保持不运动，自检确认必需模块就绪后才接收启动。首版调试可单独降级运行底盘，完整比赛不能把必需机械臂初始化失败视为可继续。

## 7. 实施顺序与验收

1. 在 `App/Inc`、`App/Src` 建立消息类型、任务创建、Match 状态机和 Safety 骨架；CubeMX 的 USER CODE 区仅调用 `AppTasks_Init()`；把新增文件和 include 路径加入 Keil 工程。先用模拟结果跑通状态转移、超时、取消与旧结果拒绝。
2. 复用现有底盘和 arm 服务，提供结构化请求及结果接口；先完成“启动→移动一个点→停止→转盘到位→回报”的最小链路。
3. 将阻塞日志移出控制链，视觉/IMU 解析移到任务，收口 CAN 所有权；拆 `ChassisMotor_Update()` 的计算与发送，避免新增 ControlTask 后原轮询仍再次执行 PID、斜坡和发送。
4. 接入升降、伸缩、夹爪和三槽载物确认，把单件抓取/放置完整调通，再编排两批物料流程。
5. 逐步验证急停期间普通命令失效、CAN 断线、视觉过期、动作超时、队列满和控制超期；检查动作终态、栈水位、总线负载与实测任务时序。

不要求为了凑任务数立即创建十个空线程。没有光流或完整融合模型时，SensorFusionTask 可先简化为传感器服务，遥测可先并入低优先级日志线程；职责和消息边界保持明确，随功能和实测需要拆分。
