# PC视觉通讯与运动预测可行性评估

日期：2026-10-17。范围：当前工作区视觉服务、STM32视觉接口、取料逻辑及补充规则。本文为检查和实施难度评估，未连接设备测量实时链路，未修改视觉/电控运行代码。

## 1. 结论

建议采用“车载相机采集，电脑进行识别和跟踪，车端接收坐标等观测并执行动作”的方案。现有检测算法和8字节协议已经提供大部分基础，第一阶段迁移难度中等；增加物料跟踪和短期预测难度中等；实现可靠的运动中抓取难度较高，主要工作是标定图像延迟、抓取动作时序和转盘运动状态。

电脑到小车的数据量非常小，通常不是帧率瓶颈。需要重点解决的是相机到电脑的图像获取、队列积压，以及电脑端与现有SET/ACK会话的衔接。

圆环跟踪器已有`velocity`和`predicted_center()`，主要用于ROI位置选择和目标匹配；对外`fresh_position()`仍使用当前实测点。这不是物料抓取预测功能，不能直接认为动态取料已经完成。

## 5. 推荐架构

```text
车载MaixCAM：原始图像采集、补光、图像帧号与采样时刻
       │ 图像 + 元数据（无线）
       ▼
电脑：接收最新图像 → 识别 → 轨迹关联 → 运动估计
       │ 坐标/颜色/有效性/场景状态等观测
       ▼
车端通讯桥 → 现有USART1视觉接口 → STM32任务/动作逻辑
       ▲
       └──── STM32 SET/STOP请求经桥转给电脑；ACK/心跳返回
```

第一阶段优先保持CAM1的现有串口连接，用MaixCAM作为图像源和双向通讯桥。电脑回传协议帧，桥转至UART；这样主控位置接口和动作状态机可基本保持。桥需要会话标识/连接代次，不能在切站、STOP或重连后重放旧结果。网络封装可比8字节UART帧更丰富，串口仍沿用原协议。

电脑服务负责实际的SET处理与ACK，桥不应在电脑尚未准备好时自行应答“识别已就绪”。协议心跳也应反映电脑处理服务状态，不能仅证明桥在运行。主控的模式请求、目标颜色、工位和flags必须传递到电脑，特别是圆环带物料档。

若使用独立无线串口模块直接接电脑，仍要处理双向模式命令；USB转串口直连适合台架联调。当前UART4是调试控制台，往该口发送8字节视觉数据不会自动进入USART1的相机接收流程，需要专门适配。

CAM2二维码程序可先保持当前独立运行；本次瓶颈优先处理CAM1物料/圆环/圆盘，减少首次迁移范围。

## 6. 通讯协议能复用多少

以`vision/protocol8.py`、当前`service.py`和`Core/Src/vision.c`实现为准；`MaixCAM_STM32_统一8字节串口协议_v0.1.md`包含早期状态，不应把“已保留”误认为“已实现”。例如文档中的FRAME_INFO为规划项，当前二进制主控解析器没有实现0x06。

- 固定帧：`6B TYPE META D0 D1 D2 D3 CRC8`，115200、8N1。
- `0x02 MAT_PX`：物料像素偏差；`0x03 RING_PX`：圆环偏差；`0x09 PLATE_PX`：圆盘切点偏差。
- 坐标右/下为正，小端int16、0.1像素。必须保持原处理分辨率或把电脑坐标映射回对应分辨率；屏幕坐标不能直接发送。
- `0x80 SET`、`0x81 ACK`、`0x82 HEARTBEAT`必须配套；心跳目标周期500ms。
- RING需要位置与`0x83 RING_COUNT`同图配组，请求轴角时还要`0x0A RING_AXIS`；PLATE需要位置与`0x85 PLATE_SCENE`配组。不是只发一对XY就能替代所有模式。
- 主控配组窗口50ms，SEQ只有4位；20Hz时0.8秒回绕，30Hz约0.53秒回绕。图像流和网络层需另有完整帧号与会话号，不能靠4位SEQ去关联跨网络图像。
- 颜色线上5=浅蓝、6=黑，规则/物料UI5=黑、6=浅蓝，保留已有映射。
- 当前取料主控请求20Hz，服务允许1–50Hz。PC可以先按30fps跟踪、按SET要求20Hz回传；若要提高回传频率，需要同步调整主控请求。

8字节在串口上线耗时约`8×10/115200=0.694ms`；16字节约1.389ms，24字节约2.083ms。30Hz下分别为240/480/720字节每秒，串口占用约2.1%/4.2%/6.3%，心跳与ACK另计。这说明传输关键信息的带宽充足，但不包含无线、桥、操作系统调度和排队延迟。

第一阶段发实测坐标即可。预测坐标不能直接塞进原MAT_PX并沿用“当前观测”含义，否则旧窗口逻辑会把未来位置当成当前位置。正式预测抓取应明确增加预测时刻/预测量接口，或由STM32基于带时间的实测状态计算触发时刻。

## 7. 图传与无线需要解决的实际问题

当前程序没有独立PC图像接收端、网络结果接收端和车端通讯桥。MaixVision可显示预览，不代表已经有可供比赛程序消费的完整机器视觉链路。

1. 保留未经mask、文字、圆圈叠加的图像发送副本。物料检测会`binary(copy=False)`修改输入，不能把检测后的二值画面作为电脑颜色识别原图。
2. 图像接收、算法计算、UI预览分开调度。采用容量1的最新完整帧槽，处理慢时替换旧帧，避免看起来帧率很高却始终在处理旧画面。视频解码器自身的缓存也需要测量和控制。
3. 图像帧号、相机采样时刻、电脑接收/处理/发送时刻、车端接收时刻应可以关联。时钟需估计偏移，或利用相机同一时钟测量发送到结果返回的往返耗时。必须说明采样时间是曝光时刻还是read完成时刻及其误差。
4. 当前主控`Vision_GetPixelWindow()`按串口接收时刻计算年龄。无线积压的旧图被刚刚送达时，现有150/200ms年龄检查不能识别其真实年龄；预测阶段需补齐这部分时间语义。
5. 用户已确认后续补光改由主控或扫码用的MaixCAM控制。本方案按这一安排实施，CAM1集中负责采集和通讯，补光不作为PC视觉迁移的待解决条件。当前CAM1的A19/PWM7初始化需在实际迁移补光时同步调整，防止遗留的引脚配置继续占用资源。厂商关于普通MaixCAM的PWM4–9与Wi-Fi资源说明仅作为本次检查记录。
6. 官方提供JPEG和RTSP图传接口，但需要在目标固件验证吞吐量和延迟。RTSP文档要求NV21，绑定后原Camera不能继续被当前读帧逻辑使用，因此不宜直接把示例塞入现有RGB服务。用户已经测过的图传方式应优先复现，再决定是否替换。

## 8. 物料跟踪与预测的实施路径

建议先做固定抓取位置的提前触发，再考虑机械臂连续追随物料。当前伸缩轴在取料等待姿态保持，更适合计算“物料何时到达夹爪位置”。完整追随需要像素到机械坐标标定和连续运动控制，范围明显更大。

第一步：每帧保留目标颜色、中心、大小和时间，用颜色约束与位置/速度匹配维持轨迹。规则初赛每盘三种不同颜色，颜色可以辅助身份；内部轨迹ID和协议颜色ID分开。使用真实时间差，不能假设每帧都正好33ms。短时可使用alpha-beta或Kalman滤波，无需先上神经网络。

第二步：识别转盘的移动、减速、停止状态。规则明确有停留且方向随机，不能只固定一个角速度永久外推。相机和机械臂姿态变化时，需要按姿态重建轨迹或补偿相机运动，否则会把相机运动当成物料运动。

第三步：在稳定观察姿态下标定转盘平面。存在透视时应先做平面映射，或使用投影圆轨迹模型，不能直接把图像椭圆上的极角当成匀角速度。物料中心所在高度与盘面不同，标定高度也需要匹配。

第四步：预测到夹爪有效接触时刻的位置：

```text
总预测时长 = 观测到当前的图像年龄 + 回传/调度延迟 + 下降与闭爪达到有效接触的时间
短时近似：p_future = p_measured + v * 总预测时长
转盘模型：theta_future = theta_measured + omega * 总预测时长
```

下降和闭爪在当前代码中并行，时间应按“从触发到形成有效夹持”的实际过程标定，不能简单把两个完整动作耗时相加。还需要测量动作时间波动、等待高度、舵机参数以及负载变化。

以规则6–10秒/圈估算角速度约36–60度/秒。若物料中心轨迹半径为100mm（示例假设，未测），速度约63–105mm/s，30ms可移动1.9–3.1mm，100ms可移动6.3–10.5mm。因此仅有30ms图传仍不足以代替抓取时序标定。

3. 转盘实拍视频上记录轨迹、方向、停留和预测误差，按实际需要的50/100/200ms预测范围检查结果。
4. 测量实车触发到有效夹持的时间分布，再接入提前触发。只有这一阶段能回答预测是否真正提高抓取成功率。

判断：可以用手机热点实现局域网图传与观测回传。未现场验证前，普通识别/静态纠偏链路按中等风险评估，依赖运动预测的抓取按较高风险评估。这是工程判断，不是故障概率或实测可靠率。手机计算性能不能保证无线时延，平均30ms不能证明现场没有200ms以上的延迟尖峰。

### 10.1 频段与拓扑

厂商当前[MaixPy设备对照表](https://wiki.sipeed.com/maixpy/)将MaixCAM列为Wi-Fi 6、2.4G/5G。应优先测试手机5GHz热点，确认这块实际设备和当前系统固件能发现、连接并稳定传输，再决定正式频段；不要仅凭旧经验认定普通MaixCAM只有2.4GHz，也不能由官网参数推断用户这台已验证5GHz热点兼容。手机当前HyperOS的热点菜单及可选择频段尚未实机核对。

优先保持以下简单拓扑，两端使用局域网地址直接通信：

```text
MaixCAM ←Wi-Fi→ 红米热点 ←Wi-Fi→ 电脑
```

此数据通路不需要经过运营商、互联网服务器或云服务。手机显示的蜂窝5G与热点Wi-Fi的5GHz不是同一概念，前者信号好不能证明图传稳定。需要实测同一热点下两客户端能互相访问，不能只检查它们能否上网；手机的客户端隔离、电脑防火墙和IP变化也要在比赛前排除。

相机到电脑的图像在该拓扑中通常要由热点接收再转发，同信道占用两段无线发送时间。只算图像文件大小不等于全部空口开销。若以后尝试电脑USB连接手机，必须先验证USB与Wi-Fi客户端之间确实能互通，不把USB共享直接视为已成立的局域网桥。

### 10.2 主要风险

| 情况 | 对系统的影响 | 建议处理方式 |
| --- | --- | --- |
| 多支队伍热点/场馆AP同时工作 | 信道竞争、退避、重传，尾部延迟上升；信号强也会发生 | 先实测5GHz；无法使用时再测试2.4GHz；按现场结果选频段 |
| 人体、车体金属和机器人朝向遮挡 | 信号与速率随位置变化，出现突发间隔 | 在允许区域固定手机位置、尽量保持视线通畅，测试全部路线和转向 |
| TCP/视频解码器积压 | 图像连续到达但越来越旧，坐标表面新鲜 | 图像队列只保留最新完整帧，关联采样时间；约束发送端和解码端缓存 |
| 把视频和控制放进同一大字节流 | 图像重传/排队连带延迟ACK与坐标 | 控制与图像分连接，小消息及时发送；但分连接不能消除共同无线拥塞 |
| 手机锁屏、省电、热量和自动关闭热点设置 | 不同系统配置可能降低稳定性或关闭热点 | 用实际比赛设置测试锁屏及持续运行；关闭适用的自动关闭/省电选项；合理供电、散热 |
| 重连后旧帧/旧结果重放 | 错把上一个工位、颜色或时间的结果用于当前动作 | 网络完整帧号、连接代次及SET上下文关联，重连后重新确认会话 |

Cisco的[射频管理资料](https://www.cisco.com/c/en/us/td/docs/wireless/controller/best-practices/base/b_bp_wlc/rfmgmt.html)说明2.4GHz的信道复用与干扰问题；其[密集部署实例](https://blogs.cisco.com/networking/accelerating-wi-fi-troubleshooting-with-agenticops)解释同信道设备争用空口会导致重试、时延上升，即使信号强也可能发生。5GHz通常提供更好的选择空间，但不是零干扰或时延保证。

### 10.3 带宽足够与时延可靠是两件事

以30fps估算，以下JPEG大小均为示例假设，实际需对相机发送内容统计：

| 每帧图像大小 | 图像有效载荷速率 | 经同频热点接收再转发的发送量量级 |
| --- | ---: | ---: |
| 10KB | 约2.4Mbit/s | 约4.8Mbit/s，另加协议、确认及重传 |
| 20KB | 约4.8Mbit/s | 约9.6Mbit/s，另加协议、确认及重传 |
| 40KB | 约9.6Mbit/s | 约19.2Mbit/s，另加协议、确认及重传 |

480×360 RGB888原始图像30fps约124.4Mbit/s，尚未计转发，不能把这种原始传输作为当前手机热点默认方案。应使用合适的JPEG或硬件视频压缩，并在颜色阈值和圆环边缘识别上验证压缩影响；当前只需一台物料相机图传，扫码结果保留本地输出可避免第二路持续视频流占用。

坐标包本身几十至几百字节每秒，远小于图像流。即使只向小车发送坐标，相机上行图像仍是整个系统的无线负载主体。提高手机蜂窝网速、单独降低坐标发送字节数都不能根治图像排队。

### 10.4 现场能否使用的验证方法

1. 固定实际比赛分辨率、压缩质量、帧率、补光、手机位置和电脑位置，分别验证2.4/5GHz实际兼容性。先跑30分钟，再做至少10轮完整3分钟任务长度的连续记录，覆盖锁屏和正常发热状态。
2. 台架可用其他自有设备正常并发传输，检查本链路受负载影响的情况；不向他人的网络制造干扰。最后仍需在比赛场地正常拥挤时测量，实验室并发负载不能替代现场射频环境。
3. 对每帧记录：完整帧号、采样/读帧时刻、电脑收到完整帧、解码完成、检测完成、结果返回车端时间；统计图像年龄与端到端延迟P50/P95/P99/最大值，及100/200/500ms以上无新观察的次数和最长间隔。`ping`只能辅助发现问题，不能替代真实图传负载测量。
4. 所有自动重连与会话重建应在发车前准备好，按规则比赛过程中不操作电脑。若需人工干预才能恢复连接，该方案还未满足比赛运行要求。
5. 是否足以预测抓取应由误差预算决定。例如物料速度100mm/s时，未补偿时间误差10ms对应约1mm位置误差，50ms对应约5mm，另加检测、标定、加减速与夹持误差。稳定的固定延迟可以标定补偿，变化的排队延迟更难预测。

建议先验收PC实测坐标与已有动作逻辑，再用记录的实际图像年龄判断预测收益。可保留车载视觉作为后续可选退路，但自动切换涉及唯一发送源、SET会话重建及旧观察清理，需要独立实现和验证，不能宣称现有程序已经能无缝切换。本次没有添加新的断网停车条件或更改控制程序。
