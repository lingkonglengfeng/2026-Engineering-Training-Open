| 2 | 上电后**保持静止约 3 s** | 先出 `[MILLAGE] reference ready`，再出 **`[IMU] zero-drift ready: N samples/Xms, gyro bias +X.XXX dps`**；屏幕右上角 `IMU ZERO CAL 2.4s` → `IMU ZERO DONE` | 没出现就再静止一会儿；倒计时跳回 0 = 车还在动。`yaw` 可查 `ready=1` |

| 7 | `&echo`（蓝牙或串口各发一次） | 每次回一行 `[ECHO] n=<递增序号>` | 同一序号重复出现 = 接收端重绘；序号跳号 = 上位机重发（§4.24） |

| 10 | 手动试：`&M1` + 短按 `&U` | 前进（速度已降到原来的 1/3） | 见 §5 |
| 11 | `&M1` + `&L90` | 向左转 90°，串口出现 `[TURN] done …ms … err=…` | 见 §5.4；若打 `[TURN] rejected` 说明没 `&EN` 或 IMU 零漂还没就绪 |

> **角度转** `&L90/&R90` 和导航段前对准走转向 PID，上限 `CHASSIS_TURN_MAX_WHEEL_RPM = 90`，不乘手动折扣。

## 3. 命令速查

### 3.1 串口控制台（UART4 9600 8N1）

| 命令 | 用途 |
|---|---|
| `help` / `status` / `yaw` | 帮助 / CAN 状态 / 陀螺与转向状态（`yaw` 现打印 `raw/zero/gyro/bias/ready/cal/turn`） |
| `zero` | 重对航向基准（摆好车头后必须做一次） |
| `nav` / `spd0.50` / `t10002051` / `cnt65536` / `t901000` / `t1802000` / `navreset` | 导航参数查看与修改（`nav` 会打印 `k=`、理论值、`t90/t180`，见 §4.23、§4.33） |
| `save` / `read` | PID + 导航参数一起存/读 W25Q64 |
| `echo` | 链路自检：回一行 `[ECHO] n=<序号>`（判"命令被重发"还是"接收端重复显示"，见 §4.24） |
| `dis` / `off` | 关闭四轮使能（**标定前必须**，否则锁轴转不动） |
| `posref` / `posd` | 抓位置基准 / 打印差值（量"计数/圈"、看符号） |
| `poscal` | 逐轮自标定：脉冲当量 / 是否执行 `0xFD` / 回读符号 |
| `posq` | 打印四轮 `0x36` 原始帧（核帧格式） |
| `verall` | 逐地址读驱动器固件版本 |
| `posmode 0/1` | 直线段执行方式：0=速度+定时（默认），1=位置模式 `0xFD` |
| `verbose` / `quiet` | 打开/关闭 CAN 原始帧日志（诊断用，很吵） |
| `kp` / `ki` / `kd` / `show` / `flash` / `delete` | 转向 PID 查看与 flash 操作 |

### 3.2 蓝牙（`&` 前缀；**token 不能带空格**，除非是下面特批的）

```
&EN  &M1  &M2  &U  &D  &L  &R  &STOP        ← 手动控制
&L90 &R90                                    ← 转向 PID 转到指定角度
&dis &off                                    ← 关使能（标定用）
&zero                                        ← 重对航向基准
&goto x y  &pose x y  &grid  &gridclear  &obs x y  &free x y  &clear
&poscal &posref &posd &posq &verall &posmode
&nav  &spd 0.50  &t1000 2051  &cnt 65536  &save  &read  &show  &flash  &kp  &ki  &kd
&t90 1000  &t180 2000  &tarc 0  &aspd 1.00   ← 转向/圆弧耗时与圆弧速度（§4.33 / §4.36）
&echo                                        ← 链路自检（回 [ECHO] n=<序号>）
&cross [1|2]                                 ← 从一个启停区直走到另一个启停区
```

> `&nav` / `&spd` / `&t1000` / `&cnt` **特批可以带空格**（`&t1000 2051`），其他 `&` 命令不支持空格（会被切成两个 token，前半段单独执行、后半段丢弃）。
> `&echo` 在两个入口（串口 `ZDT_Process_Command` 与蓝牙 `BT_BUTTON_CUSTOM`）都接了同一个 `ZDT_Print_Echo()`，序号是**同一个计数器** —— 哪条链路重发都会让序号跳。
> **`&obs` / `&free` 的坐标规则与 `&goto` 完全一致**：两个值都 **<48** 当**格**坐标，否则当**规则图 mm**（原点左下、y 向上）。
> 例：`&obs 650 2100` 与 `&obs 13 5` 是同一个格（该格格心 mm = (675,2125)，固件会把这行回显出来供你核对）。
> ⚠ **一个障碍格的代价比看上去大得多**：车体 300×300，膨胀后**车心周围 3 格内全部不可用** ——
> 也就是一个障碍格会封掉 **7×7 的格心区域**。400 mm 宽的中央十字通道膨胀后只剩 2 格可走，
> 所以**在通道里加任何障碍格都会直接把路封死**（表现为 `NO PATH`）；在 550 宽的环带里加才是"绕一下"。
> 障碍只存在 RAM 里（`&clear`/`&gridclear` 清掉，上电复位也清掉，不写 flash）。
> 新增 `&` 文本命令时**必须同时改两处**：`bt_button.c` 的 `BT_Button_IsCustomPrefix()`/`IsCustomToken()` 白名单 + `zdt_motor.c` 蓝牙事件里的同名分支；否则命令会被静默丢弃（表现为"发出去没反应"）。漏了哪一道、各自什么症状见 §4.25，**改完跑 `python tools/check_bt_whitelist.py` 交叉校验**。`&delete`（擦 PID 扇区）**故意只留给串口控制台**。
> **发完就生效，不用加换行**：网格命令与数值命令靠 300 ms 空闲超时补发（见 §4.11），`\r\n` 反而是"立刻派发"的快路径。

## 4. 已知坑（都是这次实测踩过的）

### 4.1 速度字段单位：驱动器按 0.1 RPM 解释 → 所有速度曾只有 1/10

- **现象**：`spd` 拉到 1.0、`t1000` 拉到 10000 才勉强走一两米；原地转明显慢且精度差。
- **判据**：导航日志 `[NAV] applied rpm` 显示下发 126，而 600 ms 只转 0.131 圈（应 1.26 圈）。
- **原因**：厂商手册里 X 固件那一行写着"速度 0-30000（0.1RPM，即 0-3000.0RPM）"，本车驱动器就是这个口径。
- **处理**：`zdt_motor.c` 的 `ZDT_SPEED_FIELD_SCALE = 10.0f`（发送前 ×10）。**换驱动器或用上位机改过固件后必须重验**。
- **连带影响**：修正后同样指令的实际轮速变成 10 倍，所以 `CHASSIS_MAX_WHEEL_RPM` 从 900 降到 250、转向 PID 必须重整定。

### 4.2 flash 会覆盖编译期默认值

- `&EN` 时固件从 W25Q64 读取 PID 与导航参数 → **改了 `chassis_motor.h` 里的默认值，烧录后依然会被 flash 里的旧值盖掉**。
- **处理**：改完用命令写入并 `&save`：`&kp 0.045` `&ki 0.0005` `&kd 0.0035` `&save`，然后 `&read` 复查。
- 想彻底回默认：`delete`（擦 PID 扇区）+ 导航参数 `&navreset` `&save`。

### 4.3 闭环步进使能后锁轴

- `&EN` 之后驱动器保持力矩，**手转轮子转不动**，主板复位也不解除（状态在驱动器里）。
- **处理**：标定前发 `&dis`（或 `&off`）关使能；`posref` 的输出里也会提示这一点。

### 4.4 位置模式（`0xFD`）在本车不可靠 → 默认不用

- 证据：① "缓存 + 广播触发"路径只有 2/4 轮动作，且动作的两轮转过量是下发量的 **1.885 倍**（车 45° 斜走）；② 改逐轮即时下发后四轮都动，但同一次位移里四轮"每脉冲转角"差 **3 倍**；③ 同一轮 `FR` 的脉冲当量在两次测试间从 3771 跳到 6398、回读符号还会翻。
- **处理**：`posmode 0`（默认）走"速度模式 + 定时 + 段末里程复核"；`posmode 1` 只做对比实验。
- **遗留待查**：四个驱动器不是同一批配置（`verall` 只收到地址 1、3 的回答），有机会用 ZDT 上位机统一细分/固件。

### 4.5 里程回读单位 = 65536 计数/圈（已实测确认）

- 手转一个轮子整 2 圈 → `d3 cnt=-130556` → **65278 ≈ 65536 计数/圈**，与厂商 Emm 口径一致。
- 早期"回读差 10 倍"的判断已作废，真正原因是 §4.1 的速度字段。
- 参数 `cnt` 可改，但本车就是 65536，不用动。

### 4.6 额外 CAN 轮询会与底盘调速帧抢发送队列

- 底盘每 20 ms 要发 4 帧调速命令；曾加过 10 Hz 的 `0x36` 位姿采样 → **车体剧烈抖动、原地转精度下降**。
- **处理**：任何周期性查询都要评估 CAN 流量；位姿融合方案已整体撤除（见方向文档 §15）。

### 4.7 转向 PID 与转向上限耦合

- 角度转的速度 = PID 输出 × `CHASSIS_TURN_MAX_WHEEL_RPM`。**降低上限等于降低环增益**（收敛变慢、可能超过 3 s）。
- 2026-09-12 在 90 RPM 上限下整定出稳定值 `0.045 / 0.0005 / 0.0035`；若要把上限改成 30，必须把 `kp` 提高约 3 倍才等效。

### 4.8 走行中航向漂移（"转 90° 后直走变成 90.6°"）

- 现象：原地转是准的，直走到最后方向偏 0.5~1°。
- **处理**：直走中做航向保持（`ZDT_Nav_HeadingHold()`，每 80 ms 一次，用陀螺修 omega）；段末日志 `hold peak X.XX deg` 就是保持期间最大偏差，正常应 ≤0.3°。

### 4.9 姿态精度只到 0.0055°：0.01° 判据是"贴分辨率"的

- HWT101 的 yaw 帧是 int16 × 180/32768 → **1 LSB ≈ 0.0055°**；角速度帧 int16 × 2000/32768 → **1 LSB ≈ 0.061 dps**。
- 所以"转向误差 < 0.01°"实际只有约 **2 个 LSB** 的余量：传感器量化噪声 + 走行后的零漂，可能让真实误差永远在 ±0.01° 之间跳，判据时有时无。
- 两级判据（2026-09-12 定的）：

  | 判据 | 条件 | 典型耗时 | 日志标记 |
  |---|---|---|---|
  | ① 主判据 | `\|误差\| ≤ 0.01°` 且 `\|角速度\| ≤ 2 dps`，连续 **200 ms** | 进带即停，最快 | 无 |
  | ② 稳定带判据 | `\|误差\| ≤ 0.05°` **连续保持 0.5 s**（掉出带就重新计时） | 进带 + 0.5 s | **`FB`** |
  | ③ 无进展兜底 | 误差 ≤0.20° 但 **900 ms** 内改善 <0.01°（到机械/分辨率下限） | ≤ 起始 + 0.9 s | **`ST`** |

- **0.5 s 驻留这一条为什么可靠**：真在转的话 0.5 s 会走出 1°（1.9 dps 也会走 0.95°），早就掉出 0.05° 带了 → 驻留计时清零。所以"连续 0.5 s 在带内"本身就等价于"平均角速度 < 0.1 dps"，不需要再单独卡角速度；而且它天然防止"擦着目标飞过去"被误判成到位。
- 看到 `FB` 说明误差落在 0.01°~0.05° 之间、已在传感器分辨率下限附近 —— 别再加严门限，该去查机械（麦轮摩擦、轮子打滑、地面）或改用短时陀螺积分（`gyro` 量化 0.061 dps，短时积分比 yaw 细，但要靠零偏标定压漂移）。
- 稳定带内不再有"最小输出兜底"（那个只在 `|误差| > 0.20°` 时生效），所以车能老实停在带里、不会自己把自己踢出去。

### 4.10 上电零漂：必须静止，且 `&zero` 也要重新静止

- 上电后 `0x53` 帧进来自动标定：角速度 |gz| ≤ 1.5 dps 且持续 ≥300 ms、样本 ≥20 → 平均出**朝向基准**与**角速度零偏**，打印 `[IMU] zero-drift ready`。
- **标定前转向会被拒**（`[TURN] rejected: need &EN and IMU zero-drift ready`），这是保护，不是故障。
- `&zero` 会把标定窗口清零重来（`yaw` 的 `ready=0 cal=1`），因此喊 `&zero` 之后同样要静止约 **3 s** 再动车（屏幕上有 `IMU ZERO CAL x.xs` 倒计时）。
- 上电时如果车已经在动（比如刚搬完手上还在晃），标定会一直重新计时 → 等它静下来。

### 4.11 蓝牙命令"必须发两次，而且收到的总是上一条"

- **现象**：手机 App 里发 `&goto 1 1`，车不动；再发一次才动 —— 动的是**上一次**那条；`&en`/`&l90` 之类却正常。
- **根因**：`BT_Button_Poll()` 里对网格命令写着"网格命令含空格，只在收到换行时才解析，不做空闲超时切分"，于是 `BT_Button_IsGridPrefix()` 命中时**直接 return**；而现场 App 按一次"发送"**不带 `\r\n`** → 命令一直憋在 token 缓冲区里，直到你下一次发送、第一个 `&` 到达时先执行 `BT_Button_FlushToken()` 把**上一条**补发出去 —— 形成"永远慢一条"的错位。数值命令（`&spd 0.25`）当时走的是 15 ms 窗口，也偏短，属于同一类隐患。
- **处理**（`bt_button.c`）：新增 `BT_Button_FlushDelayMs()` 统一决定派发等待时间 —— 网格命令与数值命令用 **`BT_BUTTON_GRID_WAIT_MS = 300 ms`**（这个宏原本定义了却从未被使用），角度命令 15 ms，短前缀 `&l/&r` 25 ms，普通按钮命令仍在精确匹配当拍立即派发。
- **取舍**：300 ms ≫ 一次连续发送内的字节间隔（9600 bps 下相邻字节 ≈ 1 ms），又 ≪ 两次人工按键之间的间隔。若坚持在**串口控制台逐字符手敲**网格命令，字间停顿超过 300 ms 会被提前派发 → 此时加 `\r\n` 或调大该宏。

### 4.12 白名单漏登记：`&cnt` / `&gridclear` / `&show` / `&flash` 曾被静默丢弃

- 白名单是"逐字节前缀匹配"，`&cnt` 不在 `IsCustomPrefix/IsCustomToken` 里 → `&cnt65536` 在蓝牙端被当成非法 token、`invalid_count++`，控制台上却完全正常（两条路径不同）。
- 同类：`&gridclear`（`IsGridCommand()` 的字符过滤把字母判非法）、`&show`、`&flash`。
- **处理**：四个命令补齐到白名单；并且蓝牙事件里"没有任何处理器认领"时现在会打印 **`[BT] unknown command: 'xxx'`**，不再静默。

### 4.13 距离模型换成梯形规划后，`t1000` 的角色变了（2026-09-12，方案 B）

- **旧模型**：`驱动时间 = 距离(mm) ÷ 1000 × t1000`。斜坡造成的固定欠走只能靠标定吸收 → "按 1 格标定则长段偏长、按长段标定则 1 格偏短"，改 `spd` 更是全乱。
- **新模型**：`ZDT_Nav_PlanDriveMs()` 按底盘真实斜率（加 600 / 减 900 RPM/s → A=2556.9、D=3835.4 mm/s²）解梯形/三角形，`t1000` 只当整体微调系数（参考点 = spd 0.50 走 1000 mm）。
- **现场必须做的一次动作**：重标 `t1000`（§6.1）。旧模型的 1900 在新模型下会偏短；理论零偏差值是 **2051**，现在出厂默认/`navreset` 已经直接用这个理论值（§4.23），所以**没标定过也能先按理论跑**，再用卷尺量一次把 `k` 修到 1 附近。
- **判据看两行日志**：
  ```
  [NAV] drive 1.173rev (300mm) FWD spd=0.500 v=533mm/s t=683ms
  [NAV] SEG1 done: 1.170/1.173rev (hold peak 0.21 deg)
  ```
  `v=` 是这次规划用的巡航速度，`t=` 是算出来的驱动时间。1 格现在是 683 ms（旧模型 570 ms），3 格 1726 ms（旧 1710 ms），5 格 2770 ms（旧 2850 ms）。
- **短段自动走三角形**：`spd=0.50` 时短于 **92.5 mm** 就到不了巡航速度（补走用 0.25× 速度时阈值 23.1 mm）。旧模型对短段是线性外推，越短越离谱。
- **顺带修掉"补走只走一半"**：段末补走用 0.5× 速度执行，旧代码时间按全速算 → 只走一半距离 → 误差要补 2~3 次（就是"到点了又倒两步"）。新规划按**实际速度**算时间，一次到位。
- **FPU 已经是开着的**（不用再"打开"）：Keil 目标 Cpu 串是 `FPU3(DFPU)`（双精度），编出来的 axf 里能看到 `VMOV/VADD.F32` 与 `VCVT.F64.F32`；运行时 `SystemInit()` 写 `SCB->CPACR` 打开 CP10/CP11，FreeRTOS 的 `ARM_CM4F/port.c` 还会调 `prvEnableVFP()` 并置 `FPCCR` 的 `ASPEN|LSPEN`，PendSV 按需保存 s16~s31。`FreeRTOSConfig.h` 里的 `configENABLE_FPU 0` 是 CubeMX 遗留、本工程不使用（port 只认 `__TARGET_FPU_VFP`，配错会直接 `#error`）。**核对方法**：`fromelf --text -c` 反汇编 axf，搜 `VMOV`；搜不到才是没开。

### 4.14 转向"大概率进 timeout 区"：死区没人管 + 执行粒度太粗（2026-09-12）

**症状**：`[TURN] done` 经常 >3000 ms（`OVER-3s`）、甚至磨到 8 s 超时；`overshoot` 忽大忽小；**一加 `ki` 就抖**。

**三个数字放一起就是根因**：

| 常量 | 旧值 | 说明 |
|---|---|---|
| `CHASSIS_TURN_MIN_OUTPUT_ERROR_DEG` | 0.20° | 摩擦补偿 kick 只在误差 > 0.20° 时给 |
| `CHASSIS_TURN_BAND_DEG` | 0.05° | 判到位要求误差 ≤ 0.05° |
| `CHASSIS_TX_PERIOD_MS` | 20 ms | kick = 0.08 × 90 RPM → 约 12.5°/s → **一拍走 0.25°**，是判据带宽的 5 倍 |

- **0.05°~0.20° 是无人区**：这里 PID 输出只有 `0.045 × 0.15 ≈ 0.007`（≈0.6 RPM），低于轮子静摩擦 → 轮子根本不转，误差卡住不动 → 一直等到超时。
- **末端是粗 bang-bang**：kick 带着 `|角速度| < 2 dps` 的门限，车一动角速度就超标、门限关掉、车停下、角速度衰减、门限再开…… 一次猛推 0.25°，冲过目标再回来 → 来回蹭。
- **`ki` 为什么越加越抖**：轮子卡住不动时积分器一直在攒，攒过静摩擦就窜出去，过冲后反向再攒 → 极限环。给"执行器分辨率不够"的环加增益必然抖。

**改法（三条一起才有用）**：

1. `CHASSIS_TX_PERIOD_MS` **20 → 4 ms**：末端一拍从 0.25° 变 ≈0.05°，正好等于判据带宽，落点窗约 ±0.025°。CAN 负载 4 轮 × 250 Hz = 1000 帧/s ≈ 500 kbps 的 26%。
2. `CHASSIS_TURN_MIN_OUTPUT_ERROR_DEG` **0.20 → 0.06°**：kick 覆盖到判据带边缘，填掉无人区。
3. **删掉 kick 的角速度门限**（原 `CHASSIS_TURN_MIN_OUTPUT_RATE_DPS`）：kick 方向永远跟着误差符号，不会和车体运动对抗，门限只让末端退化成粗控制。
4. 顺带把**所有到位判据从"拍数"改成"毫秒"**（`CHASSIS_TURN_SETTLE_CYCLES` 10 拍 → `CHASSIS_TURN_SETTLE_MS` 200 ms），否则改节拍会连带改判据时长（20 ms×10=200 ms 变成 4 ms×10=40 ms）。
5. 新增**无进展兜底**：误差已 ≤0.20° 且 `CHASSIS_TURN_STALL_MS(900 ms)` 内再也压不下去（改善 <0.01°）→ 判"到机械下限"，收工并标 **`ST`**。没有它，硬件做不到 0.05° 的那些转向只能磨到 8 s。

**改造后的时间线（90° 转）**：快速段 ~0.6 s（90 RPM 上限）→ 输出跌破 0.08 后以约 12.5°/s 贴靠 ~0.1 s → 进 0.05° 带 → 驻留 0.5 s → 收工，**合计约 1.2 s**。

**日志标记**：

```
[TURN] done  980ms target=+90.00 err=+0.008 overshoot=0.021 peak_o=1.00          ← 主判据（200 ms）
[TURN] done 1180ms target=-90.00 err=+0.031 overshoot=0.044 peak_o=1.00  FB      ← 稳定带（0.5 s）
[TURN] done 1620ms target=+90.00 err=+0.074 overshoot=0.090 peak_o=1.00  ST      ← 无进展兜底
```

看到 `ST` 且 `err` 明显 >0.05° → 这台车的静摩擦/机械就是做不到更细了：要么接受，要么放宽 `CHASSIS_TURN_BAND_DEG`（如 0.08），**不要**去加 `ki`。若 `ST` 的 `err` 还很大（>0.2°），说明**连 kick 都推不动**，先把 `CHASSIS_TURN_MIN_EFFECTIVE_OUTPUT` 从 0.08 往上试（0.10/0.12），或减小节拍（4 → 3 ms）。

### 4.15 比赛提速：转向是"斜坡受限"，不是"速度受限"（2026-09-12）

- 现在有**两档转向**：精确档（手动 `&L90`/`&R90`）90 RPM + 0.05°/0.5 s；**快速档（导航每段前对准）120 RPM + 0.5°/200 ms**，日志行尾标 `FAST`。
- 导航对准敢放宽到 0.5°，是因为对准之后直走有**航向保持**每 80 ms 纠一次，段前对准的验收本身也是 3.0°。
- **时间预算（90° 转，模型值）**：

  | 配置 | 纯运动 | 含驻留 |
  |---|---|---|
  | 精确档 90 RPM（斜坡 600/900） | 0.70 s | 0.90 s |
  | 快速档 120 RPM（本次新增） | 0.60 s | 0.80 s |
  | 快速档 250 RPM（上限打满） | 0.54 s | 0.74 s ← **几乎不再收益** |
  | 快速档 150 RPM + 斜坡 1200/1600 | 0.46 s | 0.66 s ← 目前最快 |

- **结论**：角加速度由底盘轮速斜坡（600 RPM/s ≈ 1039 deg/s²）决定，90° 转根本跑不到高速就该减速。要再快按这个顺序动：

  | 顺序 | 动作 | 收益 | 代价 |
  |---|---|---|---|
  | 1 | `CHASSIS_ACCEL/DECEL_RPM_PER_S` 600/900 → **900/1200**（编译期） | 每个转弯 50~140 ms，**每段起步/停车也一起快** | 起步更易打滑、电流冲击大；方案 B 自动用新斜坡重算，但 `t1000` 建议复验 |
  | 2 | 快速档 `band_deg` 0.5 → 0.8°、`band_ms` 200 → 100 ms | ~100 ms | 段首 0.8° 偏差（航向保持能纠，300 mm 段 ≈ 4 mm 横向） |
  | 3 | 快速档 `max_wheel_rpm` 120 → 150 | ~50 ms | 上限一高同样的 `kp` 更"热"，抖就先降 `kd` |
  | 4 | 规划选**拐点少**的路径 | 通常远大于抠 100 ms | 无（`grid_nav` 已合并同向连续格） |

- 两档数值都在 `Core/Src/chassis_motor.c` 的两个 `const chassis_turn_profile_t` 里（`chassis_turn_profile_precise` / `_fast`），改一处即可，不用碰判据逻辑。
- **不要**用加 `ki` 来提速（§4.14）。

### 4.16 末端抖动（即使 `ki=0`）与"残余误差偏大"：kick 顶掉了刹车（2026-09-12）

- **症状**：转向末段一直抖；把 `ki` 调到 0 也抖；停下时 `err` 偏大（0.5~1.0°）。
- **根因（两条，都在摩擦补偿 kick 上）**：
  1. 旧写法 `if (|PID 输出| < kick) 输出 = ±kick` **无条件顶掉 PID 输出**，包括 **D 项的刹车**。车正在滑向目标时 D 项本来是负的（在刹车），却被顶成正向推力 → 冲过目标 → 反向再来一次 → **极限环**。`ki=0` 时 D 项是唯一阻尼，所以"越调 `ki` 越抖、调成 0 也抖"。
  2. 快速档 `kick_deg` 曾设成 **0.60°**：推力在离目标 0.6° 就撤了，而那个误差下 PID 输出只有 `0.045×0.6 ≈ 0.027`（≈3 RPM，推不动轮子）→ 车停在那儿 → **残余 0.5~1.0°**。
- **改法**：
  - kick 加**运动门控**：先算"朝目标的闭合角速度"`closing = sign(error) × 陀螺角速度`；只有 `closing ≤ 0.30 dps`（该动却没动）才补推力；正在动时**完全交给 PID，连刹车一起保留**。→ 极限环消失，末段变成"推一下—刹住—再推"的收敛过程。
  - 快速档 `kick_deg` **0.60 → 0.10°**，让推力一直工作到离目标 0.1° 以内；推力大小改成**每档独立** `min_push`（精确档 0.05×90 = 4.5 RPM，快速档 0.08×120 = 9.6 RPM）。
- **判据**：改完末端应稳定落在 0.1~0.3°（快速档）以内，`overshoot` 从 ~1° 降到 0.2° 量级，`[TURN] done` 不再需要靠 `ST` 收工。
- **如果还抖**：先确认 `ki` 是默认 0.0005（或 0）；再降 `kd`；最后才考虑把 `min_push` 再调小（调到"车在末端完全不动"就是调过头了，那时会改由 `ST` 收工，`err` 会变成 0.1~0.5°）。

### 4.17 上电去零漂改为 3 s，并在屏幕上显示（2026-09-12）

- **窗口加长**：`HWT101_CALIB_MS` **300 → 3000 ms**（`main.c`），样本数下限仍 20；陀螺零偏用 3 s 平均，噪声小一个量级。
- **新增"静止度"检查** `HWT101_CALIB_MAX_SPAN_DEG = 0.5°`：3 s 的窗口很长，光看"瞬时角速度 ≤1.5 dps"挡不住**慢慢转/被人轻挪**，所以再要求窗口内 yaw 极差 ≤0.5°，否则窗口重来。→ 屏幕上的倒计时会**跳回 0**，这正是"车还在动"的直接提示。
- **屏幕显示**（IPS200 顶部右侧，x=180）：

  | 还没标定完 | `IMU ZERO CAL 2.4s`（倒计时） | 黄色 |

### 4.19 段结束时只更新了格位姿、**mm 位姿从不推进** → 第二次 `&goto` 从错起点规划（2026-09-13）

- **现象**：`&leave` → `&goto 24 3` → `&goto 0 0`，第二次 goto 时"少了一个 180°/90° 回正"，然后**冲出地图外**。
- **根因**：地图改成 mm 位姿之后，执行器段末只调了 `GridNav_SetPose(to_x, to_y)`（格位姿），**mm 位姿一直是"计划时那一份"**。第二次 `&goto` 的 A* 起点取自 `GridNav_GetPoseMm()` → 起点是错的（还是上一个点），于是**段方向和段长全是错的**：车按错误路线直走，看起来就是"该转的没转"+"跑出场地"。
  注意"对准转向"那段代码本身没问题（±180° 会原样传给 `TurnRelativeFast`），错的是**喂给它的目标航向**。
- **修法**：段末按本段名义位移（格数×50 mm，内部 dy 取反 = 地图 +y）累加 mm 位姿；**最后一段直接落到精确目标 mm**（顺便吸收格心吸附的 ±25 mm）。日志新增 `[NAV] pose now (x,y) cell=(a,b) after SEGn`，每次 `&goto` 后能直接核对位姿有没有推进。
- **现场判据**：连续两次 `&goto` 之后看那行 `pose now` —— 它必须跟着走；不动就是这条 bug。

### 4.20 命名点位 `&goto raw` 在蓝牙端被静默丢弃（2026-09-13）

- **现象**：`&goto 24 3` 正常，`&goto raw` **完全没反应**。
- **根因**：`bt_button.c` 的 `BT_Button_IsGridCommand()` 在前缀（`&goto`）后面**只允许数字和空格**，字母一律判非法 → `&goto raw` 这一整条 token 被当垃圾丢掉（`invalid_count++`，什么都不打印）。命名点位是新加的，忘了放宽字符集。
- **同类**：`&startpose 2`、`&nudge u 300`、`&posemm 1200 2250` 带参数但**空格会切断 token** → 参数被丢掉（命令"有反应"但参数没生效）。
- **修法**：① 网格命令前缀后**允许字母**（命名点位）；② 新增 `BT_Button_IsArgCommand()`：网格/数值命令 + `&startpose/&startzone/&nudge/&posemm/&gotomm` 统一"token 内允许空格 + 300 ms 空闲超时派发"。
- **判据**：蓝牙发 `&goto raw` 应回 `[NAV] PATH …`；发 `&xyz` 应回 `[BT] unknown command: 'xyz'`（不再静默）。

### 4.21 目标点不可通行时会"静默吸附"（2026-09-13）

- `&goto 0 0` 是**场地角上**（车 300×300 放不下），固件会吸附到最近的可行格。以前不打印任何提示，现场会以为"走到了 (0,0)"。
- 现在 `GridNav_PlanMm()` 在吸附时打一行 `[NAV] note: not drivable -> snap … stop at (x,y) not (a,b)`。
- **提示**：本场的"回家"点是 `&goto h1`（右下角启停区）或直接 `&home`，**不是** `&goto 0 0`。

### 4.22 日志"每行重复 N 遍 / 字符互相穿插"（2026-09-13）

- **先分清是谁的锅**：现场日志出现"同一行打印 4 遍、字符交错"（如 `PASS: address 3 ret PASS: address 3 ret …`）。
  判据：**找那些固件里"只可能打一次"的行** —— 例如 `[IMU] zero-drift ready`（有 `hwt101_calib_reported` 守卫）、`[ZDT] No motion command … Type help.`（只在 `ZDT_Motor_Begin()` 里）、`TX version query`（`ZDT_CAN_SendVersionQuery()` 只发一帧）。这些行也变成 N 份 ⇒ **不是固件重复执行，而是接收端/显示端把同一份数据渲染了 N 遍**（蓝牙链路重复推送，或串口 App 重绘/复制）。
  → 换一个"原生终端 + 写文件"（PuTTY logging）复测；只接 USB-TTL、断开蓝牙，若重复消失即链路问题。
- **2026-09-13 现场定性（第一层）：不是固件重复执行。** 判据是 `&echo` 自检（§4.24）：
  点一次 `&echo` 收到 **4 条 `[ECHO] n=1 tick=5010ms`** —— **序号相同**。固件里的 `zdt_echo_sequence` 每收到一次命令才 +1，
  `n` 只出现 `1` ⇒ `ZDT_Print_Echo()` **只运行了一次** ⇒ 里面只做了一次 `snprintf` + 一次 `ZDT_UART_Print()`。
  同理每条被接受的命令只回**一条** `OK!`（`ZDT_Motor_Poll()` 里按 `valid_count` 增量打印）。
  （顺带排除"上位机把命令发了 4 次"：那样序号会是 1,2,3,4。）
- **2026-09-13 定向（第二层）：MCU 的 TX 引脚上只出去了一份字节流。** 收发路径全查过：
  ① 所有打印都走同一个 `ZDT_UART_Print()` → 一次 `HAL_UART_Transmit(&huart4, …)`（**阻塞轮询模式，不是 DMA**，所以不存在 DMA 循环重发）；
  ② 全工程只有 `huart4` 一个打印口，**没有第二路镜像**；
  ③ 中断里的日志队列 `ZDT_IsrLog_Service()` 是 head/tail 环，每条 flush 一次后 tail 才前进。
  ⇒ 重复**不在 MCU 内部**。
- **剩下的两个嫌疑（都在 MCU 之后）**：**(i) 蓝牙模块**（多连接/回显配置，同一份数据推给多个 SPP 链路）；
  **(ii) 手机 App 的接收渲染**（把接收缓冲重复渲染/重复追加）。
  现场现象更偏向 (ii)：4 份数据**逐字节相同但相位错开**、`tick` 值相同、连启动时的 `OK!`/开机行都会在发命令之后"重新出现" —— 这更像**接收缓冲被重绘**，而不是干净的行复制。
- **要真正分清 (i)/(ii)，必须换一个独立接收端**（只看同一个 App 永远分不出来）：
  - **最快（1 分钟，不用接线）**：换一个蓝牙串口 App（例如 Serial Bluetooth Terminal）或换一台手机，看每行是不是只出现 1 次；
  - **最确定**：PC + USB-TTL 接 **UART4 TX / GND**，9600 8N1 用 PuTTY 看（发命令可以用手机，也可以直接用 PC 敲）。
    若 PC 上每行 1 次 ⇒ App 渲染的锅；若 PC 上也是 4 次 ⇒ 蓝牙模块/链路的锅（重新配对、或检查模块是否被多个设备占用）。
- **影响面：无功能影响，别再为它花时间。** 命令**只执行一次**（`n=1` 一次、每条命令一条 `OK!`），
  `&spd`/`&t1000`/`&goto`/`&startpose` 都不会被重复执行。**看日志时同一行只读一遍即可**；要留档核对就用原生终端写文件。
- **但固件里确实有一个会加剧它的真问题**：`[ZDT] ver addr=…` 这类诊断是在 **CAN 接收中断**里直接 `HAL_UART_Transmit` 的。它是**阻塞式**（9600 baud 一行 ~30 字符 ≈ 30 ms）且**不可重入** —— 在中断里阻塞 30 ms 会拖延 CAN 接收；与任务里的打印同时进行时两路互相截断/穿插。
  → 已修：`ZDT_UART_Print()` 现在自己判断上下文（`__get_IPSR()`），**中断里只入 4×96 B 的队列**，由任务（`ZDT_Motor_Poll()` → `ZDT_IsrLog_Service()`）flush；队列满则计数丢弃，`&status` 会打印 `isr logs: queued drops=N`（>0 说明日志会缺行，需要放慢诊断频率）。

### 4.23 `nav` 打印过的 `t1000=(xxx mm/s)` 是旧模型的残留，会让参数看着"打架"（2026-09-13）

- **现象**：上电日志里两行参数看着互相矛盾 ——
  `[NAV] spd=0.200 (50 RPM, 213 mm/s)  t1000=2100ms (476 mm/s) …`
  同一个"速度"位置出现 213 和 476 两个数，现场第一反应是"参数被写坏了"。
- **真相**：`476 mm/s` 是拿 `1000000 / t1000` 算出来的**旧线性模型**口径（那时"驱动时间 = 距离/1000 × t1000"，
  所以 t1000 反推出来的确实是个等效速度）。改成梯形规划器之后（见 §4.13）**距离由 `spd` 决定、`t1000` 只是时间微调系数**，
  这个除法已经没有任何物理意义，纯属陈旧的打印没跟着改。参数本身没问题。
- **正确读法**（现固件打印）：
  ```
  [NAV] spd=0.200 (50 RPM, 213 mm/s)  t1000=2100ms  k=1.024 (theory2051ms)  cnt=65536/rev
  [NAV] mode=VELOCITY+TIME  set: spd0.50 / t1000=2051(theory) / cnt65536 / navreset, then `save`
  ```
  `k = t1000 / 理论值`：`k≈1.00` 说明标定与运动学一致；`k=1.024` = 实际比理论慢 2.4%（现场标定的正常量级）；
  **正常范围约 0.5~2.0**；`k>2` 或 `k<0.5` 不是"标定偏了"，而是**单位/常量出错了**（见下），别去拧 `t1000`。
- **顺手修掉的两个坑**：
  ① 打印改掉假速度，改成 `k` + 理论值；
  ② 出厂默认 `t1000` 原本写死 1900 ms（旧模型遗留，比理论 2051 短 7%），现在由 `zdt_motor.c` 启动时用规划器算出的理论值顶掉
  （`Nav_Params_SetReferencePlanMs()`），`navreset` 也一样 —— 否则一旦 flash 记录失效，默认值会**静默短走约 7%**。
  flash 里存过的现场标定值（如 2100）不受影响，照旧覆盖理论默认值。

### 4.23.1 ⚠ 秒 / 毫秒的单位坑：`k=1023.964 (理论2ms)`，以及它会怎么咬人（2026-09-13）

- **现象**：改完打印后第一次上电，日志直接打出
  `[NAV] spd=0.200 (50 RPM, 213 mm/s)  t1000=2100ms  k=1023.964 (理2ms)  cnt=65536/rev`。
- **根因**：`ZDT_Nav_PlanSeconds()` 的返回值是**秒**（参考条件下 2.0508 s），而下游（日志里 k 的分母、以及"没标定时的默认 t1000"）要**毫秒**。
  我在调用点把它当毫秒传进去了，`k = 2100 / 2.0508 = 1023.964`，与日志数字**完全吻合**。
- **为什么这不是"只是打印难看"**：同一个值还喂给了 `Nav_T1000DefaultMs()`，于是
  ① `&navreset` 会把 `t1000` 设成 **2.05 ms**；② flash 记录失效（换板/擦扇区）时开机默认也是 2.05 ms。
  两者都会让每段驱动时间被 `ZDT_NAV_DRIVE_MIN_MS` 夹住 ⇒ **车几乎不动，而且全程一句报错都没有**。
  本板 flash 里有有效记录（2100）才没立刻发作 —— 属于埋在地里的雷。
- **修法（两道）**：
  1. 换算**收进一个函数** `ZDT_Nav_ReferencePlanMs()`（`1000.0f × ZDT_Nav_PlanSeconds(...)`），调用点不许自己乘；
  2. `Nav_Params_SetReferencePlanMs()` 加**区间防呆**：参考时间不在 `NAV_REF_PLAN_MIN_MS~MAX_MS`（50~20000 ms，与 `t1000` 的可调范围一致）内就**拒绝并打 WARNING**，不再静默接受。
     宁可开机多打一行 `[NAV] WARNING: reference plan 2.051ms is out of range …`，也不要"车不走但没线索"。
- **离线复核**（不需要硬件，会打印出固件**应该**打的 `&nav` 行，直接和日志对照）：
  ```
  C:\ProgramData\miniconda3\python.exe tools\check_nav_units.py
  ```
  它从 `chassis_motor.h` / `zdt_motor.h` / `zdt_motor.c` / `nav_params.c` 里读真实常量重算一遍，并检查是否落在防呆区间内。
  当前：`ZDT_Nav_PlanSeconds = 2.0509 s → 2050.9 ms`，`t1000=2100 → k=1.024` ✓。
- **教训（通用）**：凡是"计划值 → 打印值 → 默认值"三处共用的中间量，**单位必须写在函数名里**（`...PlanSeconds()` / `...PlanMs()`），
  并且**下游要有个区间防呆**；否则单位错只会以"距离偏短/车不动"这种远症状出现。

### 4.24 日志"每行重复 N 遍"的判定工具：`&echo`（2026-09-13）

- §4.22 教了"找只可能打一次的行"来分清固件与接收端，但那要靠人记哪行是守卫过的。现在有直接工具：
  发一次 `&echo` → 回一行 `[ECHO] n=7 tick=123456ms`。
  - **序号重复**（`n=7` 出现 4 次）⇒ 固件只收到一次，重复在**接收/显示侧**（App 重绘、蓝牙模块重复推送）。
  - **序号连续**（`n=7,8,9,10`）⇒ 命令**真的被投递了 4 次**，要查上位机发送逻辑。
- 为什么这不只是"日志好看"的问题：重复投递是**功能性**故障，而且不同命令后果不同：
  - `&goto` 重发**不会被忽略**：蓝牙分支每认领一条 `&goto` 就调 `ZDT_Nav_Start()`，而它第一件事是 `ZDT_Nav_Cancel()`
    ——**停车（`CHASSIS_COMMAND_STOP`）+ 回到 IDLE + 按当前位姿重新规划**。表现就是"走到一半突然顿一下又重新起步"，
    或者段方向按旧位姿算错。看到这种"间歇性重启"先怀疑命令被重发，而不是怀疑 A*。
  - `&spd` / `&t1000` 重发只是重复写同一个值，无害；但 `&startpose` 重发会**重置位姿并重对航向基准**，
    连发时后面几次的 3 s 零漂窗口全白等，还会把现场刚摆好的基准冲掉（这行会打密码级别的关键日志：`start zone N: pose=… nose=…`）。
- 用法：接好链路 → 发一次 `&echo` → 看 `n`。更换手机/App/终端后先做这一步，再排查任何"命令没生效 / 走到一半重启"。
- **2026-09-13 现场结果**：手机点一次 `&echo` → 收到 4 条 **`[ECHO] n=1 tick=2822ms`（序号相同）** ⇒ 固件只收到一次，重复在接收端/显示端（详见 §4.22 的结论）。
  发命令是好的：`&echo`/`&nav` 都正常应答，`&nav` 打出了 `spd/t1000/k/cnt` 四个值。

### 4.25 蓝牙 `&` 命令有**两道**白名单闸门，只登记一道 = 静默丢弃（2026-09-13）

**这条是本项目复发最多的一类 bug（§4.12、§4.20、以及 `&echo` 三次），现在有自动校验，改完必须跑。**

一条 `&` 命令要过两个**独立**的闸门，两个都在 `bt_button.c` 里，漏一个的症状各不相同：

| 闸门 | 位置 | 管什么 | 漏了的症状 |
|---|---|---|---|
| ① 逐字节存活 + 超时 | `BT_Button_IsCustomPrefix()`（配合 `IsArgCommand`/`IsGridPrefix`） | 输入到一半的 token 是否"仍可能是合法命令"；**同时决定空闲超时** | 不认 → token 被标 `invalid`；更坑的是 `BT_Button_FlushDelayMs()` 返回 **0** → **永远不按超时派发**，只能等下一次发别的内容时补发 ⇒ 就是"要发两次、收到的总是上一条" |
| ② 派发 | `BT_Button_IsCustomToken()` | 超时到点后 `BT_Button_FlushToken()` 是否把它当文本命令推给上层 | 不认 → 落到按钮表 → `invalid_count++`，**一个字都不打印**（连 `[BT] unknown command` 都没有）⇒ 看起来就像"根本没收到" |

`&echo` 那次就是**只加了①没加②**：打字过程一路正常（所以不像被丢），超时到点被静默丢进 `invalid_count`。
`&wp`（`&waypoints` 的别名，`grid_nav.c` 里一直支持）则是**两道都没有**，从来没在蓝牙上能用过。

- **自动校验**（离线，不需要硬件）：
  ```
  C:\ProgramData\miniconda3\python.exe tools\check_bt_whitelist.py
  ```
  它把 `bt_button.c` 的两道白名单与 `zdt_motor.c` 蓝牙 `BT_BUTTON_CUSTOM` 分支（含 `Nav_Params_/GridNav_/PID_Storage_ProcessCommand` 三个转交解析器）交叉比对，会分别报出：
  **`DROPPED AS GARBAGE`**（②漏了）、**`PREFIX-ONLY (flush drops it)`**（只有①没有②）、以及"白名单认了但没处理器"（会答 `[BT] unknown command`）。
  故意只留给串口的命令写在脚本的 `INTENTIONAL_CONSOLE_ONLY` 里（当前只有 `&delete`），新增例外必须写理由。
- **修法**：新命令**两处一起加**，再跑上面的脚本确认 0 问题。

### 4.26 `&startpose 2` 被静默当成 1 号区 → `&leave` 日志"看着对"、车却半悬在场外（2026-09-13）

**这是本项目最会骗人的一类 bug：日志全对，车走出去了。现场实录。**
用户把车摆在**右上角 2 号区**，发 `&startpose 2` → `&leave`（日志落点 `(2125,450)` 完全正常）→ 发 `&goto raw` → **车直接冲出场地**。

- **根因（一行代码）**：
  ```c
  uint8_t zone = (event.text[9] == '2') ? 2U : 1U;   /* 错 */
  ```
  蓝牙 tokenizer **保留 token 内部空格**（这是刻意的，正是它让 `&t1000 2100`、`&startpose 2` 不被切碎），
  所以 `&startpose 2` 到达时是 `"startpose 2"`，而 **`[9]` 就是那个空格** → 判成 `zone = 1`。
  只有**不带空格**的 `&startpose2` 才是对的 —— 而文档里教的是带空格的那种，于是"2 号区"从来没生效过。
- **为什么日志会骗人**：`&leave`/`&home` 是**相对动作**（前进 300 + 平移 125），动作表按**固件以为的区号**选，落点也是按**固件以为的位姿**累加打印的。
  固件以为在 1 号区、车头 +y，于是打印 `(2125,450)`；而车实际在 2 号区、车头 −y，
  同样的相对动作把它朝**右**多推了 250 mm（半悬场外，右边缘只有 250 mm 余量）。
  接着 `&goto raw` 用错误的起点+朝向规划 → 冲出场地。**三个环节全都"自洽"，只有物理世界不对。**
- **修法（三道）**：
  1. **参数解析**：新增 `ZDT_SkipSpaces()`，`&startpose 1|2` 与 `&startpose1|2` 都支持；
     **参数缺失/写错一律打 `usage`**，不再"默认猜 1 号区"（`&nudge u 300` 同样改用该助手）。
  2. **动作闸门** `ZDT_Script_RequirePoseNear()`：`&leave` 要求当前位姿**还在所选启停区内**（中心 ±150 mm），
     `&home` 要求在**出场落点**附近（±200 mm）；不满足就**拒绝执行**并打印"期望位姿 vs 当前位姿"。
     这条正好拦住本次事故的后续动作（也拦"连发两次 `&leave`"这种会把车顶到围栏的操作）。
  3. **确认行**改成带角位与车头方向，让选错能当场看出来：
     `[NAV] start zone 2 (TOP-RIGHT, nose -y into the field): pose=(2250mm,2250mm); keep still ~3s`
- **离线校验**（新增）：`python tools/check_arg_parsing.py` —— 在 `zdt_motor.c` 里找"固定下标取参数"的写法，
  要求同一个 handler 内必须显式跳过空格。当前 **0 处**；已用"把 `event.text[9]` 注入回去"的负向自测确认能复现本 bug。
- **现场纪律**：换启停区 ⇒ 必须重跑 `&startpose N` 并**静止 3 s**；不确定就先 `&nudge u 300` 自检
  （车头朝反时它会往反方向走，见 §4.16 之后的方向自检条目）。看到 `[NAV] REFUSED …` 不要绕过去，先看位姿对不对。

### 4.27 IPS 屏幕怎么读，以及它为什么会"显示错的"（2026-09-13）

屏幕不是独立的数据源，它**只是一张位姿的投影**。所以"屏幕显示错了"永远是两类原因之一：**位姿错了**（真 bug），或**屏幕画了一个还没有依据的东西**（显示逻辑的锅）。这次两者都有。

**屏幕元素与含义**（`ChassisTelemetry_Show()` → `Dashboard_DrawMap()`，128 px 示意图）：

| 元素 | 含义 | 数据来源 |
|---|---|---|
| 灰底 | 可通行区域 | 固定几何：十字通道 + 外环带 |
| 红块 ×4 | 4 块 450×450 禁区 | 固定几何（x 550–1000 / 1400–1850，y 550–1000 / 1400–1850） |
| **蓝块 ×2** | 两个启停区（右下角 = 1 号，右上角 = 2 号） | 固定几何 (2100,0)–(2400,300) / (2100,2100)–(2400,2400) |
| 青块 ×4 | 原料(上)/粗加工(下)/暂存(左)/二维码板(右) | 固定几何 |
| 黄点 | 固件**以为**车在哪（位姿） | `GridNav_GetPoseMm()` |
| 绿点 | 目标点 | `GridNav_GetTargetMm()`（**只在规划过之后才画**） |
| 品红小方块（3×3 px） | 运行时障碍在**哪个格**（`&obs`） | `GridNav_IsObstacle()` |
| **`OBS n`（品红，地图正下方 y=159）** | 屏幕上画了几个障碍格；带 `+`（如 `OBS 48+`）表示超过 `IPS_MAP_MAX_OBSTACLE_MARKS`(48) 个、没全画 | 统计值 |
| **`ZONE n  POSE x,y`（绿）** | 本次上电跑过 `&startpose` ⇒ 位姿可信；`n` = 固件以为的区号，`x,y` = 它以为的位置(mm) | `ZDT_Script_IsStartPoseSet()` / `ZDT_Script_GetStartZone()` / `GridNav_GetPoseMm()` |
| **`ZONE n? POSE x,y`（黄）** | 只装了**开机默认区**（`ZDT_START_ZONE_DEFAULT` = 2 号区 = 右上角），人还没确认过 ⇒ 位姿是假定值 | 同上 |
| **`ZONE ?  POSE 0,0`（红）** | 连默认区都没装上（初始化异常，正常不该出现） | 同上 |

> 这一行画在地图下沿（y=176）左半边，和右侧遥测文字（x≥150）不重叠。

**这次修掉的两个"显示错的"**：
1. **开机黄点画在默认区**：位姿默认取自 `ZDT_START_ZONE_DEFAULT`（**2 号区 = 右上角 (2250,2250)**，即本队发车区），与车此刻实际摆在哪儿无关。默认区与实际摆放不一致时，屏幕看起来就像"坏了"，其实是"位姿只是假定值"。
   → 地图下方一行区分三种状态：**黄的 `ZONE 2? POSE 2250,2250`** = 只是假定值（还没发 `&startpose`）；**绿的 `ZONE 2  POSE 2250,2250`** = 人确认过；红的 `ZONE ?` = 初始化异常。
   **现场判据：这一行的 `ZONE n` 必须等于车实际所在的区，`POSE` 必须与车实际位置相符，否则不要发 `&leave`/`&goto`。**
   （黄点位置可以离线算：mm→px 是 `px_x = 6 + x*128/2400`、`px_y = 28 + (2400−y)*128/2400`。
   位姿 (2250,2250) → 黄点 (126,36) = 右上角蓝块内；位姿 (2250,150) → (126,148) = 右下角蓝块内。
   所以"黄点在右上角"**等价于**"固件认为位姿是 (2250,2250)" —— 这条可以用来反查区号有没有生效，不是主观判断。）
2. **开机凭空出现一个"目标"绿点**：`GridNav_Init()` 把 `last_target` 预置成 (2250,2250)，而屏幕无条件画目标点 ⇒ 什么都没规划就显示了一个"要去的地方"。
   → 现在目标点只在 `GridNav_GetSegments()` 返回"确实规划过"时才画。

**顺带修掉一个重画滞后**：`GridNav_SetPoseMm()` 只更新 mm 位姿，而版本号（触发重画的 `GridNav_GetRevision()`）原本只在**格**（50 mm）变化时才 +1 —— 同一格内挪动屏幕不会重画，黄点最多滞后 50 mm。现在 mm 变化也 bump。

> 与 §4.26 的关系：`&startpose 2` 曾被静默当成 1 号区，屏幕上的 `ZONE` 格子就是为这种错误准备的当场判据 —— 以前没有任何地方能一眼看出"固件以为我在哪个区"。

### 4.28 工位台面不可接触（`PAD`）与"小幅横移"（2026-09-13）

**两件事都是现场要求，一起改了。**

**① 加工区/原料台/暂存台/二维码板：车体不得接触。**
原来这些区域在网格里只是"语义标记"（`WORK`），车体可以压上去。现在把**台面实物占的那块地面**
单独标成 **`PAD`**，与 `BLOCKED` 一样参与车体膨胀 → 车心必须离它 **≥150 mm**，也就是车体
最多贴到边沿、绝不重叠：

| `PAD` 实物 | 范围 | 车心最近可到 |
|---|---|---|
| 原料台（顶边中央，深 150） | x 1000–1400, y 2250–2400 | y ≤ 2100 |
| 粗加工台（底边中央，深 150） | x 1000–1400, y 0–150 | y ≥ 300 |
| 暂存台（左边中部，宽 150） | x 0–150, y 1050–1350 | x ≥ 300 |
| 二维码板（右边中部，宽 50） | x 2350–2400, y 1100–1300 | x ≤ 2200 |

**关键：`WORK`（功能区语义，含停位空间）必须保持可通行，只有 `PAD`（实物）挡车** ——
一刀切把 `WORK` 禁掉会把整个顶边环带切断，地图直接断开。
跟着改的还有**命名点位**：`raw/rough*/temp*/qr` 从"台面中心"改成**接近点**（台前自由车道的中线，
前后各留 50 mm）：

```
raw   (1200,2250) → (1200,2050)      rough* (·,300) → (·,350)
temp* (300,·)     → (350,·)          qr     (2250,1200) → (2125,1200)
```

离线校验结果：可行格 **864 → 734**，**全场仍全连通**，四个接近点都可行。
（`&goto raw` 这类命令名字不变，只是落点更保守了。）

**② 小幅度让位改用横移，不再"转 90°→走一点→转回 90°"。**
新规则（`ZDT_Nav_SegmentStrafeSign()`）：

| 情况 | 动作 |
|---|---|
| 段长 **≤ 3 格（150 mm）** 且相对当前车头是**纯横向** | **不转车头，直接横移**（只给 `vy`） |
| 跨度 >3 格的横向段 | 照旧**原地转 90°** 再走（这算改变方向） |
| 反向（掉头）/ 其它方向 | 照旧**原地转** |

- 为什么值得：A* 在环带里选车道时会产出 1 格让位，老做法是两次原地转（≈1.5~2 s）+ 两次 ±0.5° 对准残差；横移一次走完，**全程航向不变**。实测规划：`h2→h1` 由 4 次转降到 **1 次转**（`turn+go D750 | strafe L50 | go D1300 | strafe R50`）。
- 横移段的两处特殊处理（改这块代码时必须一起考虑）：
  1. **不做直走里程复核**：横移时四轮转向是 `[1,-1,-1,1]`，用直走的 `[1,1,1,1]` 投影量出来≈0，会误判成"没走"并触发段末补走；横移只走**时间规划 + 停稳判据**。
  2. **航向保持的目标是"开始横移时的车头"**，不是本段的地图航向（后者与车头差 90°，照它纠会把车拧过去）；段末的"航向漂移 >20° 报警"也对横移段跳过。
- 日志判据：横移段打 `[NAV] strafe 50mm LEFT/RIGHT (no turn) spd=… t=…ms`，段末打 `[NAV] SEGn done (strafe 50mm, no turn)`；直走仍是 `[NAV] drive … FWD/BACK`。

### 4.29 `&cross`：从一个启停区直走到另一个启停区（2026-09-13）

一条指令走完整段路，中途只有**一次**转向：

```
&cross          # 去"另一个"启停区（当前区号自动取反）
&cross 1 / &cross 2   # 明确指定目标区；已经在那个区则拒绝并提示
&cross1         # 不带空格也行（参数解析走 ZDT_SkipSpaces）
```

动作序列（以 1 号区 → 2 号区为例，日志逐行可核对）：

| 步 | 动作 | 地图位移 | 落点 |
|---|---|---|---|
| 1 | `FWD 300`（出场前进） | y +300 | (2250, 450) |
| 2 | `STRAFE-L 125`（平移到右边缘车道） | x −125 | (2125, 450) |
| 3 | **`FWD 1500`（沿车道直走）** | y +1500 | (2125, 1950) |
| 4 | **`TURN 180`（掉头）** | — | (2125, 1950)，车头翻转 |
| 5 | `STRAFE-L 125`（平移回区轴线） | x +125 | (2250, 1950) |
| 6 | `BACK 300`（后退进区） | y +300 | **(2250, 2250) = 2 号区中心** |

- **为什么必须掉头**：两个区都要求车头朝**场地内**（1 号区朝 +y、2 号区朝 −y），方向正好相反。
  沿同一条车道直走过去车头朝向不变，于是到对面时车头朝着场外 —— 那样下一次 `&leave` 的"前进"直接撞墙。
  掉头放在**车道尽头**做（那里有空间），做完正好用"平移 + 后退"进区。
- **直走量是 1500 mm，不是 2100 mm**：算的是两个**出场落点**之间（450 → 1950），
  不是两个区中心之间（150 → 2250）——出场已经朝场地内走了 300、进区还要走 300。
  ⚠ 这里写错过一次（按 2100 算，车会多冲 600 mm 撞对面墙），`tools/check_map.py` 的
  `&cross` 端位自检当场抓到（两个方向都必须精确落到目标区中心）。
- **到位后自动切区**：调用 `ZDT_Script_SetStartZone(目标区)`，一并更新
  ① 当前区号（屏幕 `ZONE n` 跟着变）② 位姿（精确到区中心）③ **车头绑定（必须翻转！）** ④ 重对陀螺零漂。
  所以**到位后要静止约 3 s**（屏幕 `IMU ZERO CAL x.xs` → `IMU ZERO DONE`），这期间转向会被拒。
- **起手闸门**：与 `&leave/&home` 同一套位姿检查 —— 起手不在当前启停区里会打
  `[NAV] REFUSED &cross` 而不是硬走（相对动作从错起点会冲出场）。
- **日志判据**：`[NAV] cross: zone 1 -> zone 2, straight 1500mm on lane x=2125, then 180 turn`
  → 6 行 `[NAV] script i/6: …`（含 `TURN 180 (face into the field)`）
  → `[NAV] cross done: now in start zone 2 (keep still ~3s)`。
- **不要与 `&home` 混用**：`&cross` 自己就把车**停进**目标区了，不需要再 `&home`；
  而 `&leave`/`&home` 只是"出/进当前区"。跨区之后想再跨回来，再发一次 `&cross` 即可。

### 4.30 走中线 / 先出库 / 出库后不碰启停区（2026-09-13 现场三条要求）

**① 尽可能让车走在路中间。** 原来 A* 只保证"格心可走"，外环带 550 宽、膨胀后 6 格可走，
它可能挑贴着场边的那一格 —— 车看起来就是"贴着墙走"。现在两层保证：

| 层 | 做法 | 效果 |
|---|---|---|
| 规划层（软约束） | A* 每格加 `GRID_NAV_LANE_COST_PER_CELL(3) × 偏离车道中线的格数`（`GridNav_LaneDeviationCells()`），中线 = **275 / 1200 / 2125** | 路径自然收敛到中线附近；**实测 `exit1→raw`、`exit2→rough2` 都从 3 段降到 2 段**（少一次中途让位） |
| 执行层（起步对齐） | `ZDT_Nav_ComputeLaneSnap()`：起第一步前算"与第一段垂直那一维"离中线的偏差，>40 mm 就**先横移过去**（1 步脚本，跑完自动接着跑导航），日志 `[NAV] lane centring: strafe Nmm LEFT/RIGHT to the nearest lane centre` | 车从任意位置出发都会先回到中线；偏差 ≤40 mm 不动（车道中线落在格边界上，格心天然偏 25 mm） |

**①b 平移段也做距离复核（2026-09-13 补）。** 原来只有**直走段**在段末做"量里程 → 残差补走"，
横移段被我特意跳过，理由是"横移四轮是 `[1,-1,-1,1]`，用直走的 `[1,1,1,1]` 投影会量出 0"。**这个顾虑是错的**：
`ZDT_Nav_MeasureDistance()` 是拿**每一轮自己的投影分量**当分母（`delta_rev / wheel_values[i]`），
横移时那组分量正是 `[1,-1,-1,1]`，本来就量得对。代价是横移段一直没有距离闭环。
现在横移段同样走"量 → 补"（日志 `[NAV] revs … (strafe)`、`[NAV] correct ±0.0xx rev STRAFE`），
并且**补走必须走横移通道（`vy`）**——走直走通道会朝前/后补一段，横向残差原封不动。
（`&leave/&home` 的 125 mm 平移走的是**脚本**那条路，不是 A* 段，所以不在这次改动范围内。）

**①c 脚本步也做航向闭环（2026-09-13 补）。** 导航的直走/横移段一直有航向闭环（`ZDT_Nav_HeadingHoldTo`，80 ms 一次），
而**脚本动作**（`&leave`/`&home`/`&cross` 里的每一步）原来是**纯开环**：给速度、定时、停，中间不看陀螺。
后果最明显的是 `&cross` 那条 **1500 mm 直走**（`spd=0.2` 下约 **7.5 s**）：车头一旦慢慢偏就没人管，
而它后面接的掉头/平移/后退都是**相对**动作 ⇒ 段末歪多少、落点就偏多少，车停在区里是**斜的**。
现在每步开始时记下当时的车头，走行期间每 80 ms 纠一次（`ZDT_Script_HeadingHold()`，
kp/限幅/死区与导航**完全相同**；速度通道按本步方向给 —— 直走 `vx`、平移 `vy`）。
掉头步不参与（转向有自己的 PID）。日志没新增行：纠偏是静默的，看屏幕 `ANG` 是否钉住即可。

**② 起步时无论发什么指令都先出库。** 车还在启停区里时收到 `&goto …`：

```
[NAV] car is in the start zone: leaving first, then running the goto
→ 自动执行 &leave（前进 300 + 平移 125 到车道中线）
→ [NAV] script done: pose=(2125,450)
→ [NAV] now planning from the exit point   ← 用**出场后的位姿**重新规划
→ 正常出发
```

- **为什么要重新规划**：出场把车从区中心挪到了出场落点，用旧位姿算出来的路径起点/段长全错
  （§4.19 那次"冲出场地"就是同一类错）。所以推迟到出场结束再按 `goto <目标 mm>` 重规划。
- 区三面是围栏/场边，从区中心直接往外走没有路，只有"先前进再平移"出得去 —— 这也是让指令
  "无论是什么"都能安全起步的原因。
- **不受影响的命令**：`&leave` / `&home` / `&cross`（自己就管进出）、`&nudge`（自检必须就地走）、
  手动 `&U/&D/&L/&R`、`&L90`（人在直接操纵，不该被自动带走）。

**③ 启停区可以经过（2026-09-13 现场更正）。** 原来这里有一条"**出库后不得再碰到启停区**"，
做法是 `&leave` / `&cross` 结束时把**刚离开的那个区**锁成"车体不可接触"（`GridNav_SetZoneNoTouch()`），
`&startpose N` 才解锁。现场确认两个启停区就是地面上两块 300×300 的区域、**车可以正常压过去**，
所以这套锁定**已整段删除**（`GridNav_SetZoneNoTouch()` / `GridNav_GetZoneNoTouch()` /
`GridNav_RectOverlapsLockedZone()` 三个函数与 `zdt_motor.c` 里的三处调用全删）：

- **为什么删掉是对的**：锁着的时候 A* 必须绕开区，顶角那段路被迫走远路；而且离线基线因此分成两套
  （不锁 734 格 / 锁 699 格），固件当时跑的是 699 那套 —— **离线报告与现场不一致**。
  圆弧过弯的几何判定里也带着"不可碰锁定区"，区口的转角被无谓拒掉。
- **现在**：`check_map.py` 不再模拟锁定，**离线基线 734/2304 格、全连通与固件完全一致**；
  仍在的约束只剩物理那几条：场边、四块 450 黄区、四个工位实物台面（PAD）、运行期障碍格。
- **没有改的东西**：`&leave` / `&home` / `&cross` 的位姿闸门（`[NAV] REFUSED`）照旧 ——
  它管的是"车是不是真在它以为的地方"，跟"能不能压过去"是两件事。
- ⚠ 一个小提醒：`&goto` 的"车在区里就先出库"仍然按**位姿是否落在区盒子里**（中心 ±150 mm）判断。
  区现在可以过路，所以万一车停在区里（例如刚 `&home`），下一条 `&goto` 仍会先执行一次出库动作 ——
  这是期望行为（车确实在库里）；正常任务流程里车不会在区内停住，所以不影响。

### 4.31 段末补走已关闭：不补走时位置刚刚好（2026-09-13 现场结论）

- **现场观察**：车**不补走**的时候位置**刚刚好**；补走（`[NAV] correct -0.0xx rev …`，残差为负时车往回退一点）
  反而把车推偏。
- **为什么会这样**：时间规划本身已经把距离算对了 —— 系统性的欠走/多走早被 `t1000`（微调系数 `k`）吸收；
  而这里算出来的残差主要来自**里程回读的偏差**（打滑、轮径/刻度误差、四轮不一致）。
  拿一个**有偏的测量**去"纠正"一个**本来正确的动作**，结果就是引入新误差。
  雪上加霜的是补走本身也是时间规划：受 `ZDT_NAV_DRIVE_MIN_MS` 下限与加/减速斜坡影响，
  几毫米的残差会走出十几毫米的动作。
- **改法**：`ZDT_NAV_END_CORRECTION_ENABLE` 置 **0**（`Core/Src/zdt_motor.c` 顶部）。
  现在**照常测量、照常打印**，只是不再驱动补走：

  ```
  [NAV] revs FL+1.171 FR+1.176 RL+1.170 RR+1.174 spread=0.006
  [NAV] residual -0.004rev (-1mm), no correction by design     ← 有残差但不动车
  [NAV] SEG1 done: 1.177/1.173rev (hold peak 0.31 deg)
  ```

  想恢复闭环只改这一个 `#define`，别的都不用动。残差大到超过 `ZDT_NAV_CORRECT_MAX_REV`（0.5 圈）时
  仍会打 `odometry suspect`（那是真异常：符号/单位/打滑），与"要不要补走"无关。
- **要修"系统性走不到位/走过头"该动哪里**：`&t1000`（或 `&spd`），**全局一次标定**，别用每段补走凑。
  现在每段都会打印实测值，正好是标定的依据：连续几段都差同一个比例 → 按比例调 `t1000`；
  上电日志里 `&nav` 的 `k=…` 就是"实测/理论"的现成读数（`k>1` = 实际走得比理论慢）。
- **注意**：补走关闭后**最后一段仍然精确落到目标 mm**（末段位姿直接写目标 mm，不靠补走），
  所以停位精度不受影响；段间也不会再出现"顿一下再倒回去"的两拍。

### 4.32 起始车道居中的横移方向曾经会反（两套坐标混用，2026-09-13 现场 bug）

- **现场现象**：`qr → raw → rough → rough1-2-3 → raw` 这种任务链，**最后一段回 `raw` 时横移方向是反的**，
  车往错的方向平移，**压线**。
- **根因（典型的两套坐标混用）**：`ZDT_Nav_ComputeLaneSnap()` 算"把车横移到最近车道中线"的方向时，
  用**规则图 mm**（y 向上）的偏移量去点乘**内部帧**（y 向下）的车体右向量 `R = (-F.y, F.x)`：
  ```c
  /* 错：delta 是规则图 mm，R 是内部帧 */
  *body_sign = ((delta * r_x) + (0.0f * r_y)) > 0.0f ? 1 : -1;
  ```
  **x 分量在两套坐标里不翻**，所以"横向是 x"时恰好蒙对；而**横向是 y 时符号整个反掉**。
- **为什么正好在回 `raw` 这一段发作**：从 `rough3` 去 `raw` 要沿**顶边横向行驶**（行进方向是 x），
  这时需要修正的横向恰好是 **y** → 命中了出错的那一支 → 横移反向 → 朝场边/PAD 压过去。
  沿 y 行驶时（修正 x）则一直是好的，所以之前一直没暴露。
- **修法**：偏移量先翻成内部帧再点积（`di = (map_dx, −map_dy)`）：
  ```c
  di_x = *map_dx;  di_y = -(int32_t)(*map_dy);
  *body_sign = ((di_x * r_x) + (di_y * r_y)) > 0.0f ? 1 : -1;
  ```
- **新增离线守卫** `python tools/check_frame_signs.py`：对**每种车头朝向 × 每种可达的横向修正**
  做"地图偏移 → 车体方向 → 回推地图位移"的**往返一致性**检查，并且带**负向对照**
  （把旧公式一起算一遍，确认它在 4 个组合上确实是反的）。当前结果：
  ```
  nose 2 (+x)  offset (0,+100): fixed=-1 old=+1   <-- old formula was REVERSED here
  nose 2 (+x)  offset (0,-100): fixed=+1 old=-1   <-- ...
  nose 3 (-x)  offset (0,+100): fixed=+1 old=-1
  nose 3 (-x)  offset (0,-100): fixed=-1 old=+1
  PASS: every offset round-trips with a consistent sign, and the negative control
        reproduces the field bug
  ```
  这条守卫专门用来防"又有人在某个新函数里拿规则图 mm 直接和内部帧向量做运算"。

### 4.33 转向耗时是**运行参数**：`&t90` / `&t180`（给 A* 选路用）

规划器要比较"转向时间 + 行驶时间"才能选对路线（见地图文档"代价模型"一节），
所以"转一次到底多久"必须准。它是**运行时参数**，现场实测后填，不用重编译：

```
&t90 1000         # 直角（90°）耗时，毫秒（当前默认 1000）
&t180 2000        # 掉头（180°）耗时，毫秒（当前默认 2000）
&save             # 存进 W25Q64；&read 读回来；&navreset 恢复默认
&nav              # 打印当前值（含新的一行 turn cost）
```

**怎么实测（不用尺子、不用秒表）**：每次转向结束固件都会打一行体检，里面的毫秒数就是实测值：

```
[TURN] done 1680ms target=+90.00 err=+0.008 overshoot=0.014 peak_o=1.00  FAST
```

- 连发 3~5 次 `&L90`（或 `&R90`），把 `[TURN] done <ms>` 的毫秒数取平均 → 填给 `&t90`；
- 连发 3~5 次 `&L180`，同样取平均 → 填给 `&t180`；
- 这个数**已经含**加减速斜坡与停稳时间 ✓ 正是代价模型需要的口径。
- ⚠ **要读带 `FAST` 标记的那些行**：导航段前对准走**快速档**（0.5° 收工、上限 120 RPM），
  而手动 `&L90`/`&R90` 走的是**精确档**（0.01°/200 ms）→ **明显更慢**。
  拿 `&L90` 的毫秒去填 `t90` 会把"转向"估得比导航实际更贵 ⇒ 规划器会更爱绕路。
  正确的取数方式：跑一次带拐弯的 `&goto`（例如 `temp → rough` 会拐 2 次），
  读日志里 `[TURN] done <ms> … FAST` 的毫秒数取平均 ✓。

**它怎么影响选路**：单位是"格数当量"。执行器在每次规划前按当前 `spd` 折算：
`t90 相当于走几格 = GRID_NAV_MOVE_COST × (t90 / 走一格的时间)`。
所以 `spd=0.2`（一格 235 ms）时 `t90=1000` → 相当于 **4.3 格**、`t180=2000` → **8.5 格**；
`spd=0.5`（一格 94 ms）时同样 1000 ms → 相当于 **10.6 格**（快走时转向更贵，更值得绕路）。

- **注意 flash 记录版本变了**：参数结构新增了两个字段，`NAV_STORAGE_VERSION` 从 2 升到 3。
  旧的 v2 记录会被判无效，**上电会明确打印**：
  `[NAV] flash record v2 is obsolete (now v3): spd/t1000/cnt/t90/t180 are back to defaults, please set them again and save`
  → 按提示把 `spd` / `t1000` / `cnt` 重新设一遍再 `&save`（现在 `&nav` 就能读到当前值照抄）。

### 4.35 `&obs 1200 1200` 在屏幕上"不显示"（2026-09-13 现场）

**现象**：发 `&obs 1200 1200`，串口正常回显、`&grid`/规划也确实绕开了，但 IPS 地图上**看不出障碍在哪**。

**原因（两个叠加，都不是指令没生效）**：

1. **屏幕根本没画障碍的位置**。旧代码只在"至少存在一个障碍"时，在地图**左上角**点一个 5×5 的品红点当"存在提示"，从不按真实格位画 —— 角落那个点在黑底上又小又像界面杂点，`&obs 1200 1200` 落在地图正中（格 (24,23)、格心 (1225,1225)）就更什么都看不到。
2. **一根 50 mm 格在 128 px 示意图上只有约 2.7 px**，即使按位置画也是"一粒沙"，必须放大到 3×3 px 才肉眼可见。

**现在的行为**（`Dashboard_DrawMap()`）：

* 每个障碍格在它的格心位置画 **3×3 px 品红方块**（`px_x = 6 + 格心mm_x*128/2400`、`px_y = 28 + (2400−格心mm_y)*128/2400`）；
* 地图正下方多一行 **`OBS n`**（品红，y=159），一眼看出"设了几个"；超过 `IPS_MAP_MAX_OBSTACLE_MARKS`(48) 个就不再逐个画（面板是 SPI 逐像素推，画多了卡屏），此时角落补一个提示点、该行显示 `OBS 48+`；
* 那行**定宽输出、空格补黑底**，所以个数变少或 `&clear` 清零后不会留下残影；
* 图例同步改成 `Y CAR  G GOAL  M OBS  C PATH`（旧图例写的是 `R OBS`，颜色名都错了）。

**验证（离线手算，`&obs 1200 1200`）**：mm(1200,1200) → 格 (24,23) → 格心 (1225,1225) → 屏幕 **(71,90)**，即 3×3 方块画在 x 70..72 / y 89..91 —— 地图区域是 x 6..134、y 28..156，正中约 (70,92)，**对得上**。

**顺带说明为什么"改了之后马上就变"**：`GridNav_SetObstacle()` 会 `grid_nav_revision++`，而屏幕在版本号变化时整幅重画地图（`freertos.c` 里 `cached_map_revision != GridNav_GetRevision()`），所以 `&obs`/`&free`/`&clear` 下一拍就会刷新，不需要重新上电或 `&startpose`。

### 4.36 90° 圆弧过弯：`&tarc` / `&aspd`（2026-09-13 现场提问后实现）

**现场问题**："如果采用圆弧过弯的话是不是会更快，可不可以尝试一下" → "设置个参数：90° 圆弧过弯需要的时间（时间越短半径越小），然后让我调整，以及速度"。

**改了什么**：直角不再是"到角点 → 停车 → 原地转 90°（车轮在转、车**不往前**，现场约 1 s）→ 再起步"，
而是一段**边走边转**的四分之一圆。参数只有一个旋钮 + 一个速度比例：

| 参数 | 含义 | 默认 |
|---|---|---|
| `&tarc <ms>` | 90° 圆弧**目标耗时**。0 = 关闭。**时间越短半径越小**：`R = 2·v·T/π` | **0（关闭）** |
| `&aspd <比例>` | 圆弧时的车体速度 = 当前 `&spd` × 本比例（1.00 = 与直走同速） | **1.00** |

改完 `&save` 存 flash；`&nav` 会把这套参数换算成**半径与外轮转速**打出来：

```
[NAV] arc: tarc=1000ms aspd=1.00 -> v=213 mm/s R=136 mm outer 161 RPM (cap 250)
```

**两件必须知道的事（固件都做了钳位，并且会打在日志里）**：

1. **几何**：圆弧中途车头正好斜 45°，车体扫过的是 **212 mm 外接圆**（300×300 的对角线；原地转其实也是这个圆）。
   所以半径不是想给多大就给多大 —— 固件用 `GridNav_RotatedBodyFreeMm()`（分离轴，精确矩形）在圆弧上取 9 个位姿逐个判定，
   不过就**逐 5 mm 降半径**，降到 50 mm 还不行就**放弃圆弧、照旧原地转**：
   ```
   [NAV] arc armed: corner (2125,1200) R=136mm +90deg v=213mm/s t=1069ms outer=161RPM (this leg -136mm)
   [NAV] arc refused: corner (1225,1150) wants R=136mm, geometry allows less than 50mm -> in-place turn as before
   ```
   实测（离线，`tools/analyze_arc.py`）：**场地里绝大多数直角都能过圆弧**，但**启停区边缘那两个转角**（车还在区里、
   离场边只有 150 mm）以及 `(1225,1150)` 这种贴着黄区的转角**过不了**，会按老办法原地转。
2. **轮速**：麦轮外轮要跑 `v × (1 + 300/R)`（`CHASSIS_SPIN_ARM_MM` = 半轴距+半轮距 = 300 mm）。
   `R` 越小外轮越吃紧，超过满量程 250 RPM 时底盘 Mix 会**整体缩放**（半径不变、车变慢）。
   所以 **`tarc` 并不是越小越快**：`spd=0.2` 下低于约 600 ms 就吃满轮速、实际反而更慢。日志里会标 `[wheel-cap slowed]`。

**圆弧靠什么闭环（现场追问"不能通过姿态传感器来进行圆弧转弯吗"）**：

| 环节 | 靠什么 | 说明 |
|---|---|---|
| "转够了没有"（**收工判据**） | **姿态传感器（陀螺）** | `\|目标航向 − 当前航向\| ≤ 1°` 就停车。规划时长只当**超时兜底**（+400 ms），超了会打 `arc timeout` 并照常收工 |
| 转的**快慢**（每 80 ms 纠一次） | **姿态传感器** | 期望航向按时间线性推进，用陀螺误差按 P 律补 `omega`（死区 0.2°、限幅 0.20） |
| 圆弧**半径/走向**（前馈） | 时间规划 | `vx = v`、`omega = v/R` 同时下发；麦轮"边走边转"必然打滑，所以这只是前馈 |
| **位移记多少**（位姿） | 时间规划 + 陀螺 | 弧长取规划值（"走多少"由 `t1000` 标定过），**半径按实测转角反算**：`R_act = 弧长 ÷ 实测转角`，弦 `= 2R_act·sin(θ/2)`。跟不上时自动修正位姿，避免"第二次 `&goto` 从错起点规划"那类老 bug |
| **绝对位置**（横向落在哪） | ✗ 没有传感器可闭 | 车上只有轮编码器（打滑时不可信）与陀螺（只有角度），**没有外部定位**。所以圆弧的横向精度最终靠"车道够宽 + 段末不补走"这条已验证的策略 |

> 一句话：**"转到 90°"这件事现在是姿态传感器说了算，时钟只负责兜底**；能不改的是"走了多远"，那仍然靠标定。
> 现场判据还是 `ARC done` 那行：`by sensor` = 陀螺转到位收工（正常），`by timeout` = 打滑严重没转够（要降 `&aspd`）。

**现场会看到的日志**（一次圆弧）：

```
[NAV] arc armed: corner (2125,1200) R=136mm +90deg v=213mm/s t=1069ms outer=161RPM (this leg -136mm)
[NAV] SEG1 done: ... [arc: leg shortened by R]                ← 本段只走到角点前 R
[NAV] ARC start: R=136mm +90deg vx=0.200 omega=+0.444 t=1069ms outer=161RPM
[NAV] ARC done: R=136mm(act 140) +90deg(meas +89.4) 1040ms by sensor, heading err +0.6 deg, pose now (2125,1200)
[NAV] arc timeout: heading still off -12.3 deg after 1469ms (wheels slipping); stopping anyway
[NAV] arc refused: corner (1225,1150) wants R=136mm, geometry allows less than 50mm -> in-place turn as before
```

`ARC done` 那行是圆弧的完整体检：`act` = 实测反算的半径（≈ 规划值说明没怎么打滑）、`meas` = 实测转角、
`by sensor / by timeout` = 收工判据、`heading err` = 最终航向残差（超 0.5° 时下一段自动补一次原地对准兜底）。

**离线预期收益**（`python tools/analyze_arc.py`，`spd=0.2`、`tarc=1000`、`aspd=1.0`，模型与固件同一套）：
每个能过圆弧的直角 **省约 1.2 s**（`exit1→raw` 13.9 s → 11.5 s，两个直角省 2.4 s），
整组标准路线的总时间 **−8%**。省下来的量来自：原地转那 1 s 的空转 + 圆弧比"两段直线"短 0.43R。

**`tarc` 旋钮对照表**（`spd=0.2`，`aspd=1.0`）：

| `&tarc` | 半径 R | 外轮转速 | 实际圆弧耗时 | 说明 |
|---|---|---|---|---|
| 400 ms | 54 mm | 326 RPM | 592 ms | **吃满轮速**、底盘自动降速 → 反而更慢 |
| 600 ms | 81 mm | 234 RPM | 669 ms | 可用区间下沿 |
| **1000 ms** | **136 mm** | **161 RPM** | **1069 ms** | **建议起点** |
| 1500 ms | 203 mm | 124 RPM | 1569 ms | 转得温柔，省钱少 |
| 2000 ms | 271 mm | 105 RPM | 2069 ms | 大半径，只在宽环带里放得下 |

**上机测试步骤（建议顺序）**：

1. `&nav` 确认 `spd=0.200`、`t1000`、`cnt`（flash 记录版本升到 **v4**，第一次上电会打印 `flash record v3 is obsolete`，
   需要重设 `&spd 0.2` / `&t1000 2100` / `&cnt 65536` 再 `&save`）。
2. `&tarc 1000`、`&aspd 1.00`，然后 `&goto raw`（`exit1` 有两次直角、路也长，最能看出差别）。
3. 打**表**：同一条 `&goto` 跑一次 `&tarc 0`（关闭）再跑一次 `&tarc 1000`，比时间。
4. 看 `ARC done` 的 `heading err`：>2° 就把 `&aspd` 降到 0.8/0.6 再试（圆弧的航向跟踪比直走难，速度越低越稳）。
5. 觉得稳了再试 `&tarc 800`；**不要**试 600 以下（轮速吃满，反而更慢，日志会标 `[wheel-cap slowed]`）。
6. 满意就 `&save`。以后想关掉发 `&tarc 0` 即可，**不用重新烧录**。

> ⚠ **A\* 仍然按 `&t90`（原地转的耗时）选路**，不按圆弧的耗时算 —— 这是故意的：A\* 不知道哪个转角会被几何拒绝，
> 按"最坏情况"规划更稳，圆弧只是让**执行**比计划更快。想让规划器也认为转角便宜，就手动把 `&t90` 调小。
> 另外 `&tarc` 只作用于**直角（90°）**：掉头（180°）和 ≤3 格的横移让位都不走圆弧（180° 圆弧扫过的面积是直角的两倍多，环带里放不下）。

## 5. 症状 → 排查路径

### 5.1 车不走 / 只走一点点

1. `&nav` 看 `spd`：太小？→ `&spd 0.3` 试。
2. `&goto` 时看 `[NAV] applied rpm`：远小于 `spd×250` → 下发链路问题（查 §4.1）；等于设定值而车只走一点点 → 垫起车看轮子是否真转（打滑/堵转/供电）。
3. 看 `[NAV] revs FL.. FR.. RL.. RR.. spread=..`：**四轮差异大** → 某轮驱动器/接线异常（§4.4 遗留项）。
4. 段末 `odometry suspect`：里程误差超 0.5 圈被跳过矫正 → 先确认 `cnt` 与距离刻度。

### 5.2 走偏 / 斜着走

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 整体斜 45° | 只有一对角线在驱动（位置模式缓存+触发路径） | `posmode 0` |
| 斜 30°+ 且方向固定 | 航向基准与摆放不一致 | 摆好车头 → `&zero` |
| 段的**方向反了** | 摆放约定与 `ZDT_NAV_MAP_FORWARD_PLUS_Y` 不匹配 | 改宏或按 +y 摆放 |
| 直走终点偏差 0.5~1° | 走行航向漂移 | §4.8 航向保持（已实现） |
| 横移方向反 | 麦轮是镜像底盘（情况 2） | 换轮或统一翻符号，见方向文档 §3.2 |

### 5.3 距离不准

- **稳定地**偏短/偏长 → 调 `t1000`：实际走 250 mm（要 300）→ 按 `k` 等比放大：`t1000 = 当前 × 300/250`（例：2100 × 1.2 = 2520），再 `&save`。理论值 2051（`k=1`）。
- **乱跳**（同段两次差别大）→ 打滑或某轮异常，先看 `revs` 的 `spread`。
- 只改过 `spd` 之后距离变了 → 新模型下**不该**再变（`spd` 直接进运动学公式）；若真变了，先查 `&nav` 的 `k` 是否被人改过，别急着拧 `t1000`（§4.23）。

### 5.4 转向抖动 / 太慢 / 不到位

1. 看每次转向那行体检：
   ```
   [TURN] done 1680ms target=+90.00 err=+0.008 overshoot=0.014 peak_o=1.00
   [TURN] done 2410ms target=-90.00 err=+0.041 overshoot=0.062 peak_o=1.00  FB
   ```
   - `>3000ms` 会标 `OVER-3s`（目标是 ≤3 s）。
   - `err` 是**判到位那一刻的残余误差**（3 位小数）：≥0.01 且带 `FB` → 靠 0.05°/0.5 s 稳定带停的，见 §4.9。
   - `overshoot` 大 → 阻尼不够 / P 太大。
   - `peak_o` 长期 1.00 → 吃满转向上限。
   - 一行 `[TURN] rejected: need &EN and IMU zero-drift ready` → 没使能或零漂没就绪（§4.10）。
2. 先分清**机械还是供电**：`&dis` 后垫起车、再 `&EN` + `&L90`，离地顺不顺？
   - 离地顺、落地抖 → 供电跌落（×10 修正后电流是原来的约 10 倍）或地面打滑；
   - 离地也抖 → 控制参数（降 `kd` 再降 `kp`）或速度上限偏高。
3. 在线调：`&kp 0.04` → `&L90` → 看 `[TURN] done` → 满意 `&save`。

### 5.5 命令发出去没反应

- 该命令是否在 §3.2 的清单里？（`where`/`tlog` 已删除）
- 是不是带了空格？→ 除 `&nav/&spd/&t1000/&cnt` 外都不支持。
- 是新增命令吗？→ §3.2 末尾那两处白名单都改了吗？
- 有 `OK!` 但没有输出 → 说明 token 被接受但分支没匹配（看串口 `usage:` 提示）。

## 6. 调参流程

### 6.1 距离（最常用）

1. 摆好车 → `&zero` → `&EN`；
2. 跑一段已知长度（`&goto 0 1` = 300 mm，走 3 格更准）；
3. 卷尺量实际位移 `L_actual`：`t1000_new = t1000_old × L_want / L_actual`；
4. `&t1000 <值>` → `&save`。
5. 判据：段末 `[NAV] SEGn done: 实测/目标rev` 应接近 1.173（1 格）。
6. **方案 B 之后再加一步**：各跑一次 1 格和 3 格，比较两个 `实测/目标` 比值 —— 应该一致（差 <1%）。若仍随段长明显变化，改的是底盘斜率常量 `CHASSIS_ACCEL_RPM_PER_S`/`CHASSIS_DECEL_RPM_PER_S`，不要再拧 `t1000`（§4.13）。

> 换了规划模型后 `t1000` 必须重标一次：含义没变（spd=0.50 走 1000 mm 的毫秒数），但实现变了，旧模型的 1900 会偏短。
> 想直接用理论值就是 `&t1000 2051`（= 规划算出的 1000 mm 所需时间，此时微调系数 `k=1`）；现在 **`navreset`/出厂默认已经是这个值**，标定只是把 `k` 从 1 修到实际（例如现场 2100 → `k=1.024`）。
> 看 `&nav` 打印的 `k` 就够了，不用自己拿 1900 当基准算（§4.23）。

### 6.2 速度

- 导航：`&spd <比例>`（轮速 = 比例 × 250 RPM）。0.5 ≈ 125 RPM ≈ 0.53 m/s；先 `&spd 0.2` 慢速验证再提速。
- 手动：改 `CHASSIS_MANUAL_SPEED_SCALE`（要重编译）。
- 转向：改 `CHASSIS_TURN_MAX_WHEEL_RPM`（要重编译）+ PID 重新整定（§4.7）。

### 6.3 转向 PID

> **先看 §4.14**：转向慢/超时**不要**靠加 `ki` 解决 —— 那是在给"执行器分辨率不够"的环补增益，必然抖。先确认死区（kick）和节拍是对的。

| 现象 | 调整 |
|---|---|
| 慢、收敛不动、输出未饱和 | 提高 `kp` |
| 慢、输出长期 ±1.00（饱和） | 提高转向上限 |
| 过冲大 | 降 `kp` / 加 `kd` |
| 抖动、一顿一顿 | 降 `kd` |
| 末端磨蹭、`err` 卡在 0.05~0.2° 然后超时 | 不是增益问题：查 kick 门槛/节拍（§4.14） |
| 一加 `ki` 就抖 | 正常现象（积分对抗静摩擦的极限环）：把 `ki` 退回去，改 §4.14 那三项 |

## 7. 分层调试顺序（不要跳级）

```
① 机械：麦轮排布判定（无力矩手推对角线）→ 方向文档 §3.3/§3.4
② 单轮：poscal（是否执行 0xFD、脉冲当量、回读符号）+ posref/posd（手转 1 圈量计数）
③ 手动：&M1/&M2 + &U/&L/&R（速度已 1/3）+ &L90/&R90（PID 转，看 [TURN] done）
④ 导航单段：&goto 0 1 → 看 align turn / drive / revs / SEG done / hold peak
⑤ 导航多段：&goto 3 2 → 每段都应有 align turn；段末无 heading drift 报警
⑥ 整条任务：`&goto` 串起来 + 视觉/机械臂配合
```

**每一级都要"看得见"再往上走**：②看计数，③看 RPM 与 `[TURN] done`，④看 `SEG done` 实测/目标与 `hold peak`。
