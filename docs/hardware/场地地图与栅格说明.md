## 1. 为什么从 8×8@300 mm 换成 48×48@50 mm

旧模型（8 格 × 300 mm = 2400 mm）在**场地尺寸上是对的**，但在几何上对不上规则图：

| 场地要素 | 实测 mm | ÷300 | ÷50 |
|---|---|---|---|
| 场地外轮廓 | 2400 | 8 ✓ | **48 ✓** |
| 中央十字通道净宽 | **400** | 1.33 ✗ | **8 ✓** |
| 四块黄色禁区 | **450** | 1.5 ✗ | **9 ✓** |
| 外环带净宽 | **550** | 1.83 ✗ | **11 ✓** |
| 启停区 | 300 | 1 ✓ | 6 ✓ |
| 粗加工/暂存区深 | **150** | 0.5 ✗ | **3 ✓** |
| 车体投影 | 300 | 1 ✓ | 6 ✓ |

**所有尺寸都是 50 的整数倍，只有 300 不是**。300 mm 网格的三个致命问题：

1. 通道 400 mm ÷ 300 = 1.33 格 → "一格就是通道"不成立；
2. 轴线 X=1200 / Y=1200 落在第 3/4 格**边界**上（格心在 150、450、750、1050、1350…）
   → **格心永远对不到轴线**，`&goto x y` 停位天生带 150 mm 偏差；
3. 450/550/150 全都不是 300 的倍数 → 禁区边界跨格，"避障"判定失真。

## 2. 坐标系（★ 两套口径，只有一个转换点）

| | 用途 | 原点 | x | y | 单位 |
|---|---|---|---|---|---|
| **对外 / 规则图** | 地图表、JSON、卷尺实测、命令参数、串口打印 | 场地**左下角**内边沿 | 向右 | **向上** | mm |
| **对内 / 格子** | A*、段、执行器、屏幕 | 格 (0,0) = 场地**左下**那格 | 向右 | 行号**向下**递增 | 格 = 50 mm |

换算（**全工程唯一的 y 翻转点**，在 `Core/Src/grid_nav.c`）：

```c
cx = x_mm / 50                       // x 不翻转
cy = 47 - (y_mm / 50)                // 行号向下，所以翻转
x_mm = cx*50 + 25                    // 格心
y_mm = (47 - cy)*50 + 25
```

**为什么内部要"行号向下"**：执行器里那条经过现场验证的方向链
（`ZDT_Nav_GetBodyVelocity()`：`dy>0 = 前进`、`MAP_FORWARD_PLUS_Y`）是按"y 向下"写的。
让内部行号保持向下递增，这条链**一行都不用改**；y 翻转只在上面两个换算函数里发生。
屏幕绘制再做一次翻转（`y 向上 → 屏幕 y 向下`），见 `Dashboard_MmToPxY()`。

> ⚠ 历史上"地图左右镜像/走斜线"那几次事故的根因就是**两套口径混用**。改地图时请只改
> 第 4 节那张几何表（`Core/Inc/grid_nav.h`），不要另开第二处换算。

## 3. 场地分区（几何 → 格子类型 → 车体膨胀）

几何分区（mm，全部能被 50 整除；`550+450+400+450+550 = 2400` 正好铺满）：

| 分区 | x 范围 | y 范围 | 类型 |
|---|---|---|---|
| 中央十字通道（纵臂） | 1000–1400 | 全高 | `ROAD` |
| 中央十字通道（横臂） | 全宽 | 1000–1400 | `ROAD` |
| 外环带（四条边） | <550 或 ≥1850 | 或 y <550 或 ≥1850 | `RING` |
| **四块黄色禁区 450×450** | 550–1000 / 1400–1850 | 550–1000 / 1400–1850 | **`BLOCKED` 不可通行** |
| 启停区 1（**右下角**） | 2100–2400 | 0–300 | `START`（可通行） |
| 启停区 2（**右上角**） | 2100–2400 | 2100–2400 | `START`（可通行） |
| 原料区**功能区**（上方居中） | 1000–1400 | 1850–2400 | `WORK`（可通行，含停位空间） |
| 粗加工区**功能区**（下方居中） | 1000–1400 | 0–300 | `WORK` |
| 暂存区**功能区**（左侧居中） | 0–300 | 850–1550 | `WORK` |
| 二维码**功能区**（右侧居中） | 2100–2400 | 1000–1400 | `WORK` |
| **原料台实物**（深 150） | 1000–1400 | **2250–2400** | **`PAD` 车体不得接触** |
| **粗加工台实物**（深 150） | 1000–1400 | **0–150** | **`PAD`** |
| **暂存台实物**（宽 150） | **0–150** | 1050–1350 | **`PAD`** |
| **二维码板实物**（宽 50） | **2350–2400** | 1100–1300 | **`PAD`** |

`BLOCKED` 与 `PAD` 之外的一切都**可通行**，这正是规则图"十字 + 外环带"的形状。

> ★ **`WORK` 与 `PAD` 的区别**（2026-09-13 新增，别混）：
> `WORK` 是"功能区"的**语义覆盖层**，包含车可以站的**停位空间**，必须保持可通行；
> `PAD` 是台面/板子**实际占的那块地面**，**车体不得接触**（比赛判罚），所以它和
> `BLOCKED` 一样参与车体膨胀：车心必须离 `PAD` ≥150 mm，即车体最多贴到它的边沿、
> 绝不重叠。因此命名点位 `raw/rough*/temp*/qr` 全部改成了**接近点**（台面前方那条自由
> 车道的中线，前后各留 50 mm），而不是台面中心。

### 3.1 车体膨胀 6×6（关键规则）

车体 300×300 mm = 6 格。**一个格"车能过"的定义是：以它为中心、车体覆盖到的所有格
都不是禁区、且不越出场边**（`GridNav_CellPassable()`）。后果：

- 400 mm 宽的十字通道：膨胀后只剩 **2 格**（格心 1175 / 1225）可走 → 通道仍然连通，
  但车心横向自由度只有 ±25 mm；剩余误差由**执行器的车道吸附**（`GridNav_LaneMm()`）
  把车拉回 1200 / 2125 / 275 三条车道中心线。
- 550 mm 宽的外环带：膨胀后可走格心范围 2000–2250（6 格）✓ 余量充足。
- 场地最外圈（x<150 等）**不可通行**：车心贴边会超出场边。

启停区 300×300 与车体同宽 → 车在里面**零余量**，所以"先前进、再平移"是几何上被逼出来的
（见第 6 节）。

> 两个启停区在**右边缘**（右上 + 右下），**二维码板在右边缘中部、正好被两区夹在中间**

## 5. 命令

| 命令 | 作用 |
|---|---|
| `&map` / `&grid` | 打印整张 48×48 地图（大写 = 车能过，小写 = 地面可走但车过不去，`#` 障碍，`.` 黄区，`@` 小车，`+` 目标） |
| `&waypoints` / `&wp` | 打印命名点位表 |
| `&goto raw` | 按**命名点位**规划（推荐现场用） |
| `&goto 1200 2250` | 按 **mm** 规划（含 ≥48 的数即按 mm 解释） |
| `&goto 24 3` | 按**格**规划（两个数都 <48） |
| `&obs 24 20` / `&free 24 20` | 加/撤**运行期障碍**（随机障碍用；格坐标） |
| `&clear` | 清空运行期障碍（四块黄区禁区仍在） |
| `&pose 24 3` / `&posemm 1200 2250` | 设当前位姿（格 / mm） |
| `&startpose 1` / `&startpose 2` | 设定**启停区**起始位姿 + 车头朝向（1=右下角/朝−x，2=左上角/朝+x）+ 重对航向基准 |
| `&nudge u|d|l|r [mm]` | 朝向自检：沿**地图**方向走一小段，验证摆位与朝向绑定一致 |
| `&leave` | 出场：**前进 300 mm → 平移 125 mm** 到外环带中心线 |
| `&home` | 回场：**平移 125 mm → 后退 300 mm** 回到启停区 |
| `&tarc <ms>` | 90° **圆弧过弯**目标耗时（0 = 关闭，默认）；**时间越短半径越小** `R=2vT/π`，见 §7 末 |
| `&aspd <比例>` | 圆弧车体速度 = `spd` × 比例（默认 1.00） |

## 6. 启停区出场/回场（规则要求"先前进、再平移到大路中央"）
### 6.1 本场排布（2026-09-13 现场确认）

| | 位置 | 区中心 | 车头朝向 | 出场落点 |
|---|---|---|---|---|
| 启停区1 | **右下角** x[2100,2400] / y[0,300] | (2250, 150) | **+y（朝上，朝场地内）** | (2125, **450**) = `exit1` |
| **启停区2** | **右上角** x[2100,2400] / y[2100,2400] | (2250, 2250) | **−y（朝下，朝场地内）** | (2125, **1950**) = `exit2` |

> ★ **本队实际发车区 = 启停区2（右上角）**，也就是固件默认区 `ZDT_START_ZONE_DEFAULT`（`Core/Src/zdt_motor.c` 一行常量，换发车区只改这一行）。
> 开机时位姿与车头绑定先按它假定，屏幕那行显示黄色 `ZONE 2? POSE 2250,2250`；发过 `&startpose 2` 后变绿。
> 用启停区1 时发 `&startpose 1` 覆盖即可。默认区与实际摆放不一致的后果见调试手册 §4.26。

启停区1 的出场序列（车头沿 +y，所以"前进"= 地图 +y）：

| 步 | 动作 | 地图位移 | 落点 |
|---|---|---|---|
| 0 | 摆车 + `&startpose 1`（+ 静止 3 s 等零漂） | — | (2250, 150) |
| 1 | **前进** 300 mm（沿 +y） | y +300 | (2250, 450)，车尾让开 y=300 |
| 2 | **平移** 125 mm（到右边缘环带中线） | x **−125** | **(2125, 450)** = `exit1` |
| 3 | `&goto <目标>` 交给 A* | — | 沿右边缘环带 x=2125 走 |

**为什么必须先前进**：启停区占掉右边缘环带外侧 300 mm，紧贴场边剩下的通道只有
2400−2100 = **250 mm < 车宽 300 mm**，**绕不过去**；只能沿启停区自身轴向先驶出，
车尾离开 y=300 之后才能横移。（右上角那个同理，只是镜像：车头朝 −y 时地图 −x 在车体**右侧** → STRAFE-RIGHT，落点 (2125,1950)。）

**为什么用平移而不是"转 90°→走→转回"**：平移保持车头不动、不引入转角误差；
转两次要 ~2 s（快速档 0.8 s×2）并叠加两次 ±0.5° 对准残差。平移 125 mm 在 `spd=0.5`
下约 0.5 s，落点误差只受横向标定影响。

### 6.2 四向车头朝向（2026-09-13 由"±y 二进制"扩展）

原来的绑定只有"车头朝 ±y"两种（`forward_plus_y`），**表达不了本场"车头沿 ±x"的摆法**。
现在只维护一个"车头在内部坐标系里的单位向量 F"，映射由点积给出：

```
R(车体右侧) = (-F.y, F.x)            ← 内部坐标系里"F 顺时针 90°"
vx(前向) = d · F        vy(车体向右) = d · R
heading  = atan2(-(d · R), d · F)     ← 左转为正
```

四种取值：`0 = 地图 −y(下)`、`1 = 地图 +y(上)`、`2 = 地图 +x(右)`、`3 = 地图 −x(左)`。
`&startpose 1` 设成 3（朝左），`&startpose 2` 设成 2（朝右）。**改摆位只需重设，不用重编译。**

> 用 `&nudge u|d|l|r [mm]` 现场自检：它用**与导航完全相同**的映射沿地图方向走一小段。
> 转向是**相对**的（陀螺只测转了多少），所以"车头朝反了"陀螺和里程都发现不了 ——
> 但第一条指令就会让车朝错方向走（本场启停区紧贴场边，会直接冲出去）。

### 6.3 `&cross`：从一个启停区直走到另一个启停区（2026-09-13 新增）

两个区都在右边缘、中间夹着二维码板，所以整段路就是**沿右边缘车道 x=2125 的一条直线**：

```
1 号区 (2250,150)  --出场 300+平移125-->  (2125,450)
                   ==沿车道直走 1500mm==>  (2125,1950)      ← 这就是"直走"
                   --掉头 180°-->          (2125,1950) 车头翻转
                   --平移125+后退300-->    (2250,2250) = 2 号区
```

- **直走量 = 1500 mm**（两个**出场落点**之差 = |2250−150| − 2×300），**不是 2100**：
  出场已经朝场地内走了 300、进区还要再走 300。⚠ 写错过一次，被 `check_map.py` 的端位自检抓到。
- **必须掉头 180°**：两个区都要求车头朝场地内，方向相反；不掉头的话到对面时车头朝场外，
  下一次 `&leave` 的"前进"直接撞墙。
- 到位后 `ZDT_Script_SetStartZone()` 把**区号 / 位姿 / 车头绑定**一起切过去（绑定必翻），
  并重对零漂 ⇒ 到位后静止约 3 s。
- 离线自检（`check_map.py` 会打印两个方向的端位，必须精确等于目标区中心）：

```
&cross (start zone -> other start zone) end-position check:
  zone 1 -> zone 2 : ends at (2250, 2250) (expected (2250, 2250)) OK
  zone 2 -> zone 1 : ends at (2250, 150) (expected (2250, 150)) OK
```

### A* 的代价模型：按**时间**比较（2026-09-13 改）

现场发现 `temp→rough` 该走外圈（90°+90°）却掉头走中间（180°+90°）。查实原因：
**两条路的曼哈顿长度完全相同（都 34 格）**，而旧代价里 **90° 与 180° 都是 120** →
A* 只能"随手选一条"。

现在代价按现实时间折算（单位仍是"格数当量"，走一格 = `GRID_NAV_MOVE_COST` = 10）：

| 项 | 值（`spd=0.2` 时） | 含义 |
|---|---|---|
| 走一格 | 10 单位 = **235 ms** | 当前 `spd` 下走 50 mm 的规划时间（由执行器算） |
| 直角 90° | 43 单位 = **1000 ms** | `t90` 参数（现场给值 ≈1 s；默认 `NAV_TURN90_DEFAULT_MS`） |
| 掉头 180° | 85 单位 = **2000 ms** | `t180` 参数（现场给值 ≈2 s） |

执行器在**每次规划前**调 `GridNav_SetCostModel()` 按当前 `spd` 折算，所以**速度变了、权重跟着变**
（快走时转向相对更贵 —— 与直觉一致）。离线验证（`tools/check_map.py`）：

```
temp   -> rough   34 cells, 2 legs, 2 turns (90deg x2, 180deg x0), ~11.4s: turn+go R850 | turn+go D850
rough  -> temp    34 cells, 2 legs, 2 turns (90deg x2, 180deg x0), ~11.4s: turn+go U850 | turn+go L850
turn cost model: move=10/cell (235 ms at spd=0.20), 90deg=43 (1000 ms), 180deg=85 (2000 ms)
```

**已知未覆盖**：车**起步前那次对准**（第一条段方向与当前车头不一致时）不在 A* 代价里 ——
A* 不知道车此刻朝哪。所以"路径本身"已经没有 180° 掉头，但**起步对准**仍可能是 180°。
要连这个一起优化，需要把"起始车头"喂给 A*（`GridNav_SetStartHeading()`），属于下一步。

### A* 的转向惩罚 + 小幅横移（strafe jog）+ 走中线

执行器每一段原本都要一次原地对准（快速档约 0.8 s），所以**少拐弯**比少走格重要：
`GRID_NAV_TURN_COST = 120`（单格代价 `GRID_NAV_MOVE_COST = 10`）。加了它之后 `exit1→raw` 从 4 段降到 3 段。

2026-09-13 又加了一层：**短横向段不再转向，直接横移过去**（`ZDT_Nav_SegmentStrafeSign()`）——
段长 ≤ 3 格（150 mm）且相对当前车头是纯横向时，车头不动、只给 `vy`。
理由：这种 1~3 格让位老做法是"转 90° → 走 50 mm → 转回 90°"，两次原地转 ≈1.5~2 s，
还叠加两次 ±0.5° 对准残差；横移一次带走完，且航向全程不变。
**真正改变方向（转角、掉头）或跨度 >3 格的横向段，仍然原地转**（`&leave/&home` 里
那 125 mm 平移也一直是横移）。上面 `h2→h1` 那段就是受益者：4 段路从 4 次转降到 **1 次转**。

**再加一层"走中线"**（2026-09-13）：A* 的每格代价额外加
`GRID_NAV_LANE_COST_PER_CELL(3) × GridNav_LaneDeviationCells()`，也就是"离 275/1200/2125
三条车道中线几格"——外环带膨胀后有 6 格可走，不加这一笔 A* 会挑贴着场边的那格。
效果（离线实测）：`exit1→raw`、`exit2→rough2` 都由 3 段降到 **2 段**（少一次中途让位），
因为路径直接沿中线走到底再拐。执行器另外在起步前做一次 `ZDT_Nav_ComputeLaneSnap()`：
横向离中线 >40 mm 就先横移过去（日志 `[NAV] lane centring: strafe …`）。

**启停区可以照常经过**（2026-09-13 现场更正）：两个启停区就是地面上两块 300×300 的区域，
车可以正常压过去、也可以从里面过路。这里原来有一套"出库后把刚离开的区锁成车体不可接触"
（`GridNav_SetZoneNoTouch()`）的机制，**已整段删除**，原因：

- 锁着的时候 A* 必须绕开区，顶角那一段路会被迫走远路（离线基线也因此分成两套：不锁 734 格 / 锁 699 格，
  而固件当时实际跑的是 699 那套 —— 现场与 `check_map.py` 报告不一致）；
- 圆弧过弯的几何判定里也带着"不可碰锁定区"，区口的转角会被无谓拒掉。

现在**离线基线与固件完全一致：734/2304 格可通行、全连通**（锁区那 699 格那一节已从
`check_map.py` 删掉，改为打印 4 个区相关点位的可通行性）。仍在的约束只有物理那几条：
场边、四块 450×450 黄区、四个工位实物台面（PAD）、以及运行期障碍格。

### 90° 圆弧过弯：为什么"旋转中的车体"不能查膨胀表（2026-09-13 新增）

`grid_nav_walkable` 的 6×6 膨胀判的是"**轴对齐**车体把格心当中心时会不会压到禁区"。
但转角和圆弧过弯时车头在转：300×300 的车体扫过的是半径 **212 mm**（对角线的一半）的外接圆，
比半边长 150 mm 大得多。所以**不能用膨胀表**判圆弧，固件新增了
`GridNav_RotatedBodyFreeMm(x, y, yaw)`：按真实姿态做**分离轴矩形精确判定**，
覆盖 ①场边 ②四块 450×450 黄区 ③四个工位实物台面（PAD）④运行期障碍格（`&obs`）。
用到的矩形表和建图共用（`grid_nav_zone_block_rects` / `grid_nav_pad_rects`），
`tools/analyze_arc.py` 会把它们**反解回来自查**，防止两边漂移。

这条也顺带解释了"圆弧不是想给多大半径就给多大"：

* 外环带中心线离黄区/场边 275 mm，够 212 mm 的外接圆，余量 63 mm；**400 mm 宽的十字通道只有 200 mm，本来就不够** ——
  所以在通道里原地转 90° 时，车体角其实已经压过黄区标线约 37 mm（**值得现场复核**：如果判罚看车体投影，
  通道里的转角要挪到通道口再转）。
* 实测（`python tools/analyze_arc.py`）：标准路线上的直角**几乎都能过圆弧**（几何允许 275~435 mm 的半径），
  例外是**车还在启停区里**那两个转角（离场边只有 150 mm）和贴着黄区走的 `(1225,1150)`。

| 项 | 值 |
|---|---|
| 参数 | `&tarc <ms>`（0 = 关闭，默认）、`&aspd <比例>`（默认 1.00） |
| 半径 | `R = 2·v·T/π`，`v = spd × aspd × 250RPM×4.2616`；固件再按几何逐 5 mm 钳位、下限 50 mm |
| 轮速 | 外轮 = `v × (1 + 300/R)`，上限 250 RPM（超了底盘 Mix 整体缩放：半径不变、车变慢） |
| 收益 | 每个直角 **约 −1.2 s**（省掉原地转的 1 s + 圆弧比两段直线短 0.43R）；标准路线组 **−8%** |
| 闭环 | **收工判据 = 陀螺**（`\|目标航向−当前航向\| ≤ 1°`；时钟只当 +400 ms 超时兜底）；位姿按**实测转角**反算半径记弦；横向绝对位置无外部传感器，靠车道宽度 |
| 不适用 | 掉头 180°、≤3 格横移让位、被几何拒绝的转角（照旧原地转） |

## 8. 已知待办 / 风险

| 项 | 说明 |
|---|---|
| 车道吸附尚未接进执行器 | 现在 A* 给的是"格心路径"，车心可能离车道中线 25~75 mm（通道 400 mm、余量 ±50 mm，可接受）。要更精准就在每段起走前把横向坐标吸到 `GridNav_LaneMm()`。 |
| 精确停位修正 | 目标 mm 与格心可差 ≤25 mm，执行器目前按"格数×50 mm"走，所以停位可能差 25 mm。已在设计里留了"最后一段按目标 mm 修正段长"的位置，未实现。 |
| 平移段里程投影 | **已接（2026-09-13）**：`ZDT_Nav_MeasureDistance()` 本来就是拿**每轮自己的投影分量**当分母，横移时那组分量正是 `[1,-1,-1,1]`，所以它本来就能正确量出横向位移 —— 之前"横移不做段末复核"是多余的顾虑，已去掉；横移段的**补走也改走横移通道（vy）**，不再误用直走通道。注意 `&leave/&home` 的 125 mm 平移走的是**脚本**那条路（定点动作、非 A* 段），那条路仍是时间开环。 |
| 雷达/CAN RAM 余量 | `grid_nav_nodes`(23 KB) + 路径/开放表等约 85 KB 落在 AXI SRAM（IRAM2 320 KB，用 264 KB，余 ~55 KB）。再加 48×48 级别的大数组要留意。 |
| 通道宽度待实测 | 规则图**没有标注**灰色通道宽度，本模型按 400 mm（与黄区 450/外环 550 互锁推出）。如果实测不是 400，只改 `GRID_NAV_CROSS_HALF` 并重跑 `check_map.py`。 |
