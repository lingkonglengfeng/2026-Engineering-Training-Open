## 0. 一句话结论

达妙 DM4310 驱动**不是新写的**——本工程早在 `b95566e` 就有 `dm_motor.c`，并且 2026-09-09 已台架验证过"使能 + 位置控制 + 反馈"。这次做的是：

1. 把它从"控制台点动"提升为**可用于任务的模块**（句柄式 API、无阻塞、周期服务）；
2. 按官方例程与参考工程**修掉 5 个真实 bug**（含一个让 CAN 帧 DLC 全错的致命 bug）；
3. 新建 `arm_task` 把转盘接入 FreeRTOS；
4. 把达妙接进整车停机路径（失去控制即松劲）。

### 2.2 控制帧

| 模式 | CAN ID | 长度 | 载荷 |
|---|---|---|---|
| POS（本车使用） | `ESC+0x100` = **0x101** | 8 B | 小端 float32 位置(rad) + 小端 float32 速度(rad/s) |
| SPD | `ESC+0x200` = 0x201 | 4 B | 小端 float32 速度(rad/s) |
| MIT | `ESC+0x000` = 0x100 | 8 B | pos16 / vel12 / kp12 / kd12 / tor12 位域打包 |
| PSI | `ESC+0x300` = 0x301 | 12 B | 需 CAN FD，**本车经典 CAN 下不可用** |

### 2.3 特殊命令帧

`FF FF FF FF FF FF FF cmd`，8 字节，ID = `ESC + 模式基址`（POS 模式下即 0x101）：

| cmd | 含义 |
|---|---|
| `0xFC` | 使能 |
| `0xFD` | 失能（松劲） |
| `0xFE` | 保存当前位置为零点（**写电机 Flash**） |
| `0xFB` | 清除故障 |

### 2.4 MIT 映射范围

| 量 | 范围 | 位数 |
|---|---|---|
| 位置 | **±12.5 rad** | 16 |
| 速度 | ±30 rad/s | 12 |
| 扭矩 | ±10 N·m | 12 |
| Kp | 0~500 | 12 |
| Kd | 0~5 | 12 |

> PMAX 由 2026-09-14 用户提供的 `达妙电机参数.txt`（DMTool 导出）确认为 **12.5**（VMAX=30、TMAX=10）。⚠ 本文件早期版本曾写 18.5 —— 那是更早一次 DMTool 记录，已修正。**若用上位机改过 PMAX/VMAX/TMAX，`dm_motor.h` 里的 `DM_P_MAX/DM_V_MAX/DM_T_MAX` 必须同步**，否则 MIT 帧会被截断、POS 模式软限位也会失准。

### 2.5 反馈帧（电机 → 主机，8 字节，ID = 0x11）

| 字节 | 内容 |
|---|---|
| `data[0]` | 高 4 位 = 状态/故障码（`1` = 使能），低 4 位 = 电机 ID |
| `data[1..2]` | 位置，**16 位无符号**，中心为 0 |
| `data[3..4]` | 速度，12 位无符号（`data[3]<<4 \| data[4]>>4`） |
| `data[4..5]` | 扭矩，12 位无符号（`(data[4]&0x0F)<<8 \| data[5]`） |
| `data[6]` | MOS 温度 ℃ |
| `data[7]` | 线圈温度 ℃ |

> ⚠ **温度字段**：本车电机疑似老版本固件，用户反馈读不到温度。驱动仍解析 `data[6]/data[7]`，但只有非 0 时才把 `fb.temp_valid` 置 1；`dm status` 会额外打一行说明。**不要基于温度为 0 做任何判断**（0 ℃ 与"不支持"无法区分）。
>
> ⚠ **电流拿不到**：反馈帧里没有电流字段，POS 模式下也没有；只有 PSI 模式（12 B FD 帧）才有电流。所以"读电流防堵转"在经典 CAN + POS 模式下**做不到**。用户 2026-09-14 决定：**本次不做堵转/过温保护**，先把链路调通。

## 3. 本次修掉的 5 个 bug

移植过程中对照官方例程与参考工程逐条核对，发现并修复：

### 3.1 【致命】CAN 帧 DLC 编码全错

旧代码：
```c
tx.DataLength = (len <= 8U) ? dlc_lut[len] : (len == 12U) ? FDCAN_DLC_BYTES_12 : ...;
```
而 HAL 在经典与 FD 两条分支里都执行 `(DataLength & 0xFU) << 16`，所以 `DataLength` 必须是 `FDCAN_DLC_BYTES_n`（= `n << 16`）。

- 旧代码对 **FD 分支**给了正确预移位的常量，对**经典分支**给了裸字节数 —— 两条分支语义正好相反。
- 本车是经典 CAN，于是：`len=8` → DLC 字段 0 → **DLC=0**；`len=4` → DLC 字段 4 → DLC=4（碰巧对）。
- 现象：0x101 位置帧**时好时坏**，`dm pos` 有时"发了没反应"。

现在统一走 `DM_ByteToDlc()`，所有长度都编码正确。

### 3.2 初始化入参被丢弃

旧代码 `DM_Motor_Init` 把 `esc_id/mst_id/mode` 全部 `(void)` 掉，再硬编码 `0x01/0x11/POS`；而 `main.c` 传的是 `0x05/0x00/MIT`，文件头注释又说 FDCAN2 —— **三处说法互相矛盾**。

现在配置真正生效，唯一来源是 `arm_task.c` 里的 `dm_config_t`。

### 3.3 反馈位置被当有符号解码

旧代码 `(int16_t)((uint16_t)data[1] << 8 | data[2])`。达妙规范里 16 位位置是**无符号**、中点为 0（官方例程 `p_int = (rx[1]<<8)|rx[2];` 也是无符号）。

后果：任何原始值 ≥ 32768（约 **+0.001 rad 以上**）都被解成大负数 —— **正半轴位置读数全错**。现在按无符号解码。

### 3.4 每发一帧阻塞打印

旧代码在 `DM_SendFrame` 里对**每一帧**阻塞调用 `HAL_UART_Transmit(&huart4, ...128 字符..., 100)`。UART4 是 9600 baud → 128 字符 ≈ 133 ms > 100 ms 超时：日志被截断，且**每次发帧把调用者阻塞约 100 ms**，任何 1 ms/10 ms 的任务循环都会被拖死。

现在走 `ZDT_Console_Print()`（中断里入队、任务里 flush），并默认只打印错误/状态变化；逐帧打印由 `DM_LOG_ALL_TX` 编译开关控制。

### 3.5 RX 缓冲区栈溢出隐患

旧代码 `uint8_t data[8]`，但 RX FIFO 元素尺寸被设成 16 字节，HAL 按 DLC 实际长度拷贝 → 一旦切到 CAN FD（>8 字节帧）就是栈溢出。现在缓冲区 64 字节并按 DLC 夹紧。

### 3.6 附带修复

| 项 | 说明 |
|---|---|
| 头文件注释 | 旧 `dm_motor.h` 说"接管 FDCAN2 / zdt 在 FDCAN1"，**全反**；已全部改正 |
| `dm zero` | 会写电机 Flash 改零点，旧版在**共用蓝牙控制台**上无任何确认；现在必须 `dm zero confirm` 且电机已失能 |
| 模式切换 | 旧版 `dm speed`/`dm pos` 静默改模式，导致下一次 `dm enable` 发到别的 ID 上；现在模式变化会清使能标志并提示"需重新 enable" |
| 命令认领 | 旧版 `strncmp(command,"dm",2)` 会把 `dmp` 也吃掉；现在要求 `dm` 后紧跟结尾或空格 |
| `dm pos` 无保护 | 旧版默认速度 1.0 rad/s、不检查当前位置与量程；现在强制量程与速度校验、要求已使能 |
| FDCAN1 错误分支 | `DM_Motor_Init` 开了 BUS_OFF/ERROR_* 通知，但 `HAL_FDCAN_ErrorStatusCallback` 只认 FDCAN2 → 达妙总线断了固件看不见；现在加 `DM_OnCanError()`（中断只置标志，任务里按计数变化打印） |
| 线圈温度 | 旧版直接丢掉第 7 字节；现在解析进 `fb.t_coil_c` |

## 4. 不照抄参考工程的地方

1. **反馈分发**：参考工程 B 族 `fdcan1_rx_callback` 写的是 `case 0x11→Motor2, 0x12→Motor3...`，**`Motor1`（真正的转盘电机，`mst_id=0x11`）根本没被路由**，且整体相对声明的 `mst_id` 错位一位。本工程按 MST ID 显式匹配单台电机，不做数组下标映射。
2. **`fdcanx_send_data` 的 FD 位**：参考工程无条件置 `FDFormat = FDCAN_FD_CAN` + `BitRateSwitch = BRS_ON`，在 `CCCR.FDOE=0` 时那两位是 don't-care 才碰巧能跑。本工程显式置经典 CAN。
3. **多电机数组与寄存器状态机**：参考工程的 `motor[10]`、`read_all_motor_data`/`receive_motor_data` 全是**零调用的死代码**。本工程只做单实例句柄 + 按需扩展。
4. **启动写电机参数**：参考工程 `MY_4310_Init()` 会在每次上电 `write_motor_data(id,10,pos_mode)` + `save_motor_data(id,10)` —— **改电机 Flash**。本工程**永不写电机参数**（用户 2026-09-14 明确要求），电机 ID/模式/波特率由 DMTool 一次性配好。
5. **上电自动使能**：参考工程启动序列最后会 `dm_motor_enable()` 并 `pos_ctrl(2*PI, 2)` 让转盘自动回位。本工程**上电不使能、不发控制帧**，转盘保持松劲，必须显式 `dm enable`。
6. **周期发送**：参考工程靠裸机大循环里"每个姿态发一帧"，不做周期重发。本工程默认同样不做，但留了 `DM_PERIODIC_RESEND` 编译开关（见第 7 节）。

## 5. 任务与接线

### 5.1 新增任务

| 任务 | 周期 | 优先级 | 栈 | 职责 |
|---|---:|---:|---:|---|
| `armTask` | **10 ms** | `osPriorityNormal3` | 2048 B | `DM_Motor_Service()`（失去控制即松劲）+ 失联/bus-off 事件打印 |

- `ArmTask_Init()` 在 `MX_FREERTOS_Init()` 里、**调度器启动前**调用（内部要 `HAL_FDCAN_Init/Start`）。
- 失败不致命（底盘仍可跑），但会置 `g_boot_error = 5` 并在控制台打 `[ARM] ERROR`。
- 优先级/栈与 `freertos_task/FreeRTOS任务安排与设计.md` 里 `ActuatorTask` 的定位一致（该文档写 10 ms / Normal3 / 1536 B，这里栈上浮一档，因为 `dm status`/`dm probe` 有 192 B 缓冲 + `snprintf` 浮点格式化开销）。
- **后续升降/前后轴（ZDT35）和抓取舵机（TIM4）应并入这个任务**，而不是另开任务。

### 5.2 安全接线

| 入口 | 行为 |
|---|---|
| 控制台 `dis` / `off` | 底盘四轮失能 **+ 转盘失能**（整车"松劲"语义） |
| `ChassisMotor_EmergencyStop()` | 四轮急停 **+ `ArmTask_EmergencyStop()`**（清目标 + 发失能帧 + 打印） |
| 反馈超时 200 ms | `DM_Motor_Service()` 内自动失能 + 打印 `[DM] link lost`，`armTask` 补打带计数的一条 |
| 电机自报故障码 > 1 | 自动失能 + 打印 `[DM] motor fault code N` |
| FDCAN1 bus-off | `DM_OnCanError()` 计数，`armTask` 按变化打印 `[ARM] FDCAN1 BUS-OFF #n` |

> 急停按钮 PA1 已配 EXTI 但**没有 `HAL_GPIO_EXTI_Callback` 实现**，按了没用 —— 这是**独立的既有问题，本次未动**。

## 6. 控制台命令（UART4 / 蓝牙，9600 8N1）

**同一条 UART4 上有两条入口，规则完全不同**：

| 入口 | 形式 | 何时可靠 | 限制 |
|---|---|---|---|
| **有线控制台** | `dm status`（裸命令 + 回车） | 仅在"本次上电还没发过任何 `&` 命令"时 | 一旦发过 `&` 命令，蓝牙分词器会把后面两个行结束符吃掉（`bt_button_suppress_line_end = 2`），那一行就不会被派发 —— 表现是"回车之后没反应，再敲一行才把上一行执行掉" |
| **蓝牙 App** | `&dm status`（带 `&` 前缀） | 任何时刻 | 载荷 **≤ 15 字符**（`bt_button_event_t.text[]` 只有 16 字节） |

原因：每个字节先过 `BT_Button_ProcessByte()`，它只认 `&` 开头的 token；非 `&` 字节返回 0
落给控制台。所以裸命令能用，但它的**行结束符**会被 `&` 之后的分词器状态吞掉。

**`&dm` 已登记进 4 个地方**（2026-09-14）：`bt_button.c` 的
`BT_Button_IsCustomPrefix()`（token 存活）、`BT_Button_IsCustomToken()`（flush 派发）、
`BT_Button_IsArgCommand()`（空格保留），以及 `zdt_motor.c` 的 `BT_BUTTON_CUSTOM` 路由。
缺任一个都会出现"命令看起来发出去了、什么都不回"这种最难查的现象。

机械校验：`tools/check_uart_command_paths.py`（路径 + 长度）、
`tools/check_bt_whitelist.py`（两白名单，已扩展为认识达妙的动词式解析器）。

```text
裸命令（有线优先用）          蓝牙形式                     说明
dm help                     &dm help                   命令列表
dm probe                    &dm probe                  ★ 先跑这个：打印实际位时序 + 监听 300 ms + 触发反馈
dm loopback                 &dm loopback               ★ 内部回环：只验芯片侧，不碰收发器/接线/对端
dm loopback ext             &dm loopback ext           外部回环：TX 经收发器出去再收回来
dm brscan                   &dm brscan                 ★ 自动扫 125K/250K/500K/1M，报哪个通
```

### 6.1 推荐台架调试流程

达妙代码**从没在硬件上跑过**（用户 2026-09-14 反馈"只是理论上完成"），所以从只读诊断开始：

```text
dm help        → 确认命令在
dm status      → 看 state / fb 计数；此刻应该 fb=0 或小、en=0
dm probe       → 关键一步。它会向 0x101 发一帧"当前位置 @ 0 速度"来触发反馈
                 （**不看电机是否使能** —— 否则链路不通时连触发帧都发不出去，
                 这个命令就没用了），然后监听 300 ms。三种结果：
                 (a) frames=0            → 接线/收发器/电机 24V/终端电阻/波特率
                 (b) frames>0, matched=0 → ID 配错，用 dm setid 试
                 (c) matched>0           → 链路通，继续
dm enable      → 看 [DM] enable sent to 0x101，且 fb 计数继续涨
dm pos 0 0.5   → 小角度低速，先确认方向与量程
dm pos 0.2 0.5 → 再走一点
dm disable     → 松劲，用手转一下确认真的松了
```

**注意**：`dm pos` 要求电机已使能、位置在 ±12.5 rad 内、速度在 (0, 30] rad/s。
`dm enable` 之后如果 200 ms 内没有任何反馈，驱动会**自动失能并打印 link lost** ——
这是设计行为（失去控制即松劲），不是 bug；此时先解决链路再谈运动。

### 6.2 第二次台架实测：线接上之后（2026-09-14）

第一次 `probe` 的 `bit0 + bus-off` 已确诊为**信号线根本没接**（用户确认）。接上之后的输出：

```text
[DM] bus: NBTP=0x02030E03 brp=4 seg1=4 seg2=15 -> 1000000 bit/s
[DM] probe done: frames=0 matched=1 other_id=0 txfail=0
```

| 现象 | 含义 |
|---|---|
| `LEC=0`、`busoff=0`、`passive=0` | **总线层已干净**（对比第一次的 `LEC=5`+`busoff=1`） |
| **`matched=1`** | **有一帧反馈 ID 正好是 `mst_id=0x11` 且被完整解析 → 电机回话了，链路通** |

**两个据此修掉的驱动问题：**

1. **`probe` 的假失败**：判定改用**累计计数的增量**（`rx_count`/`rx_other_count`），
   不再只看探测循环自己的 `seen`；命中中断路径时明确打印
   "consumed by the RX interrupt - the link IS alive"。回环测试早先已修同一类问题。
2. **`&dm enable` 之后立刻 `link lost`** —— 这是**真实行为**，不是故障：达妙电机收到一条

   放宽到 **500 ms**（要给 `dm probe` 的 300 ms 阻塞留余量）。
   诊断命令（probe/loopback/brscan）期间会抑制重发并在结束时重置判据起点。

**顺带印证**：`can_br=4` 之后两端确实都是 1 Mbps，`LEC` 归 0 与此一致。

### 6.4 首次上电实测（未接信号线，2026-09-14）

判读：

| 现象 | 含义 |
|---|---|
| `-> 1000000 bit/s` | 内核时钟与位时序**没问题**，不用怀疑配置 |
| `txfail=0` | 帧成功进了 TX FIFO。**这同时印证本次修的 DLC 编码是对的**（旧版这里会是 DLC=0 的废帧，根本进不去） |
| `frames=0` | 线上一个字节都没有 → **排除 ID 配错**（ID 错会看到帧、只是 `matched=0`） |
| `flags` 三位同时置起 | BUS_OFF + ERROR_PASSIVE + ERROR_WARNING：错误计数从 96 涨到总线关闭 |
| `LEC=5` | **bit0 错误**：驱动的位与回读的位相反 → 物理层或对端波特率 |

`&dm enable` 随后打印 `link lost` 是**必然的次生现象**：bus-off 后控制器被关掉，
收不到反馈就自动松劲（这正是"失去控制即松劲"的保护）。

**用回环把问题一刀切开**（不需要第二个节点）：

```text
&dm loopback        # 内部回环：TX 在芯片内部接回 RX，收发器和引脚都不参与
&dm loopback ext    # 外部回环：TX 真的驱动引脚、经收发器再收回来
```

| 内部 | 外部 | 结论 |
|---|---|---|
| PASS | PASS | 本板收发器、引脚复用、控制器全部正常 → 问题在**对端**：CANH/CANL 极性、共地、终端电阻 |
| PASS | FAIL | 控制器正常，**收发器或其供电/引脚复用**有问题 |
| FAIL | — | **不要查线**：问题在芯片侧（FDCAN 配置或 PLL2Q 内核时钟） |

**本次症状（`LEC=5` bit0 + bus-off + 0 帧）的收敛判断**：电机波特率已确认是 1 Mbps，
本端位时序实测也是 1 Mbps（`NBTP=0x02030E03 -> 1000000 bit/s`），**两端速率一致**。
bit0 错误在"两端速率一致"时最常见的成因是 **CANH / CANL 接反**（发什么读回什么的反）
或**共地缺失**。所以：

1. 先 `&dm probe` —— 若第一行不是 1000000 bit/s 才回去查配置（本车是 1000000，跳过）；
2. 再 `&dm loopback` → `&dm loopback ext`，用上表定位是本板还是对端；
3. **若内/外部回环都 PASS** → 直接**断电对调 CANH/CANL** 重试。这是当前最可能的一步。

> 实现细节：回环自检复用 `DM_BusConfigure()`（与 `DM_Motor_Init` 同一份时序/过滤器/
> 通知落位），测完自动切回正常模式并清零 bus-off 计数，避免旧计数误导现场。
> 另：内部回环时 RX 中断也会触发，会把测试帧抢先消费掉 —— 所以判定同时复查
> `rx_count`/`rx_other_count`，否则会把"通过"误报成"失败"。

### 6.5 UART4 丢字节 / "卡住要 reset"（2026-09-14，既有问题，本次顺带修）

用户报告：`&dm txlog 1` 被当成 `txlog off`，输出里 `off` 和 `1` **分成两行**；
并说"之前调底盘时也这样，先读取、使能小车、再 `leave`，然后发就收不到消息，
像卡住一样，要 reset 才可以"。**这不是达妙的问题，是 UART4 输入路径的既有缺陷。**

根因在 `ZDT_UART_ProcessByte()` 的**逐字符同步回显**：

```c
zdt_uart_command[...] = (char)byte;
(void)HAL_UART_Transmit(&huart4, &byte, 1U, 100U);   /* 9600 baud ≈ 1.04 ms/字符 */
```

UART4 是 9600 baud，**每收一个字符就阻塞任务 ~1 ms 去回显**。蓝牙 App 一次推一整行时：
15 字符的命令 = 15 ms 任务阻塞，期间 RX 环形缓冲（128 字节）被 ISR 填满就**静默丢字节**
→ 命令被腰斩、尾部字符变成下一条命令（`txlog` + `1` 分行就是它），
严重时命令永远拼不完整，现场就像"卡死"。人手工敲键盘（字符间隔 >> 1 ms）不会触发，
所以这个缺陷一直没暴露。

**三处修改：**

| 改动 | 原因 |
|---|---|
| 字符回显**默认关闭**，运行期开关 `uecho 0\|1` | 去掉 1 ms/字符的任务阻塞。App 自己会显示发出的内容；手工敲键盘时才需要 `uecho 1`。**与 `&echo`（应用层链路自检）无关**，所以没有复用 `echo` 这个名字 |
| RX 丢字节**计数**（环形缓冲满 + 硬件 ORE/FE/NE/PE 都算） | 原来丢字节没有任何痕迹，"命令缺字/卡住"完全无法归因。现在 `status` 打印 `uart rx: dropped=N`，非 0 时额外报警 |
| `dm txlog` 参数解析失败时打印**收到的原文**并提示可能是 UART 丢字节 | 直接指向根因，而不是干巴巴一句 usage |

> 用 `tools/check_arg_parsing.py` 自检时**抓到了我自己的一处错误**：`uecho` 的参数我一开始
> 写成 `command[6]`（固定偏移），而蓝牙 token 内部保留空格，第 5 位就是那个空格 →
> 偏移错位。已改为 `ZDT_SkipSpaces(command + 5)`。这个脚本存在的意义正在于此。

**现场绕过办法**（在烧新固件之前）：命令之间**停 0.5 秒**再发，别连发；
或改用有线 USB-TTL（PC10/PC11 @9600）对比——有线通、蓝牙不通即确认是这条路径。



| 项 | 状态 |
|---|---|
| **周期重发** | 默认**关**（对齐参考工程行为）。若台上出现"发一次之后过一会儿关节自己松了"，把 `dm_motor.h` 的 `DM_PERIODIC_RESEND` 改成 1 重新编译（10 ms 重发当前目标） |
| **电机 TIMEOUT 寄存器** | 未确认。参考工程从没读过它。这是"要不要周期重发"的唯一依据 |
| **堵转 / 过温保护** | **本次不做**（用户决定）。原因：反馈帧无电流字段，POS 模式也拿不到；温度为 0 说明老固件可能不支持。将来要做的话，可行路径是 `力矩 = KT × 电流` 反推，KT 要从电机寄存器 `RID_KT_VALUE`(1) 读 —— 但参考工程从没读过任何寄存器，属新增功能 |
| **零点标定** | 转盘的"0 度"就是电机保存的零点，靠 `dm zero confirm` 手动标一次。**没有自动回零**（参考工程也没有：`save_pos_zero` 是注释掉的） |
| **转盘行程** | 电机物理量程 **±12.5 rad**（约 ±716°，按 PMAX=12.5 且 Gr=10）。软限位就是它，不分方向 |
| **舵机 / 升降轴** | `servo.c` 仍零调用者、TIM4 仍是 CubeMX 占位值（PSC=0/ARR=65535）；机械臂升降/前后 2 台 ZDT35 无代码。**本次未动** |
| **`freertos_task/FreeRTOS任务安排与设计.md` 的 10 任务架构** | 仍是设计提案。现状：`zdtMotorTask`(1 ms) + `defaultTask`(50 ms) + `armTask`(10 ms) |
| **构建配置落 `.ioc`** | `DM_Motor_Init` 仍承担"修 CubeMX 配置"的职责（`.ioc` 生成的 FDCAN1 是 `TxFifoQueueElmtsNbr=0` + `RxFifo0ElmtSize=8B`，**发不出帧**）。建议后续把这几项写进 `.ioc`，否则每次 CubeMX 重新生成都要靠这个函数兜住 |

### 6.6 TX FIFO 卡死与日志雪崩（2026-09-14，两个我自己造成的问题）

现场输出（每帧一次、持续不断）：

```text
[DM] TX ERROR id=0x101 HAL=1 err=0x08000200
```

`0x08000200` 的位含义（**对着 `stm32h7xx_hal_fdcan.h` 查，别凭印象**）：

| 位 | 宏 | 含义 |
|---|---|---|
| `0x00000200` | `HAL_FDCAN_ERROR_FIFO_FULL` | **写不进 TX FIFO** |
| `0x08000000` | `HAL_FDCAN_ERROR_LOG_OVERFLOW` | 错误日志溢出 → 错误累积极快 |
| `0x00000001` | `HAL_FDCAN_ERROR_TIMEOUT` | 等空位超时 |

> HAL 里**没有** `HAL_FDCAN_ERROR_ACK` 这个宏 —— 我第一版代码凭印象写了它，
> 编译直接报 `identifier undefined`。教训：错误位一律查头文件。

**根因链**（两个问题叠在一起）：

```text
电机不应答（无 ACK，错误快速累积 → ERRLOG_OVERFLOW）
   ↓
AutoRetransmission = ENABLE → 硬件无限重传同一帧
   ↓
TX FIFO（4 元素）被永久占满 → FIFO_FULL，之后每帧都写入失败
   ↓
TX 错误逐帧打印 × 100 Hz 重发 → 9600 baud 串口被打印占满 → 任务阻塞
   ↓
现场："一直刷这个，什么指令都没反应"
```

**两个都是我引入的：**

| 问题 | 修法 |
|---|---|
| `AutoRetransmission = ENABLE`：对端不应答时无限重传会锁死 TX FIFO，**连失能帧都发不出去** —— 电机带着力矩却无法让它松，属于安全问题（CubeMX 占位值本来就是 DISABLE） | 改回 **DISABLE**：宁可丢一帧，也不锁死发送通道 |
| TX 错误**逐帧打印**无节制，把串口和任务占满 | **限流**：只打第 1 条和每第 50 条（≈0.5 s），恢复后打一条 `TX recovered`；并按错误位给可执行提示 |
| 卡死后没有任何出路 | 新增 **`dm recover`**：重建 FDCAN1，冲掉 TX FIFO / bus-off / 错误计数。**"发不出去"时现场第一件事** |
| 状态里看不出"当前发不出去" | `dm status` 新增告警行 `*** TX BLOCKED: N consecutive send failures` |

> ⚠ `dm recover` **不能**解决"电机不应答" —— 它只恢复**本端**发送通道。
> 若 `dm probe` 仍然 `frames=0` 且 `LEC!=0`，那就是物理层/对端问题：
> 查电机 24V 供电（`UV_Value=15V`，12V 不工作）、电机是否进了保护
> （`OC_Value=0.8A` 过流 / `OT_Value=100℃` 过温，保护后可能停止应答）、接线。

### 6.7 bus-off 不会自愈：`FIFO_FULL` 刷屏的真正原因（2026-09-14）

现场输出：`[ARM] FDCAN1 BUS-OFF #1` 紧跟 `[DM] TX FAILED x1..x1100 err=0x08000200 FIFO_FULL`，
每 50 条打印一次，控制台基本刷哑。

**关键点：`FIFO_FULL` 不一定是"FIFO 真的满了"。**

`HAL_FDCAN_AddMessageToTxFifoQ()` 只检查 `TXFQS.TFQF`（见
`stm32h7xx_hal_fdcan.c:2727`），而**控制器进入 bus-off 后 TX 被禁止**：
帧即使被排进去也发不出去，`TFQF` 就一直置位，于是**每一帧都报 FIFO_FULL**。
看起来像 FIFO 满，其实是**控制器停了**。

**而 FDCAN 不会自己退出 bus-off**，HAL 也**没有**提供"退出 bus-off"的 API
（只有 `HAL_FDCAN_Start/Stop`）。按 ISO 11898-1，控制器要等 RX 上出现 128 次连续
11 个隐性位才自行恢复；**总线上没有第二个节点时这个过程可能永远不完成**。
所以它就一直躺在 bus-off 里，100 Hz 重发持续失败。

**修法：**

| 改动 | 说明 |
|---|---|
| `DM_Motor_Service()` 最前面处理 bus-off | 中断里只置 `bus_off_latched`（不打印、不阻塞），任务里做实际恢复 |
| bus-off 期间**跳过所有发送** | 直接止血：不再往残废的 TX 里塞帧、不再刷屏 |
| **自动恢复** `DM_BusOffRecover()` | 置 `CCCR.INIT`（`HAL_FDCAN_Stop`）→ 清 `TXBCR` 清空发送请求 → 清 `CCCR.INIT`（`HAL_FDCAN_Start`）→ 等最多 50 ms 确认 `PSR.BO` 归零 |
| 恢复后电机回到**未使能** | 不带着力矩凭空恢复，必须重新 `dm enable`（安全侧） |
| `dm status` 增加 bus-off 计数行 | `bus-off events=N auto-recovered=M now_busoff=0/1` |
| TX 失败提示按 `now_busoff` 分流 | bus-off 时**明确说"这不是 FIFO 满，是控制器停了"**，避免误判 |

编译期开关 `DM_BUSOFF_AUTO_RECOVER`（默认 1）；置 0 则只告警、要求手动 `dm recover`。

> ⚠ 到这里，"什么指令都没反应"的三层原因才全部落清：
> ① UART 逐字符回显阻塞（6.5）→ 命令缺字；
> ② TX 错误逐帧打印 + 自动重传锁 FIFO（6.6）→ 刷屏；
> ③ **bus-off 不自愈**（本节）→ 永久失败。
> 前两条是代码问题（已修），第三条是"缺功能"（已补自动恢复），
> 而**触发 bus-off 的原始原因仍是总线上没有 ACK** —— 这一点必须靠硬件排查。

| **电机 TIMEOUT 寄存器** | 实测 **0**（超时保护关闭）→ 重发不是为了防电机松劲，而是为了感知链路 |
| **堵转 / 过温保护** | **本次不做**（用户决定）。反馈帧无电流字段、POS 模式也拿不到；`KT_Value=0` 未写入 → "力矩/KT 反推电流"也不通。电机自带 `OT_Value=100℃` / `OC_Value=0.8A` 硬件保护 |
| **零点标定** | 转盘"0 度"是电机保存的零点，靠 `dm zero confirm`（写电机 flash）或运行期 `dm zerohere`（RAM 软零点）。**没有自动回零** |
| **转盘行程** | 电机物理量程 **±12.5 rad**（PMAX=12.5，Gr=10）。软限位就是它，不分方向 |
| **舵机 / 升降轴** | `servo.c` 仍零调用者、TIM4 仍是 CubeMX 占位值；机械臂升降/前后 2 台 ZDT35 无代码。**本次未动** |
| **10 任务架构** | `freertos_task/FreeRTOS任务安排与设计.md` 仍是设计提案。现状：`zdtMotorTask`(1 ms) + `defaultTask`(50 ms) + `armTask`(10 ms) |
| **构建配置落 `.ioc`** | `DM_Motor_Init` 仍承担"修 CubeMX 配置"的职责（`.ioc` 生成的 FDCAN1 是 `TxFifoQueueElmtsNbr=0`，**发不出帧**）。建议后续写进 `.ioc` |
| **UART4 9600 baud** | 是输入丢字节的结构性约束（见 6.5）。提高波特率（需同步改 JDY-23）是根治方案，但会牵动底盘控制台，未在本次做 |
