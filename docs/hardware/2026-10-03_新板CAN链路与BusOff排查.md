## 1. 已确认的软件/通信现象

`BusOff=1 warning=1 passive=1 TEC=248 REC=0 RX=0`：FDCAN2 已退出正常通信，没有收到 CAN 帧；`0x08000000` 在本工程 HAL 中对应仲裁阶段协议错误，单凭它不能区分 ACK、位或其他具体错误。

`CAN=listening` 来自初始化时保存的标志，不是当前总线健康测量。`TX version query`/`verall ... sent` 也不能证明发送及回包成功。

`&EN` 当前仅以 CAN 入队成功设置软件使能；出区脚本以时间推进，未验证轮端实际运动就累加计划位移。车不动而打印 script done 是已确认的程序行为缺口。本轮先补诊断以辨认总线故障，尚未重写使能确认和动作验收。

## 3. 与故障相关的图面缺口

### A. U12 输出缺稳定电容

AMS1117 图中的电容接在 5V 输入侧；3.3V 输出到两颗 CAN 芯片，未画输出稳定电容。用户确认是裸芯片，不能把模块内部电容当作已存在。

如果实物也按此图没有输出电容，应按所购芯片厂家手册补输出稳定电容。原厂 AMS1117 手册明确把输出电容用于环路补偿，给出 22 µF 固体钽电容的稳定性参考；不能只补一个100 nF便认为满足稳压器要求。电容类型、ESR、容量、耐压和摆放应核对实际芯片厂家，不把同名替代品视为完全相同。[原厂AMS1117资料的镜像](https://www.datasheets.com/advanced-monolithic-systems/ams1117/datasheet.pdf)

先测电源板 U1-3 相对 U1-2 的电压，而不是只测主控板3.3V。两个板上同名3.3V标签不能证明它们通过26P排线传电；此图26P没有专用3.3V电源脚，电源板CAN芯片由本地U12供电。万用表读3.3V只能检查直流值，不能排除振荡和瞬态跌落；有示波器时需在发送窗口看纹波。

### B. U1/U4 缺近端去耦

图面未画两颗SN65HVD230的电源去耦。TI建议每颗VCC与GND之间就近配置100 nF陶瓷电容。实物如未安装，应各自补齐，不能只用远处的一个大电容代替。[TI数据手册第12节](https://www.ti.com/lit/ds/symlink/sn65hvd230.pdf)

接法：每颗收发器的3脚VCC ↔ 100 nF ↔ 2脚GND，走线尽可能短。稳压输出电容接3.3V_OUT与GND；有极性电容正端接3.3V，负端接GND，断电施工。

### C. 26P排线是当前必须实测的环节

两张图U6的5脚均为ZDT_TX、7脚均为ZDT_RX，偶数脚为GND。断开全部电源，连同实际线缆测PB13到电源板U1-1、U1-4到PB12、公共地；同时确认信号未被错误压接/翻转接地。不要只看排线红边判断针序。

### D. 终端数量需要核验，RS连接本身有依据

R2=120Ω跨步进CANH/CANL。所有连接的电机和上部小板终端都算入同一条总线，常规只在总线两端各保留120Ω。断电且整条总线保持连接后测CANH/L：理想两只120Ω并联约60Ω；120Ω、40Ω或更低需结合现有终端和其他并联路径解释，不能直接盲加。[TI终端说明](https://www.ti.com/tool/TIDA-01238)

R1/R3 的 RS 经10k接地是SN65HVD230支持的斜率控制接法，不能仅凭这点认定故障，也不把短接电阻作为第一步。实际RS若被拉成高电平则会进入待机，需核对焊接与电平。[TI数据手册](https://www.ti.com/lit/ds/symlink/sn65hvd230.pdf)

## 4. 建议的实物排查顺序

1. 测电源板U1-3到U1-2的实际供电；核实U12输出电容、U1/U4去耦是否真的缺失，按正确手册补齐图纸和实物。
2. 断电测26P的5、7脚完整路径和公共地，核对PCB封装/排线插合面；再测总线终端等效电阻。
3. 确认驱动器实际CAN模式与500 kbit/s配置。电机有24V只能证明电机供电存在，不能证明CAN模式、收发器供电和信号链正常。
4. 若仍不通，在保留正确终端的条件下，减少为主控+电源板+一台已知地址电机。正常工作的CAN接收节点通常不因应用地址不同而不进行物理ACK；不能仅靠改地址解释Bus-Off，也不能在没有LEC时把根因认定为缺ACK。
5. 如有示波器，在复位后第一次查询期间沿PB13→U1-1→U1-7/6→U1-4→PB12逐级观察。进入Bus-Off以后不再看到发送波形，不能单凭此时静态波形判定TX断线。

| 波形观察 | 优先检查 |
| --- | --- |
| PB13有发送变化，U1-1没有 | 主控排座、26P排线、PCB线/焊点 |
| U1-1有变化，CANH/L没有对应差分变化 | U1供电、RS状态、芯片方向/焊接/损坏、总线短路 |
| 总线有变化，U1-4/PB12路径不对应 | 接收器、RX连线和焊点 |
| 信号链均有波形，仍持续错误 | 实际位时序、驱动器CAN模式、终端/线束拓扑与波形质量 |

验证成功要看到BusOff=0且真正收到版本/位置回应。修复物理条件后再复位主控；当前底盘没有完整Bus-Off恢复流程。

## 5. 本轮诊断代码改动与验证

- `Core/Inc/zdt_motor.h`：追加volatile错误观测计数及最近有效LEC。
- `Core/Src/zdt_motor.c`：status追加LEC及名称、最近捕获错误、时钟/CCU分频、NBTP位时序及计算波特率。这个波特率来自寄存器和HAL时钟计算，不是示波器测量。
- 在正确的`HAL_FDCAN_ErrorCallback()`中捕获协议错误；本工程HAL的`ErrorStatusCallback()`处理状态改变，不能依靠它捕获PEA/PED。PSR读取会影响LEC，因此在ISR先锁存有效错误，防止周期轮询后只剩NO_CHANGE。
- 编译时发现已有“未知蓝牙命令”64字节日志可能截断，缓冲扩大到80字节，增加16字节局部栈预算。
- 用Arm GNU Toolchain 14.2对zdt_motor.c进行Cortex-M7对象编译，`-Wall -Wextra -Werror`通过；修改文件`git diff --check`通过。未完成Keil整工程链接、烧录、实车回归；这些改动不会自动修好物理总线。

重新编译并烧录该版本后，status应增加类似以下格式，数值仅为格式示例：

```text
[ZDT] protocol: LEC=7(no-change) last=3(ACK) errors=...
[ZDT] timing: kernel=80000000Hz div=1 NBTP=... brp=8 seg1=15 seg2=4 calculated_rate=500000bit/s
```

`last=3`表示曾捕获ACK错误；`last=4/5`表示位错误；`last=1/2/6`表示填充、格式、CRC错误。LEC=7并不表示当前总线正常。上述例子不代表故障实物已经测得ACK错误。
