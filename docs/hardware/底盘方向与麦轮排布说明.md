# 底盘车辆方向与麦轮排布说明

> **2026-10-04当前为调头180°试验版。** 用户实测第一版表下FWD仍倒退，要求按相反方向试验；`CHASSIS_FRONT_REVERSED_TRIAL=1`，相对第一版前后/左右平移同时翻转，原地转向与IMU角度符号不变。当前逻辑轮位地址 FL=4、FR=2、RL=3、RR=1；工位继续按“认定车头左侧是机械臂”设置，扫码朝东。认定的车头朝场内摆放，具体效果待实车验证。历史及本次试验说明见[方向记录](2026-10-04_车头翻转与摆位说明.md)。

> 本文件描述**本车固件实际实现**的车体方向、麦轮排布、符号链与导航行进方式，并记录 2026-09-12 连续多轮实测的结论与修复。
> 所有结论都标注了代码位置或实测数据来源；凡属"现场待定"的项都明确标出，不替现场下结论。

## 0. 结论速查

| 项目 | 结论 |
|---|---|
| 车体坐标 | `vx>0` 前进、`vy>0` **车体右侧**、`omega>0` **俯视逆时针（左转）** |
| 轮位与电机地址 | FL=4、FR=2、RL=3、RR=1（调头180°试验；首版1/3/2/4） |
| 航向正方向 | 内部 `heading_deg` **左转为正**（与 `omega>0` 同向） |
| 麦轮排布 | 标准 **X 型**：对角线同型号（FL≡RR、FR≡RL），两条对角线互为镜像（2026-09-12 推车实测确认，§3.4） |
| 直线段行进方式 | **原地对准方向 → 直走**（不横移）；距离 → 时间 只用两个参数换算（§7.4） |
| 里程回读单位 | `0x36` 位置 = **65536 计数/圈**（与往届工程独立互证，§8/§12） |
| 位置模式(0xFD) | 本车驱动器不稳定，**默认不用**（§0.1-20/21），保留 `posmode 1` 供对比 |
| 姿态零漂 | 上电**静止约 3 s** 自动标定（朝向基准 + 角速度零偏，打印 `[IMU] zero-drift ready`；屏幕 `IMU ZERO CAL x.xs` → `IMU ZERO DONE`）；标定完成前转向被拒（§16.3） |
| 转向到位判据 | **两档**：精确档（手动 `&L90`）0.01°/200 ms + 0.05° 稳定带；快速档（导航对准）0.15°/60 ms + **0.5°/200 ms**，日志标 `FAST`（§16.1/§16.6） |

## 3. 麦轮排布（物理几何与判定）

### 3.1 麦轮的两个方向必须分开看

每个麦轮有两种方向：

1. **滚动的方向**（轮体绕轮轴转，靠地面摩擦传递）；对轮体受力分析时，麦轮能施加给地面的力**只沿辊子轴线方向**；
2. **辊子被动空转的方向**（辊子绕自身轴转）。车体若沿这个方向移动，轮子可以被"拖着走"而**轮体不转**。

这条区别是后文所有判定（推车测试、45° 斜走、横移为什么怕单轮偏差）的基础。

### 3.2 四轮排布的唯一正确形式：对角线同型号

以 `ChassisMotor_Mix()` 的反解

```
FL = vx + vy - omega
FR = vx - vy + omega
RL = vx - vy - omega
RR = vx + vy + omega
```

配合"力只沿辊子轴线"这一约束可以反推出：要使四轮同时满足纯滚动、且横移/自转都能实现，滚子朝向必须满足

- **对角线上的两个轮子型号相同**：FL ≡ RR，FR ≡ RL；
- 两条对角线互为镜像。

这就是标准 **X 型**排布。两类"装错"的表现完全不同：

| 情况 | 实物特征 | 现场症状 |
|---|---|---|
| 情况 1：左右同型号（FL≡FR、RL≡RR） | 辊子朝向按左右分 | 横移时四轮推力**两两抵消**，车几乎不动或原地挣扎 |
| 情况 2：镜像底盘（两条对角线整体翻转） | 对角线配对正确但手性相反 | 横移**方向反**，原地自转力臂偏弱（∝1/(L−W)） |

### 3.3 固件所要求的具体辊子朝向

以车体坐标（`x` 前、`y` 右）记，标准 X 型要求：

| 轮位 | 辊子轴线方向 `â` | 沿 `â` 方向滚动 | 被动空转方向（推车时轮体不转的方向） |
|---|---|---|---|
| FL | (1, +1)/√2（前右） | 有推力 | (1, −1)/√2（沿 FL–RR 连线） |
| RR | (1, +1)/√2（前右） | 有推力 | (1, −1)/√2（沿 FL–RR 连线） |
| FR | (1, −1)/√2（前左） | 有推力 | (1, +1)/√2（沿 FR–RL 连线） |
| RL | (1, −1)/√2（前左） | 有推力 | (1, +1)/√2（沿 FR–RL 连线） |

俯视示意（`车头` 在上方时，FL–RR 是"＼"、FR–RL 是"／"）：

```
        车头
   FL ●────────● FR          辊子轴线：
      │＼    ／│              FL、RR 沿 "／" 对角线（前右方向）
      │  ＼／  │              FR、RL 沿 "＼" 对角线（前左方向）
      │  ／＼  │
      │／    ＼│              被动空转方向与辊子轴线垂直，
   RL ●────────● RR             即 FL/RR 沿 "＼"（FL–RR 连线）
        车尾
```

**"沿 FL–RR 对角线推车"的含义**：推行方向与"FL 与 RR 两个轮心的连线"平行（即朝车体左前 45° 推，或朝右后 45° 拉），不是"用手去推 FL 那个轮"。此时 FL、RR 的辊子正好沿各自被动方向 → **轮体不转**；而 FR、RL 的辊子方向与推行方向垂直 → 只能靠轮体滚动，**会被带着转**。

### 3.4 实物实测记录

2026-09-12 现场测试（断电/未使能，平整地面，匀速推行 20~30 cm）：

- 沿 **FL–RR 对角线**推：**FL、RR 不转**，FR、RL 被带动 → 与 §3.3 表完全一致；
- 结论：本车为**标准 X 型**（情况 1、情况 2 均已排除），`CHASSIS_WHEEL_SIGN_*` 的左右分组与固件假设一致；
- 待补：换另一条对角线（朝车体右前 45°）推一次，应看到 FR、RL 不转、FL/RR 被带动（两条对角线表现互换）。
- 提示：若两个方向推都"四轮全不转"，那不是排布问题，是推太快打滑或地面太滑。

**与后续现象的关系**：`&goto` 早期出现"向左下 45° 再向右上"斜走，正是因为当时只有一对角线在驱动（位置模式的"缓存+广播触发"路径失效，§0.1-17/19）——"对角线驱动 → 45° 斜移"与"沿对角线推 → 该对角线不转"是同一个几何事实的两面（§11.5）。

## 4. 从速度指令到四轮：动作表

归一化 (±1) 速度指令经 `ChassisMotor_Mix()` 得到四轮值，再乘符号表得到电机命令
（`电机命令 = 轮值 × CHASSIS_WHEEL_SIGN_i`，左列为 −1、右列为 +1）：

| 动作 | vx | vy | omega | FL | FR | RL | RR |
|---|---|---|---|---|---|---|---|
| 前进 | +1 | 0 | 0 | + | + | + | + |
| 后退 | −1 | 0 | 0 | − | − | − | − |
| 右移 | 0 | +1 | 0 | + | − | − | + |
| 左移 | 0 | −1 | 0 | − | + | + | − |
| 原地左转 | 0 | 0 | +1 | − | + | − | + |
| 原地右转 | 0 | 0 | −1 | + | − | + | − |

（表中"+"表示该轮速度值为正；**电机命令**再乘 `CHASSIS_WHEEL_SIGN_i`：
左列 FL/RL 为 −1、右列 FR/RR 为 +1。）

**动作 → 地图方向**（默认车头朝地图 +y，§7）：

| 地图方向 | 段字母 | 车体动作 |
|---|---|---|
| y 增大（屏幕向下） | D | 前进 |
| y 减小（屏幕向上） | U | 后退 |
| x 增大（屏幕向右） | R | 车体**向左**（因为地图 +x 在车体左侧） |
| x 减小（屏幕向左） | L | 车体向右 |

> **当前导航不使用横移**：每段先原地转到该段方向，再直走（§7.4）。上表仍适用于手动模式（`&M2` + `&L/&R` 等）。
>
> **手动速度折扣**：`&U/&D`（前进/后退）与 `&L/&R`（平移或连续转）的实际速度 = 满量程 × `CHASSIS_MANUAL_SPEED_SCALE`（现 **0.3333**，2026-09-12 按要求降到原来的 1/3）→ 前进最高约 **83 RPM ≈ 0.36 m/s**（原 250 RPM ≈ 1.06 m/s）。**导航不受这个折扣影响**（导航速度由 `spd` 决定）。
> 角度转（`&L90`/`&R90`、导航段前对准）走的是转向 PID，速度由 `CHASSIS_TURN_MAX_WHEEL_RPM`（现 90）决定，不乘这个折扣。

## 6. 航向（yaw）方向与原地转

### 6.1 传感器链路

- HWT101 通过 UART 提供累积 yaw；上电后需**静止约 3 s**（静止窗 ≥3000 ms、窗口内 yaw 极差 ≤0.5°、≥20 个 `0x53` 样本）才建立零漂基准，并同时估出**角速度零偏**（串口打印 `[IMU] zero-drift ready`；屏幕 `IMU ZERO CAL x.xs` 倒计时 → `IMU ZERO DONE`；`yaw` 命令可查 `ready=1`、`bias=`）。细节见 §16.3。
- 传感器倒装，原始读数是**右转为正**；固件用
  `heading_deg = HWT101_GetZeroDriftDeg() × CHASSIS_YAW_RIGHT_POSITIVE_SIGN(−1)`，
  使内部航向**左转（俯视逆时针）为正**，与 `omega>0` 同向。
- 需要重新对基准时用 `zero`（控制台）或 `&zero`（蓝牙）：把**当前**朝向记为 0°，之后约 **3 s** 内不要动车（标定窗口会重新计时，屏幕倒计时可见）。

### 6.2 转角命令的两层符号

| 层 | 约定 |
|---|---|
| 蓝牙 token | `&L<角度>` / `&R<角度>`：**右转为正**（`&R90` = +90） |
| 内部调用 | `ChassisMotor_TurnRelative(角度)`：**左转为正**（+90 = 逆时针） |

因此 `&R90` → token 角 +90 → 内部 `TurnRelative(-90)` → 顺时针，与期望一致。

### 6.3 原地转的实现

- `CHASSIS_MODE_TURN` 下 `L/R` 为原地转；`ChassisMotor_TurnRelative()` 启动航向 PID（默认 `kp=0.045 / ki=0.0005 / kd=0.0035`，可用 `kp/ki/kd` 命令改，`save` 存 flash）。
- 到位判据：**两级** —— ① `±0.01°` 且角速度 <2 °/s、连续 10 个周期（≈200 ms）；② 或 `|误差| ≤ 0.05°` **连续保持 0.5 s**（体检行标 `FB`）。超时 8 s 强制结束；转向轮速上限 90 RPM。细节与判读见 §16.1/§16.3。
- 标定未完成（`ready=0`）时转向会被拒绝：`turn` 直接返回 `HAL_ERROR`，蓝牙打印 `[TURN] rejected: need &EN and IMU zero-drift ready`。
- 导航里的"段前对准"与手动 `&L90` 走的是同一套 PID，所以转向的快慢/精度由这三个增益决定（不在导航两参数里）。

## 7. 栅格导航里的方向绑定

### 7.1 地图约定

8×8 格、格距 300 mm、原点在左上、`x` 向右、`y` 向下（`Core/Inc/grid_nav.h:10-14`）。
默认摆放约定：**车头沿地图 +y 摆放**，并执行 `zero` 把航向基准对齐到该方向。

### 7.2 唯一的"地图方向 → 车体速度"映射（已修复）

`ZDT_Nav_GetBodyVelocity()` 是**全工程唯一的方向映射源**：

```
车头朝地图 +y（ZDT_NAV_MAP_FORWARD_PLUS_Y = 1，默认）：
    forward = sign(segment->dy)   → vx = forward
    right   = sign(segment->dx)   → vy = -right
车头朝地图 -y（= 0）：
    vx = -forward, vy = right
```

随后四轮值按 §4 的混合公式给出（`vx±vy`）。

### 7.3 几何矛盾的成因与修法（已修复）

刚性约束：车头方向 F 与车体右侧 R 必须满足"R = F 顺时针 90°（俯视）"。地图 `x` 右、`y` 下，因此

- 车头朝 **+y**：地图 +x 落在车体**左侧** → `dx` 段必须 `vy` 取负；
- 车头朝 **−y**：地图 +x 落在车体**右侧** → `dx` 段 `vy` 取正，而 `dy` 段要取负。

两者不可能同时成立——这就是修复前"某些段方向整体相反"的根源。修法：用编译期开关 `ZDT_NAV_MAP_FORWARD_PLUS_Y` 二选一，并把映射收敛到一处。现场判定：走一个只有 D 段的目标、再走一个只有 R 段的目标，看是否沿规划方向走。

### 7.4 直线段执行链（速度模式：直走 + 到弯原地旋转）

现行流程（默认 `posmode 0`）：

1. `&goto x y` → A* 规划 → 合并成"同方向连续段"（`grid_nav.c:188-216`）。
2. `ZDT_Nav_Start()`：读四轮位置基准；按 `段长 × 300 mm ÷ 255.694 mm/圈` 折成圈数（≈ **1.1733 圈/格**，轮径 81.39 mm）。
3. **对准**：`ZDT_Nav_SegmentHeadingDeg()` 把该段方向换成航向目标 —— D=0°、R=+90°、U=180°、L=−90°；与当前航向差 >3° 就用 `ChassisMotor_TurnRelative()` **原地转**，转完重采里程基准。
4. **直走**：`ChassisMotor_SetVelocity(±spd, 0, 0)`（只有 vx，不横移）。驱动时间由 `ZDT_Nav_DistanceToMs()` 用 `t1000` 换算，时间到就发 `STOP`。
   **直走中持续做航向保持**：`ZDT_Nav_HeadingHold()` 每 80 ms 算一次"本段目标航向 − 当前航向"，用一个受限的 omega 修回来（`omega = clamp(0.030 × 误差, ±0.20)`；误差 <0.2° 不修，防抖）。这样"原地转 90° 后直走漂到 90.6°"这类**走行中漂移**会被实时压住；段末日志里的 `hold peak X.XX deg` 就是保持期间的最大偏差。
5. **段末复核**：等轮子停稳 → 回读四轮位置 → 投影成实际圈数（直走时四轮同向，取中位数）→ 误差 >0.05 圈且 ≤0.5 圈则补一小段直走（最多 3 次，补走用 0.5× 速度）。
6. **漂移体检**：与本段应保持的航向比较，>20° 直接停车报错；>3° 只打印 `heading drift`。
7. 下一段：`align_done` 清零 → 回到第 3 步重新对准。

**现场调参：只有两个参数**（串口或蓝牙都能改；改完 `save` 存进 W25Q64，`read` 读回来）

| 命令 | 含义 | 默认值 |
|---|---|---|
| `spd<值>` | 速度：**轮速(RPM) = 值 × CHASSIS_MAX_WHEEL_RPM（现 250）** | 0.50 → 125 RPM ≈ 0.53 m/s |
| `t1000<值>` | **`spd = 0.50` 时走 1000 mm 需要多少毫秒**（规划时间上的整体微调系数 k） | 1900 |
| `nav` | 打印这两个值（附 RPM / mm/s 换算） | — |
| `navreset` | 恢复默认 | — |
| `save` / `read` | 存 / 读 W25Q64（**PID 与导航参数一起**，各自独立扇区 + CRC） | — |

- **驱动时间不再是"距离 × 常数"的线性换算，而是梯形/三角形速度规划算出来的**（2026-09-12 方案 B，见 §7.6）。`t1000` 现在的角色是"整体时间微调系数"：`ms = plan_ms(距离, 速度) × t1000 / plan_ms(1000mm, spd=0.50)`。
- 距离由格数换算（1 格 = 300 mm，轮径 81.39 mm → 255.694 mm/圈）。
- 蓝牙写法与 `&kp1.0` 同风格、**不加空格**：`&nav`、`&spd0.14`、`&t10002100`、`&save`、`&read`；串口控制台可用空格（`spd 0.14`）。
- 蓝牙发 `&goto 1 1` 这类**带空格的命令时最后不必加换行**：网格/数值命令靠 300 ms 空闲超时自动派发（`BT_BUTTON_GRID_WAIT_MS`）；有 `\r\n` 则立刻派发。改这条阈值见调试手册 §4.11。
- 参数本体在 `Core/Src/nav_params.c`（含默认值），导航代码通过 `Nav_Params()` 读取。
- 其余（段前对准容差 3°、段末漂移上限 20°、补走降速 0.5×、最短驱动 40 ms）都是编译期常量，放在 `zdt_motor.c` 顶部。

### 7.5 这两个参数各自影响什么

| 参数 | 物理含义 | 调**大** | 调**小** | 怎么用 |
|---|---|---|---|---|
| `spd` | 驱动轮速（比例 × 250 RPM）。**只决定"跑多快"** | 更快、更响，越容易打滑 | 更慢更稳 | 想快就往上调；**方案 B 之后改它不再需要重标 `t1000`**（速度已进公式），但打滑比例会变，仍建议复验一次 |
| `t1000` | 规划时间上的**整体微调系数**（等效"spd=0.50 走 1000 mm 的毫秒数"） | 同样距离**走得更远** | 走得更近 | **距离校准就用它**，一次校准后固定 |

**为什么还要留 `t1000`**：运动学部分（速度、加减速斜坡、梯形/三角形切换）已经由 `spd` + 编译期常量算准，剩下的残差来自"指令轮速 ≠ 实际轮速"（麦轮打滑、驱动器跟随误差、地面），这部分只能实测，用一个系数吸收最省事 —— 而且它不随段长/速度变，所以标一次就够。

**校准 `t1000`（卷尺，一次搞定）**：

1. 摆好车、`&zero`、`&EN`；
2. `&goto` 走一个已知距离（例如 `&goto 0 1`，1 格 = 300 mm；或走 3 格 ≈ 900 mm 更准）；
3. 卷尺量实际位移 `L_actual`，与期望 `L_want` 比较：
   - 实际偏小 → `t1000` 按比例调大：`t1000_new = t1000_old × L_want / L_actual`
   - 实际偏大 → 同理调小；
4. `save`；
5. **再各跑一次 1 格和 3 格，比较 `[NAV] SEGn done: 实测/目标rev` 两个比值** —— 方案 B 之后这两个比值应该基本一致（差异 <1%）。若仍明显不同，说明底盘实际加减速斜率与 `CHASSIS_ACCEL/DECEL_RPM_PER_S`(600/900) 不符，改那两个常量而不是 `t1000`。

> **换模型后要重标一次**：`t1000` 的含义没变（还是"spd=0.50 走 1000 mm 的毫秒数"），但实现从线性换成了规划，所以现场那台车的老值（1900）会偏短一点。按上面流程重标一次即可。若想直接吃到"理论值"，把 `t1000` 设为 **2051**（= `plan_ms(1000mm, spd=0.50)`，此时系数 k=1）。

### 7.6 距离模型：梯形/三角形速度规划（方案 B，2026-09-12）

**为什么原来的线性换算不够**：底盘层对下发的轮速做了斜率限制（`ChassisMotor_StepToward()`，加速 600 RPM/s、减速 900 RPM/s，每 20 ms 一步），所以每段直走的真实速度曲线都是"加速 - 匀速 - 减速"。原来是 `时间 = 距离 ÷ 1000 × t1000`，斜坡造成的那笔**与段长无关的固定欠走**只能靠标定吸收 —— 结果就是"按 1 格标定则长段偏长、按长段标定则 1 格偏短"，换段长就得重标，改 `spd` 更是全乱。

**现在的算法**（`ZDT_Nav_PlanDriveMs()`，`Core/Src/zdt_motor.c`）：

```
v = spd × 250 RPM → mm/s            轮周长 255.694 mm，即 v = spd × 1065.4 mm/s
A = 600 RPM/s → 2556.9 mm/s²        减速 D = 900 RPM/s → 3835.4 mm/s²
梯形（L ≥ v²/2A + v²/2D）: t = v/A + v/D + (L − v²/2A − v²/2D)/v
三角形（L 更短，到不了 v）: v_peak = √(2L/(1/A + 1/D))，t = v_peak/A + v_peak/D
ms = t × 1000 × t1000 / plan_ms(1000mm, spd=0.50)
```

**收益**：

| | 旧（线性） | 新（规划） |
|---|---|---|
| 段长变化 | 每段都要重标（1 格与 3 格差约 4%） | 一个 `t1000` 通用 |
| 改 `spd` | 距离跟着变，必须重标 | 距离不变（速度已进公式） |
| 短段（< 92 mm @spd0.5） | 线性外推，越短越离谱 | 自动走三角形解 |
| 段末补走（半速执行） | 时间按全速算 → 只走一半距离 → 补 2~3 次 | 时间按**实际速度**算 → 一次到位 |

**关键数字**（`spd = 0.50`，`t1000 = 1900`）：

| 段长 | 旧时间 | 新时间 | 备注 |
|---|---|---|---|
| 300 mm（1 格） | 570 ms | 683 ms | 斜坡占比高，旧模型严重偏短 |
| 900 mm（3 格） | 1710 ms | 1726 ms | 接近 1000 mm 时两模型巧合接近 |
| 1500 mm（5 格） | 2850 ms | 2770 ms | 旧模型偏长约 3% → 就是"到点又倒车"的来源 |
| 三角形阈值 | — | **92.5 mm** | 短于它就到不了巡航速度（`spd=0.50`）；补走用 0.25× 速度时阈值 23.1 mm |

**位置模式（`posmode 1`）不受影响**：那条路的时间由驱动器自己加减速决定（`ZDT_Nav_PositionTimeMs()`），本车已判定不可靠、默认不用。
5. 段末的里程复核（`[NAV] SEGn done: 实测/目标rev`）应该自己收敛到 1.0 附近；如果**始终**差一点，就是 `t1000` 还没校准好。

## 8. 里程 / 位置模式的符号链（已修复，附验证方法）

| 环节 | 表达式 | 位置 |
|---|---|---|
| 速度混合 | `电机命令 = 物理轮速 × CHASSIS_WHEEL_SIGN` | `chassis_motor.c:123` |
| 位置脉冲 | `wheel_sign = forward_signs = CHASSIS_WHEEL_SIGN` ✔ 与上一条一致 | `zdt_motor.c` `ZDT_Nav_SendPositionMove()` |
| 里程回读 | 回读增量 × `zdt_mileage_forward_signs` = 回读增量 × **(−CHASSIS_WHEEL_SIGN)** | `zdt_motor.c` 的 `zdt_mileage_forward_signs` |
| 位置脉冲下发 | 物理前进量 × **(+CHASSIS_WHEEL_SIGN)**（与速度模式一致） | `zdt_nav_command_signs` / `ZDT_Nav_StepPulses()` |
| 里程投影 | `实际圈数 = median( normalized_i / wheel_values_i )`（4 样本取中间两值平均，抗单轮野值） | `ZDT_Nav_MeasureDistance()` |

修复理由：ZDT（张大头 Emm/X 固件）里速度指令 `0xF6` 与位置指令 `0xFD` 的方向字节都是 `0x00=CW / 0x01=CCW`，回读 `0x36` 的符号位由 `data[1]` 解析（同源计数）。**修复前 `forward_signs = -CHASSIS_WHEEL_SIGN`，把"前进"读成负圈数**，于是 `error = target - measured` 变成 `target + |actual|`，每段都朝同一方向做一次更大的矫正（600→1200→2400 mm），现场表现就是"一直向右平移"。

**实测定位结果（2026-09-12 第四轮，`&goto 1 1` 日志）**：

```
[NAV] revs FL+1.877 FR+0.045 RL-0.057 RR+1.932 spread=1.977
[NAV] odometry suspect +2.140rev, skip correction
[NAV] SEG1 done: -0.967/1.173rev
```

> ⚠️ 这一轮的结论在第六轮被修正：当时的 `+1.877 rev` 是**"缓存+广播触发"路径的异常行为**（转过量是下发量的 1.885 倍，且只有 2/4 轮动作），据此反推的"脉冲当量 2000"是错的。正确值由 `poscal`（即时下发）测得 ≈**3730**，判定见下面的 `poscal` 小节。

由这一行可以直接读出两件事：

| 观察 | 推算 | 结论 |
|---|---|---|
| 同一次测量中 FR/RL 只有 **±0.05 圈**，而 FL/RR 有 1.9 圈 | 300 mm 应转 1.173 圈 | 该段只有**一对角线在驱动** → 车沿 45° 斜走（§11.5）；`revs` 行非零说明 4 个驱动器**都有** `0x36` 应答，所以不是总线/地址问题 |
| `spread=1.977` 且中位数 −0.967 | 中位数被两个"半死不活"的数据夹住 | 中位数抗野值只在**单轮**异常时有效；两轮同时异常时无意义——`SEG done: -0.967` 就是这么来的 |

**`poscal` 逐轮自标定（第六轮实测，先垫起小车）**：

```
[ZDT] poscal FL d1: cnt=-34756 rev=-0.5303 ppr=3771 p/rev read-sign=inverted
[ZDT] poscal FR d3: cnt=+34758 rev=+0.5304 ppr=3771 p/rev read-sign=same
[ZDT] poscal RL d2: cnt=-35495 rev=-0.5416 ppr=3693 p/rev read-sign=inverted
[ZDT] poscal RR d4: cnt=+35554 rev=+0.5425 ppr=3687 p/rev read-sign=same
[ZDT] poscal SUMMARY: FL=3771 FR=3771 RL=3693 RR=3687 p/rev (4/4 moved)
```

三条结论：

1. **四轮全部动作** ✓ —— 单地址、即时（`buffered=0`）的 `0xFD` 下发在这块板子上完全可用，所以导航改为同样的下发方式（§0.1-17）。
2. **脉冲当量 ≈3730 脉冲/圈**（四轮平均；前后两组差 2.2%）→ `ZDT_POSITION_PULSES_PER_REV = 3730.0f`。它是在"回读取 65536 计数/圈"的前提下的值。
3. **左列（FL/RL）`read-sign=inverted`、右列（FR/RR）`same`** —— 同一指令下左列回读符号相反，与 `CHASSIS_WHEEL_SIGN_*` 的左右分组一致，因此 `zdt_mileage_forward_signs = +CHASSIS_WHEEL_SIGN_*` 是自洽的 ✓。

**唯一还需卷尺验证的一环**：`poscal` 的 `rev` 是"计数 ÷ 65536"，如果回读实际不是 65536 计数/圈，上面 3730 会等比例错。判据：

```
&en → &U（按住约 1 秒）→ &STOP → 读 [MILEAGE] DIST
```

- 卷尺量出的位移 ≈ `DIST` → 回读尺度正确，3730 可用 ✅
- 实际位移 ≈ `DIST × 0.849` → 回读尺度偏大 1.177 倍：把 `ZDT_POSITION_COUNTS_PER_REV` 与 `ZDT_POSITION_PULSES_PER_REV` 按同一比例改（3730 → 3168，即手册默认的 3200 附近）

> 位置模式(Emm) 的**指令**单位是"脉冲"（由驱动器细分决定），与**回读**单位（65536 计数 = 360°）是两套，别混。参考 `docs/vendor/zdt-x42s/ZDT_串口控制格式总结.md`：`0xFD` 模式字节 `00=相对上一目标 / 01=绝对位置 / 02=相对当前位置`。

**⚠️ 第七轮实测补充：脉冲当量不是一台车一个常数，而是"逐轮、逐次"都可能变**。同一辆车上，`poscal` 两次运行的对照：

| 轮 | 第一次 `ppr` / `read-sign` | 第二次 `ppr` / `read-sign` |
|---|---|---|
| FL | 3771 / inverted | 3773 / inverted |
| **FR** | **3771 / same** | **6398 / inverted** ← 同一指令，转过量只剩 59%，符号也翻了 |
| RL | 3693 / inverted | 3691 / inverted |
| RR | 3687 / inverted | 3687 / inverted |

同时导航在 400 RPM 下出现"四轮符号全对、幅值差 3 倍"（§0.1-20）。**结论：这台驱动器的位置模式（`0xFD`）在当前配置下不可靠**——符号链没问题（已闭环），坏的是"每脉冲转多少"。

两条可选路线：
- **A（继续修位置模式）**：把转速降到与 `poscal` 相同的 120 RPM 复测（已改，见 §0.1-20）；若仍不一致，就得用 ZDT 上位机逐个核对四个驱动器的细分/固件（`verall` 显示地址 2、4 连版本查询都不回）。
- **B（绕开位置模式）**：把导航的直线段执行改成**速度模式 + 里程闭环**——速度模式已实测四轮一致到 0.03%（§0.1-15），里程回读精度 0.001 圈，完全够用来做"走到目标距离就停"。代价是要重新标定停止提前量与超调。

**速度模式交叉验证（第五轮实测，用于区分"坏轮"与"不认指令"）**：

```
&en → &U（约 1 秒）→ &STOP
[MILEAGE] FL=-2.5953rev FR=-2.5951rev RL=-2.5944rev RR=-2.5953rev   (spread 0.001rev)
```

四轮全部动作且一致到 **0.03%** → 驱动器、接线、编码器回读**都没有问题**，故障被限定在 `0xFD` 位置指令这一条路径上。这同时说明：**里程回读的精度完全够做闭环**（0.001 圈 ≈ 0.26 mm），所以"速度模式 + 里程闭环"是完全可行的退路。同一次测量中"前进读数为负"的符号问题见 §11.6。

**标定"计数/圈"（30 秒，只需转一次轮子）**：

```
dis           # 先关四轮使能（蓝牙 &dis / &off）：闭环步进使能后锁轴、手转不动
posref        # 抓四轮当前位置作为基准（驱动器仍上电，只是无力矩）
              # 在 1 号轮（FL）贴个标记，手转整 1 圈（转 2 圈也行，记得除以圈数）
posd          # 打印与基准的差值 → 就是"计数/圈"
```

输出形如：

```
[ZDT] posref set (mask=0xF).
[ZDT] d1 cnt=-65536 rev65536=-1.0000 rev3200=-20.4800 rev3600=-18.2044
[ZDT] d2 cnt=+8     rev65536=+0.0001 ...
[ZDT] d3 cnt=-4     ...
[ZDT] d4 cnt=+12    ...
```

| `cnt`（手转 1 圈的轮） | 结论 |
|---|---|
| ≈ ±65536 | 回读单位 = **65536 计数/圈**（Emm 默认），与固件现有配置一致 ✅ |
| ≈ ±3200 | 回读单位 = **3200 脉冲/圈** → `ZDT_POSITION_COUNTS_PER_REV` 改成 `3200.0` |
| ≈ ±3600 | 驱动是 **X 固件**（0.1° 为单位）→ 宏改成 `3600.0` |
| 其它轮也跟着大动 | 读数串台/帧解析错位：先用 `posq` 看原始行 |
| ≈ 0 | 转的不是该轮、电机被抱死或读数没刷新，重做 |

未转动的三个轮 `cnt` 应接近 0（几十计数以内）——这同时验证了"四轮位置不会互相串"。

现场核对（3 分钟）：使能后发一次 `&U` 前进，再发 `&STOP`，看串口打印：

```
[MILEAGE] FL=... FR=... / RL=... RR=...
[MILEAGE] AVG(4/4)=+X.XXXXrev CNT=...
[MILEAGE] DIST=+XXX.Xmm
```

- 前进后 `DIST` 应为**正**；若为负，说明驱动器回读符号与指令符号相反，需把 `zdt_mileage_forward_signs` 取反**并同步** `ZDT_Nav_SendPositionMove()` 的 `wheel_sign`（两者必须同号）。
- 单轮符号不一致（4 个轮的回读符号有正有负）说明该路电机接线/地址与符号表不匹配，先查接线，不要动公式。

## 9. 现场核对流程（10 分钟，按顺序做）

**准备**：串口终端（UART4 9600 8N1）或蓝牙；上电后**保持静止**直到 `yaw` 打印 `ready=1`。
顺序：先在地面做**无力矩手推判定**（测试 A，步骤 1）→ 再垫起核对**电机方向与显示**（步骤 2-5）→ 最后落地做**车体运动方向判定**（测试 B/D，步骤 6-7）。
注意：张大头闭环步进在**使能状态下会锁轴**，手推测试必须在**未发 `&EN`**（或断电）时做。

| 步骤 | 操作 | 判据 |
|---|---|---|
| 0 | `yaw` | `ready=1`；否则重新上电并静止 |
| 0a | **摆好车头方向**（车头贴地图 +y 轴线）→ `zero`（或蓝牙 `&zero`）→ 静止约 **3 s**（看屏幕出现 `IMU ZERO DONE`） | 重新建立航向基准；**否则"前进"会斜着走**（§11.4）。`yaw` 复查 `ready=1` |
| 0b | **里程体检（两种做法，任选其一）**：① 手转法（最准）：**先发 `&dis`（或 `&off`）关掉四轮使能** —— 闭环步进一旦使能就会锁轴、手转不动；再 `posref` → 手转 1 号轮整 1 圈 → `posd`；② 驱动法（不用手转）：`&EN` 后直接跑一次 `&goto`，看段末 `[NAV] revs ...` 与 `[NAV] applied rpm ...` 两行 | 读出"计数/圈"与正负：按 §8 判定单位是否要改、符号是否要反；手转法未转动的三轮 `cnt` 应≈0 |
| 0c | `posq`（可选，抓原始帧） | 打印四轮 `0x36` 原始帧与解码值，用于确认帧格式 |
| 0d | **`poscal` 逐轮自标定（推荐，垫起小车后跑）** | 每轮打印 `cnt/rev/ppr/read-sign`：`ppr` = 该轮脉冲当量（本车实测 2000），`NO MOVEMENT` = 该轮不执行 `0xFD`（本车地址 3、2 就是这种，见 §0.1-14）；末尾汇总 `poscal SUMMARY: ...` |
| 1 | **测试 A（排布判定）**：**先不要发 `&EN`**，让电机无力矩，在**地面**朝**车体左前方 45°**（= 方向与 FL–RR 对角线平行，见 §3.3 的图）匀速推小车 | FL、RR 应**几乎不转**（辊子空转），FR、RL 被带着转；换另一条对角线（朝右前方 45°）推则相反。**若两条对角线的表现正好互换** → 实物是镜像底盘（情况 2 / a2），按 §3.2 处理。（此测试无法区分"情况 1 左右同型号"，那种排布要靠步骤 6 的横移判定） |
| 2 | 垫起小车，`&EN` | 串口 `OK!`，四轮锁定 |
| 3 | `&U` | IPS200 第 3/4 行：`RPM1/RPM2 < 0`、`RPM3/RPM4 > 0`（§5）；四个轮子物理上同向（都向前滚） |
| 4 | `&M1` + `&L90`（原地左转） | 四个 `RPM` **符号始终一致**（幅值随 PID 输出变化）；落地后车应为**逆时针（向左）**转 |
| 5 | `&STOP` → 看 `[MILEAGE]` | `DIST` 为正（§8） |
| 6 | 落地，**测试 B**：`&M2` + `&L`（平移模式左移） | 三种现象：车**向左** → 实车符合 `chassis_motor.h:8`（分支 b，**修复后应为这一种**）；车**向右** → 镜像底盘（a2）；车**几乎不动/原地挣扎** → 左右同型号（a1）。见下表 |
| 7 | 落地，**测试 D（地图方向）**：车头朝地图 +y 摆好 → `&pose 0 0` → `&goto 0 3`（3 个 D 段）→ 再 `&goto 3 3`（3 个 R 段） | 两段都应沿规划方向走（D 段向前开、R 段向车体左侧平移）。若方向相反 → 按 §7.3 翻转 `ZDT_NAV_MAP_FORWARD_PLUS_Y`；若某一段走反一段走对 → 映射公式被改动了，回到 §7.2 |

> 步骤 4 的判据说明：原地转时四个电机命令同号，是因为左列电机 `SIGN=-1` 已把方向补偿回来（§5）。因此"某个轮子转反"只可能来自接线/地址错误，而不是公式问题。

**跑 `&goto` 时按串口日志判定（修复后新增/明确的日志行）**：

| 日志 | 含义 | 若出现说明 |
|---|---|---|
| `[NAV] EXEC start.` | 路径开始执行 | — |
| `[NAV] waiting for wheels to settle` | 估算时间到了但轮子还在转，正在等停稳（§0.1-8） | 正常偶尔出现；若每段都出现，说明驱动器加速度较慢，可把 `ZDT_NAV_POSITION_MARGIN_MS` 调大以减少等待 |
| `[NAV] revs FL.. FR.. RL.. RR.. spread=..` | 四轮实测量（物理前进圈数）+ 四轮离散度，与 `wheel_values` 对照即可判定单位/符号/接线 | 见 §8 的判定表 |
| `[NAV] correct ±X.XXXrev (n/3)` | 段末里程矫正，含方向与大小 | 正常应是 0.05 圈以内的小量 |
| `[NAV] odometry suspect ±X.XXXrev, skip correction` | 误差超过 0.5 圈，已放弃矫正 | 里程仍不可信：先按 §8 用 `posq` 抓原始帧 |
| `[NAV] heading correct ±X.X deg` | 段末航向矫正，**这就是现场看到的"突然转角"** | 数值大说明直线段跑偏（轮速不一致、地面打滑，或上一动作没停就开下一段——现已加停稳判定） |
| `[NAV] SEGn done: X.XXX/X.XXXrev` | 段完成，实测/目标圈数 | 两者应接近 |
| `[NAV] ARRIVED.` | 全部段完成 | — |

**三种结局的收敛动作（由测试 B / D 判定后统一口径）**：

| 分支 | 现场现象 | 结论 | 必须做的修改 |
|---|---|---|---|
| **b（标准 X 型；2026-09-12 已由推车实测确认，见 §3.4）** | 步骤 6 车**向左**横移（与 `chassis_motor.h:8` 一致）；步骤 3、4 的轮向判据全部成立 | 实物排布 = §3.3，混合公式与符号表都对 | 已由本次修复覆盖（`&L/&R`、地图映射、里程符号）；只需按步骤 7 确认摆放约定 |
| **a1（情况 1：左右同型号）** | 步骤 6 车**几乎不动或原地挣扎**（四轮推力抵消）；步骤 7 的 R 段基本走不动 | 实物排布错，不是符号问题 | 重排轮子为"对角线同型号"（换轮位/换轮型），再回到分支 b 复测。（**本车 2026-09-12 实测已排除**，见 §3.4） |
| **a2（情况 2：镜像底盘）** | 步骤 6 车**向右**横移（方向反，即与 `chassis_motor.h:8` 相反）；步骤 4 的 `&L90` 实际**右转**，且自转力臂偏弱 | 对角线配对正确、左右手性整体镜像 | ① 首选实物换轮（把两条对角线的轮型对调）；**或** ② 保留镜像排布，翻转 `chassis_motor.h` 的 `CHASSIS_WHEEL_SIGN_*` 全部四个符号并同步地图映射/里程符号。（**本车 2026-09-12 实测已排除**，见 §3.4） |

> 建议优先走 a1/a2 的"改机械"路线：在固件里叠符号会让后续每个模块都要记住一个反号，风险远大于换一次轮子。

## 11. 故障复盘：`&pose 0 0` → `&goto 1 1` 出现"先转 45°、再一直向右平移"

### 11.1 这条指令本来应该做什么

`&goto 1 1` 走 4 邻域 A*（搜索顺序"上、右、下、左"，`grid_nav.c:25-27`），从 (0,0) 到 (1,1) 得到的路径是 **(0,0) → (1,0) → (1,1)**，合并成两个直线段：

| 段 | 方向字母 | dx/dy | 长度 | 应有动作 |
|---|---|---|---|---|
| SEG1 | `R` | dx=+1 | 1 格 = 300 mm = **1.1733 圈** | 地图 +x 方向（按 §7.3 默认约定 = 车体**向左**平移） |
| SEG2 | `D` | dy=+1 | 1 格 | 地图 +y 方向（= 车体前进） |

每段结束时程序会：回读四轮位置 → 投影里程 → 与目标比较（误差 >0.05 圈则矫正，最多 3 次）→ 航向偏差 >0.5° 则原地转回来。

### 11.2 现象与根因的对应

| 现场现象 | 代码层面根因 |
|---|---|
| **一直向右平移**（远远超过 300 mm，且看不到"到点停车"） | `zdt_mileage_forward_signs = -CHASSIS_WHEEL_SIGN` 使实测里程**符号取反**：`measured = -actual`，于是 `error = target - measured = target + actual`。矫正方向永远相同，且长度按 **300 → +600 → +1200 → +2400 mm** 的级数增长，在 `ZDT_NAV_MAX_CORRECTIONS = 3` 用尽前会一直朝同一方向走（累计约 4.5 m），看起来就是"一直向右平移" |
| **中途"旋转 45° 左右"** | 段末的航向矫正 `ChassisMotor_TurnRelative(lroundf(heading_error))`（日志 `[NAV] heading correct ±X.X deg`）。它只会发生在"某一段的里程判定结束之后"，因此现场可能表现为"横向漂移中车头被转回来"，也可能因为里程判定被提前满足而先转头、后继续横移 —— 两种时序的触发条件都是"里程不可信 + 矫正无上限"，都随本次修复消除 |
| 每段都可能重复出现 | 里程符号是全局的，每一段都会重演；且旋转矫正后下一段还沿用了转动前的基准位置（缺陷 4），误差继续累积 |
| **第二轮实测**：`SEG2 done: -31119.500/1.173rev`、`odometry suspect +60111.922rev`、`heading correct -16.6 deg`，并且看到"90° 还没转完就开始平移" | ① 里程**量值**仍不对（300 mm 不可能是上万圈）→ 已加 `posq` 原始帧诊断，见 §8；② 段末只按估算时间判定结束，驱动器还在走就进了下一段/转角矫正 → 已加"等停稳"判定（§0.1-8）；③ `heading correct -16.6°` 说明那一段车头确实偏了 16.6°，与"上一动作没停就下发下一动作"相符 |
| **第三轮实测**：`SEG1 done: -117340.250/1.173rev`、`odometry suspect +117341.422rev`、`heading correct +8.1 deg`（比上一轮小），现象为"先向左平移，然后向右上 30 多度斜着走" | ① **确认根因**：`ZDT_Nav_MeasureDistance()` 返回的是编码器计数，却当成"圈"比较 → 数值大 65536 倍（`-117340/1.173 ≈ -10⁵`），这才是"跑飞量级"的来源，已修（§0.1-10）；② 航向矫正从 16.6° 降到 8.1° → 停稳判定生效；③ "向右上 30 多度斜着走" = **航向基准与地图轴不重合**（上电后才把车摆进起点，或摆位本身斜了 30 多度），导航只保持"出发那一刻的朝向"，不会自动对齐地图轴 → 已加 `zero`/`&zero` 重新对基准（§0.1-11、§11.4） |

### 11.3 复测方法（修复后）

```
&EN                      # 使能
&pose 0 0                # 摆好车头朝地图 +y，再置位姿
&goto 1 1                # 期望：先向车体左侧平移 300 mm，再向前 300 mm，串口打印 ARRIVED
```

期望日志（这是判断"里程是否已可信"的直接依据）：

```
[NAV] EXEC start.
[NAV] SEG1 done: 1.17X/1.173rev          # 实测≈目标（误差 0.05 圈以内）
[NAV] heading correct +X.X deg           # 可选：只有真的跑偏才出现，数值应很小
[NAV] SEG2 done: 1.1XX/1.173rev
[NAV] ARRIVED.
```

- 若出现 `[NAV] odometry suspect ...`：说明里程仍不可信，按 §8 核对回读符号与接线，**不要**放宽矫正上限。
- 若 `SEG1 done` 的实测值与目标差很多但车确实走了 300 mm：说明轮径/脉冲标定（81.39 mm、3200 脉冲/圈）与实际不符，按 `[MILEAGE]` 打印重新标定。
- 若方向整体反了：按 §7.3 翻转 `ZDT_NAV_MAP_FORWARD_PLUS_Y`。

### 11.4 为什么"前进"会斜着走 30 多度（不是麦轮问题）

导航里**没有任何"把车对齐到地图轴"的逻辑**：

- 上电后 HWT101 把**上电那一刻的朝向**记为 0°（§6.1，需静止 10 帧）；
- `ZDT_Nav_Start()` 把"开始执行那一刻的航向"记为 `zdt_nav_heading_target`，之后只用 IMU 保持这个朝向不变；
- 地图 → 车体的映射是**固定轴绑定**（§7.2），不随实测航向旋转。

所以只要"上电时的朝向"和"摆进起点后的朝向"不一致（现场很常见：先上电、再把车搬/转到起点），或者摆位本身就斜了 30°，那么所有"前进"都会沿车头方向斜着走 30°，所有"横移"也会斜 30° —— 现象就是"向右上 30 多度斜着走"。

**处理办法**：摆好车（车头贴地图 +y 轴线）→ `zero`（或 `&zero`）→ 静止约 **3 s**（屏幕显示 `IMU ZERO DONE`）→ `yaw` 复查 `ready=1` → 再 `&goto`。若没有 `zero` 这一步，就改成"上电前先把车摆好、上电后别动"。

> 顺带说明：`heading correct ±X.X deg` 是**段末的漂移矫正**（上一轮 16.6°、本轮 8.1°），与"斜着走"是两件事 —— 前者是走行中车头被撞偏/打滑导致的回头，后者是基准方向本身就斜。

### 11.5 "向左下 45° 再向右上 45°"：只有一对角线在驱动

第四轮实测（`&goto 1 1`）的现象是"先向左下 45° 平移、再向右上平移"，两段都是斜移。日志给出了原因：

```
[NAV] revs FL+1.877 FR+0.045 RL-0.057 RR+1.932 spread=1.977
```

**FL、RR（地址 1、4）转了 ≈1.9 圈，FR、RL（地址 3、2）只有 ±0.05 圈** —— 四个轮子里只有一对角线在动。麦轮的推力只沿辊子轴线（§3.1），两条对角线互为镜像，因此：

- 只驱动 FL–RR 这条对角线时，推力合成沿 â_FL = â_RR 方向 → 车沿 **45° 斜线**平移；
- 另一条对角线（FR、RL）的辊子方向正好与运动方向平行 → 它们**被动空转、轮子不转**，所以回读≈0；
- 两段命令的符号相反 → 两段斜移方向相反（左下 / 右上），与现象完全一致。

这与 §3.4 的手推实测（沿 FL–RR 推时 FL、RR 不转）是同一个几何事实的两面：**FL、RR 的辊子轴线沿 FR–RL 对角线**，所以"沿 FL–RR 推"让它们空转，而"只有 FL、RR 驱动"则让车沿 45° 走。

**处理**：让地址 3、2 也执行 `0xFD`（`poscal` 可判定它们是"不认指令"还是"没使能"），否则导航必须放弃"位置模式四轮同发"的方案（例如改为速度模式 + 里程闭环，或改用单轮位置矫正）。这一步是本车导航能否走直线的前提，优先于其他标定。

### 11.6 还没定的一件事：位置模式与速度模式的方向不一致

现场已确认两件事：

| 观测 | 结论 |
|---|---|
| `&M1` + `&U`（**速度模式**）→ 车**前进** ✓ | 混合公式 + `CHASSIS_WHEEL_SIGN_*` + 速度模式方向字节这一整条链是**对的** |
| `&goto`（**位置模式**）→ 车**一上来就往后退**，之后出现"只有右轮动、左轮不动"的偏斜 | 位置模式这条链的方向**与速度模式不一致**（或地图摆放约定与预期相反） |

代码层面两条路径的方向规则**完全相同**（`ZDT_Motor_SetSpeedRpmInternal()` 与 `ZDT_Motor_MovePositionPulsesAddr()` 都是 `正值 → 0x00 = CW`），导航的每轮脉冲也用同一个符号表（`w × CHASSIS_WHEEL_SIGN_i`），所以差异只能来自下面三种之一，靠一次实测即可区分：

| 可能 | 判据 |
|---|---|
| ① 地图摆放约定相反（车头朝了地图 -y） | `&goto` 的目标方向与车头方向相反时，**后退是正确行为**。核对：车头是否贴地图 **+y**（屏幕上向下）；必要时把 `ZDT_NAV_MAP_FORWARD_PLUS_Y` 改成 `0U` |
| ② 位置模式的每轮符号与速度模式相反 | 垫起车跑 `&poscal`，**肉眼看每一轮转向**（轮顶朝车头 = 前）：若某轮被命令 +2000 脉冲却向后转，则该轮位置模式符号与速度模式相反 |
| ③ 只有部分轮子收到指令（旧固件是"缓存+触发"路径的毛病） | 新固件已改为逐轮即时下发；复测时看日志里每个 `[NAV] move ... pulses FL.. FR.. RL.. RR..` 后四轮是否都动 |

**新增诊断**：每次导航位移都会打印四轮实际脉冲，例如

```
[NAV] move 1.173rev sign=+1 pulses FL+4378 FR-4378 RL-4378 RR+4378
```

拿这行与 `&U`（速度模式，四轮同为 `CHASSIS_WHEEL_SIGN` 方向的命令）对照：**若同一次"前进"意图下两者的符号模式不同，就是②**；若相同而车仍后退，就是①。

## 15. 融合定位：评估过，已撤回（2026-09-12）

**结论：本车不适合做"陀螺 + 里程计"的位姿融合，相关代码已全部撤除**（`ZDT_Odom_*`、`&where`/`&where0`、屏幕 `POS` 行、段末 `[ODOM]` 打印都删掉了）。

**为什么不做**：

1. HWT101 只输出转动（`0x53` yaw、`0x52` 角速度，见 `main.c:133-142`），算平移要对加速度二次积分；本车没有可用的加速度输出。即便有，零偏 b 会让位置误差按 ½bt² 增长（b=0.01 m/s² 时 10 s 差 0.5 m、60 s 差 18 m），比赛尺度不可用。
2. 现场实测：加入 10 Hz 位姿采样后**车体剧烈抖动、原地转精度下降** —— `0x36` 查询帧会与底盘 20 ms 的调速帧抢 FDCAN2 发送队列，抢不过就丢那一拍的调速命令。
3. 改成"借用已有查询结果"（零额外流量）后现场仍反馈抖动、精度不如原来 → 按要求整体撤除。

**当时实现的算法（留档，供以后参考）**：位移取四轮 `0x36` 增量按麦轮正运动学解算（`s_x=(D1+D2+D3+D4)/4`、`s_y=(D1−D2−D3+D4)/4`），航向取陀螺 yaw，再用采样中点航向把车体位移旋转到地图系（x 右、y 下）。公式本身与 `ChassisMotor_Mix()` 互逆、校验算例正确，问题出在**采样所需的额外 CAN 流量**与整体收益不成比例。

**当前保留的定位能力（都是原有、已验证的）**：

| 能力 | 实现 |
|---|---|
| 航向保持 / 原地转 | HWT101 yaw + 转角 PID（`kp/ki/kd`），用于段前对准与手动 `&L90`/`&R90` |
| 直线段距离 | 速度模式 + 定时（`spd`/`t1000`），段末单轮里程复核（`[NAV] revs`、`[NAV] SEGn done`） |
| 全局栅格位置 | `&pose x y` 锚定 + 每段 `GridNav_SetPose()` |
| 绝对修正（未做） | 视觉二维码 / 贴边对齐 |

**以后若还要做定位**：先把四个驱动器统一（细分/固件，见 §0.1-18），再考虑低速率（≤2 Hz）或只在段末采样的位姿估计，并且必须验证"加入后不劣化原有转向精度"。


### 15.1 IPS200 屏幕显示的内容（8 行，无加速度）

| 屏幕行 | 含义 | 来源 |
|---|---|---|

| `RPM1/RPM2` = FL/RL、`RPM3/RPM4` = FR/RR | 实际下发的**轮速指令**（斜坡后，RPM） | 底盘 20 ms 节拍 |
| `PID e ±XX.XX deg / out ±X.XX` | 原地转 PID 的**角度误差（0.01°）/ 归一化输出** | 转角控制 |
| `KP / KI`、`KD + TURN\|IDLE` | 转角 PID 增益与运行状态 | 命令或 flash |

> 2026-09-12：`ANG` 与 `PID e` 的小数位从 0.1° 提到 **0.01°**（与串口 `[TURN] done … err=` 的 3 位小数、0.01° 到位判据口径一致）。屏幕是 320×240、5×7 字体、起点 x=150 → 一行可放约 28 字符，加宽后 `ANG +123.45 deg`（15 字符）依然宽裕。

（屏幕曾短暂加过一行 `POS X.. Y..`（融合位姿），因抖动问题已撤除，见 §15。）

**屏幕没有显示任何加速度**：本车固件不解析加速度帧（HWT101 只用 `0x53`/`0x52` 两种），也没有可用的加速度计数据。容易混的两个"加速度"其实是**驱动器参数**（不上屏）：速度指令里的加速度字节 `ZDT_CAN_RUN_ACCELERATION = 0x00`（0 = 驱动器不做斜坡，由底盘斜坡 600 RPM/s 加速、900 RPM/s 减速 ≈ 2.56 / 3.84 m/s²）、位置模式的 `ZDT_NAV_POSITION_ACCELERATION = 200`。

## 16. 转向参数与 ≤3 s 指标

### 16.1 当前用的参数（2026-09-12 现场实测稳定）

| 参数 | 值 | 位置 |
|---|---|---|
| `kp` / `ki` / `kd` | **0.045 / 0.0005 / 0.0035** | `chassis_motor.h` 编译期默认值；运行时用 `&kp`/`&ki`/`&kd` 改，`&save` 存 flash |
| 转向档位 | **精确档**（手动 `&L90`）= 90 RPM / 0.05°/0.5 s；**快速档**（导航对准）= 120 RPM / 0.5°/200 ms | `chassis_turn_profile_precise/fast`（§16.6） |
| **底盘下发节拍** | **4 ms**（控制环 250 Hz，也是末端执行粒度 ≈0.05°） | `CHASSIS_TX_PERIOD_MS` |
| 手动速度折扣 | 0.3333（= 原来的 1/3） | `CHASSIS_MANUAL_SPEED_SCALE`，只作用 `&U/&D/&L/&R` |
| 末端摩擦补偿 kick | 误差大于该档 kick 门槛（精确 0.06° / 快速 0.60°）且输出 < 0.08 → 直接给 0.08（≈7.2 RPM @90） | 档位表 `kick_deg` + `CHASSIS_TURN_MIN_EFFECTIVE_OUTPUT` |
| 到位判据 | ① 主判据；② 稳定带驻留（打 `FB`）；③ 无进展兜底（打 `ST`）—— 阈值都在档位表里 | §16.3 / §16.5 |

> 注意：flash 里若已存过 PID（曾经 `&save`），`&EN` 会用 **flash 里的值覆盖编译期默认值** → 现场改完必须 `&save`。

**每次原地转结束都会自动打一行体检**（不需要开关），这就是"转向 ≤3 s"的直接判据：

```
[TURN] done 1680ms target=+90.00 err=+0.008 overshoot=0.014 peak_o=1.00
[TURN] done 2410ms target=-90.00 err=+0.041 overshoot=0.062 peak_o=1.00  FB
```

| 字段 | 含义 |
|---|---|
| `done <ms>` | 从起转到判到位的总耗时；>3000 ms 会追加 `OVER-3s` |
| `err` | **判到位那一刻的残余误差**（度，3 位小数；转结束后 `chassis_pid_error_deg` 会被清零，故单独留了 `turn_final_error_deg`） |
| `overshoot` | 反向误差峰值 = 过冲（度），越小越稳 |
| `peak_o` | PID 输出峰值；长期 1.00 说明吃满了转向轮速上限 |
| `FB` | 本次靠 **0.05°/0.5 s 稳定带**判到位（0.01° 主判据没达成），见 §16.3 |

### 16.2 需要再调时的方向

> **先读 §16.5（死区）和 §16.6（提速杠杆）**：转向慢/超时的头号原因是"死区没覆盖 + 执行粒度太粗"，**不是增益不够**。给这种环加 `ki` 只会抖（积分对抗静摩擦 → 极限环）。比赛要总时间就调 §16.6 的三项，别加 `ki`。

| 现象 | 原因 | 调整 |
|---|---|---|
| 耗时 >3 s，且收敛慢、输出未饱和 | 增益偏小 | 提高 `kp`（0.045 → 0.055） |
| 耗时 >3 s，但输出长期 ±1.00 而车转得慢 | 速度上限偏低 | 提高该档的 `max_wheel_rpm`（精确档 90 → 120） |
| 过冲大（`overshoot` > 2°） | `kp` 偏大 / `kd` 偏小 | 降 `kp` 或加 `kd` |
| 抖动、轮子一顿一顿 | `kd` 偏大或速度上限偏高引起极限环 | 降 `kd`；也可降该档上限 |
| `err` 卡在判据带边缘然后 `ST`/超时 | 静摩擦死区没被覆盖 | §16.5：kick 门槛 / 节拍 / kick 幅值 |
| 一加 `ki` 就抖 | 积分对抗静摩擦的极限环（执行器分辨率不足的典型表现） | 把 `ki` 退回去，改 §16.5 那三项 |
| **比赛要更快** | 90° 转是**斜坡受限**，不是速度受限 | §16.6：先提斜坡（600/900 → 900/1200），再放宽快速档，最后才提上限 |

在线改（立刻对下一次转向生效），满意后存 flash：

```
&kp 0.045      &ki 0.0005      &kd 0.0035
&L90           # 或 &R90，看 [TURN] done 的耗时与 overshoot
&save          # 存 flash
&read          # 复查：应显示 kp=0.0450 ki=0.0005 kd=0.0035
```

### 16.3 传感器分辨率与 0.01° 判据（含上电零漂标定）

**HWT101 的分辨率（决定我们能"精确到几位小数"）**

| 量 | 帧 | 换算 | 1 LSB |
|---|---|---|---|
| 航向 yaw | `0x53` | int16 × 180 / 32768 | **≈ 0.0055°**（约 0.01° 的一半） |
| 角速度 | `0x52` | int16 × 2000 / 32768 | **≈ 0.061 dps** |
| 内置累计角 | `0x54`（本工程未用） | — | — |

- 因此"转向误差 < 0.01°"**只有约 2 个 LSB 的余量**，属于贴分辨率取门限；yaw 的量化噪声会让真实误差在 ±0.01° 间跳，门限时有时无。
- 固件做法是**两级判据**（`ChassisMotor_UpdateTurn()`）：

  | 判据 | 条件 | 耗时 | 日志标记 |
  |---|---|---|---|
  | ① 主判据（严格） | `\|误差\| ≤ 0.01°` 且 `\|角速度\| ≤ 2 dps`，**连续 200 ms** | 最快 | 无 |
  | ② 稳定带判据 | `\|误差\| ≤ 0.05°` **连续保持 0.5 s**（掉出带即重新计时） | 进带 + 0.5 s | **`FB`** |
  | ③ 无进展兜底 | 误差 ≤0.20° 但 **900 ms** 内改善 <0.01°（到机械/分辨率下限） | ≤ 起始 + 0.9 s | **`ST`** |

- **0.5 s 驻留为什么比"单点采样"可靠**：0.5 s 内平均角速度只要 > 0.1 dps，车就会走出 0.05° 带、计时清零；反过来说"连续 0.5 s 都在带内"本身就等价于"平均角速度 < 0.1 dps"，所以这条判据不需要再单独卡角速度，也天然防止"擦着目标飞过去被误判成到位"（旧实现是"起转 1.2 s 后单点采一次 0.05°"，既慢又可能被一次噪声骗到）。
- **不会互相干扰**：稳定带内没有"摩擦补偿 kick"（它的门槛是 0.06°，比 0.05° 带宽高一点），所以车进了带就老实待着，不会自己把自己踢出带。
- 判读：**没有 `FB`/`ST`** = 真的收敛到 0.01° 以内；**带 `FB`** = 稳定在 0.05° 带内收工；**带 `ST`** = 900 ms 内压不下去了、按"到机械下限"收工（`err` 就是这台车能做到的极限）。
- 对"原地转 ≤3 s"指标的影响：① 命中时 200 ms 收工；② 命中时 = 进带时刻 + 0.5 s；③ 兜底保证最坏也只有约 0.9 s + 贴靠时间。改造后 90° 转的典型时间线见 §16.5。

**上电自动零漂标定（"上电后自动读取数据去除零飘"）**

- 上电后由 `0x53` 帧驱动，在 **静止** 条件下自动建立基准（窗口 **3 s**，2026-09-12 由 300 ms 加长）：
  - 判据：① `|gz| ≤ 1.5 dps`；② **窗口内 yaw 极差 ≤ 0.5°**（3 s 窗口很长，只看瞬时角速度挡不住"慢慢转/被人轻挪"）；③ 样本数 ≥ 20。任一条不满足就把窗口清零重来；
  - 输出：**朝向基准** `hwt101_yaw_baseline_deg`（取窗口内 yaw 平均）+ **角速度零偏** `hwt101_gyro_bias_dps`（取窗口内 gz 平均，3 s 平均后噪声低一个量级）；
  - 打印：`[IMU] zero-drift ready: N samples/Xms, gyro bias +X.XXX dps`（ASCII）；
  - **屏幕**（IPS200 顶部右侧 x=180）：标定中显示 `IMU ZERO CAL 2.4s` 倒计时（黄色，倒计时**跳回 0** = 车还在动），完成后 5 s 内显示 `IMU ZERO DONE`（绿色）。
- 之后固件内部航向 = **相对基准的累计角**（`hwt101_zero_drift_deg`），所以"上电朝向 = 0°"，与上电时车头朝哪儿无关；`HWT101_GetGyroZDps()` 返回的值**已经扣掉零偏**。
- **标定完成前不允许转向**（`ChassisMotor_TurnRelative()` 直接返回 `HAL_ERROR`，蓝牙会打 `[TURN] rejected: need &EN and IMU zero-drift ready`）——这是保护：没有基准就转，等于闭着眼睛转。
- `&zero` / `zero` 会把标定窗口清零重来（`yaw` 命令可看 `ready=0 cal=1`）→ **喊完 `&zero` 同样要静止约 3 s 再动车**，否则基准会一直在重新计时；屏幕上 `IMU ZERO CAL x.xs` 的倒计时就是这段窗口。
- `yaw` 命令输出：`[YAW] raw=… zero=… gyro=… bias=… ready=… cal=… turn=…`（`raw` 原始 yaw、`zero` 相对基准累计角、`gyro` 已扣零偏的角速度、`bias` 标定出的零偏）。

### 16.4 与"速度字段 ×10 修正"的关系

`kp/ki/kd` 原来是按"实际只有 1/10 速度"那会儿调的；修正后同样输出对应的实际轮速变成 10 倍，所以转向环增益整体变"热"，需要重调 —— 现场已定出稳定值（§16.1）。

- 转向环的实际增益变大 → 过冲/抖动；
- 已把 `CHASSIS_TURN_MAX_WHEEL_RPM` 由 120 调回 **90**（= 修正前实际生效的上限）以恢复原有手感；
- 若仍抖，按 §16.2 先降 `kd` 再降 `kp`。

### 16.5 转向慢/超时的真因：死区没覆盖 + 执行粒度太粗（2026-09-12）

**症状**：`[TURN] done` 经常 >3 s（`OVER-3s`）或磨到 8 s 超时；一加 `ki` 就抖。

**根因是三个数字凑出来的**：

| 常量 | 旧值 | 后果 |
|---|---|---|
| `CHASSIS_TURN_MIN_OUTPUT_ERROR_DEG` | 0.20° | 摩擦补偿 kick 只在误差 > 0.20° 时给 |
| `CHASSIS_TURN_BAND_DEG` | 0.05° | 判到位要求误差 ≤ 0.05° |
| `CHASSIS_TX_PERIOD_MS` | 20 ms | kick = 0.08 × 90 RPM ≈ 12.5°/s → **一拍 0.25°** = 判据带宽的 5 倍 |

- **0.05°~0.20° 无人区**：PID 输出只有 `0.045 × 0.15 ≈ 0.007`（≈0.6 RPM），低于轮子静摩擦 → 轮子不转、误差卡死 → 只能等超时。
- **末端粗 bang-bang**：kick 还带 `|角速度| < 2 dps` 门限，车一动门限就关、停下再开 → 一次猛推 0.25°，冲过目标再回来。
- **`ki` 一加就抖**：轮子不动时积分一直攒，攒过静摩擦就窜，过冲后反向再攒 → 极限环。**给"执行器分辨率不够"的环加增益必然抖**，所以这不是调参问题。

**改法（四条一起才成立）**：

1. `CHASSIS_TX_PERIOD_MS` **20 → 4 ms**：末端一拍 ≈0.05°（= 判据带宽），落点窗约 ±0.025°。CAN 4 轮 × 250 Hz = 1000 帧/s ≈ 500 kbps 的 26%。
2. kick 门槛 **0.20 → 0.06°**：覆盖到判据带边缘（必须 > 0.05° 带宽，否则车在带内会被推出去）。
3. **删掉 kick 的角速度门限**：kick 方向永远跟着误差符号，不会与车体运动对抗。
4. 全部到位判据**从"拍数"改成"毫秒"**（`SETTLE_CYCLES`10 拍 → `SETTLE_MS`200 ms）：否则改节拍会顺手改判据时长（20 ms×10 = 200 ms 会变成 4 ms×10 = 40 ms）。
5. 新增**无进展兜底**（`ST`）：误差 ≤0.20° 且 900 ms 内改善 <0.01° → 判"到机械下限"收工，杜绝 8 s 磨蹭。

**改造后 90° 转的时间线**：快速段 ~0.6 s（90 RPM 上限）→ 输出跌破 0.08 后以 ~12.5°/s 贴靠 ~0.1 s → 进 0.05° 带 → 驻留 0.5 s → 收工，**合计约 1.2 s**（旧实现典型 3~8 s）。

**调参顺序**（若 `ST` 的 `err` 仍大）：

| 观察 | 动作 |
|---|---|
| `ST` 且 `err` ≈ 0.05~0.10° | 这台车就到这儿了：接受，或把该档的 `band_deg` 放宽 |
| `ST` 且 `err` > 0.2°（连 kick 都推不动） | 提高 `CHASSIS_TURN_MIN_EFFECTIVE_OUTPUT`（0.08 → 0.10/0.12） |
| 末端仍一顿一顿 | 节拍 4 → 3 ms（粒度 0.0375°，CAN 占用升到 ~35%） |
| 一直抖、`ki` 已退回默认 | 降 `kd`（现 0.0035）或降该档的 `max_wheel_rpm` |

### 16.6 为比赛提速：两档转向 + 真正的杠杆在哪（2026-09-12）

**档位表**（数值集中在 `Core/Src/chassis_motor.c` 的两个 `const chassis_turn_profile_t`）：

| | 精确档（手动 `&L90`/`&R90`） | 快速档（导航每段前对准） |
|---|---|---|
| 轮速上限 | 90 RPM | **120 RPM** |
| 主判据 | 0.01° / 200 ms | 0.15° / 60 ms |
| 稳定带 | 0.05°；带内且角速度 ≤0.3 dps 只需 **200 ms**，否则驻留 0.5 s | **0.5°** / 200 ms（角速度 ≤0.8 dps 时 100 ms） |
| kick 门槛 | 0.06° | 0.60° |
| 无进展兜底 | 0.20° / 900 ms | 1.00° / 400 ms |
| 调用者 | `ChassisMotor_TurnRelative()`（蓝牙 `&L90`、`&R90`） | `ChassisMotor_TurnRelativeFast()`（导航 `[NAV] align turn … fast`） |

**为什么导航对准可以只用 0.5°**：对准之后直走有**航向保持**（`ZDT_Nav_HeadingHold()`，每 80 ms 纠一次、可用 omega 上限换算约 30 deg/s），残余 0.5° 会被它纠掉；而转弯处抠到 0.05° 要额外付 0.3~0.5 s。段前对准的验收本身也是 `ZDT_NAV_ALIGN_TOLERANCE_DEG = 3.0°`，0.5° 远在门内。

**时间预算（90° 转，模型值；`R`≈141 mm 时换算：1 RPM = 1.73 deg/s）**：

| 配置 | 纯运动 | +驻留 | 说明 |
|---|---|---|---|
| 精确档 90 RPM（斜坡 600/900） | 0.70 s | 0.90 s | 上一版手动角度转 |
| **快速档 120 RPM** | **0.60 s** | **0.80 s** | 本次新增（导航对准） |
| 快速档 150 RPM | 0.55 s | 0.75 s | 上限继续加的边际收益 |
| 快速档 250 RPM（打满量程） | 0.54 s | 0.74 s | **几乎不再收益** |
| 快速档 120 RPM + 斜坡 900/1200 | 0.55 s | 0.75 s | 斜坡才是杠杆 |
| 快速档 150 RPM + 斜坡 1200/1600 | **0.46 s** | **0.66 s** | 目前能到的最快 |

**结论：90° 转是"斜坡受限"，不是"速度受限"**。上限从 120 提到 250 RPM 只省 60 ms，因为角加速度由底盘轮速斜坡决定（600 RPM/s ≈ 1039 deg/s²），90° 转根本跑不到高速就该减速了。要再快，按这个顺序动：

1. **提高斜坡 `CHASSIS_ACCEL_RPM_PER_S` / `CHASSIS_DECEL_RPM_PER_S`**（600/900 → 900/1200 → 1200/1600）：每个转弯省 50~140 ms，而且是**全局收益**（每段的起步/停车也更快）。副作用：麦轮起步更容易打滑、电流冲击更大；方案 B 的梯形规划会**自动**用新斜坡重算（`ZDT_NAV_ACCEL/DECEL_MM_S2` 就是从这两个宏推的），但 `t1000` 建议复验一次。
2. **快速档放宽**：`band_deg` 0.5 → 0.8°、`band_ms` 200 → 100 ms。省下约 100 ms，代价是段首 0.8° 的偏差（航向保持能纠，300 mm 段上 0.8° ≈ 4 mm 横向）。
3. **提高快速档上限**：120 → 150 RPM 约省 50 ms；再高无意义（见上表）。注意上限一高，同样的 `kp` 会让环更"热"→ 抖就先降 `kd`。
4. **少转弯**：`grid_nav` 已把同方向的连续格合并成一段，所以转弯次数 = 路径拐点数。规划时优先选拐点少的路径（同样的曼哈顿距离下拐点多寡会影响总时间），这一步的收益通常比抠那 100 ms 大得多。

**验证**：每段前对准会打 `[NAV] align turn … (fast)`，转完打一行体检，看 `FAST` 标记与耗时：

```
[NAV] align turn -90.0 deg (target -90, fast)
[TURN] done  720ms target=-90.00 err=+0.312 overshoot=0.980 peak_o=1.00  FAST  FB
[TURN] done  980ms target=+90.00 err=+0.008 overshoot=0.021 peak_o=1.00          ← 手动 &L90 精确档
```
