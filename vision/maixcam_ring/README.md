## 规则与选择方法

比赛规则 PDF 第 5 页图 3/4：工位板 580×150 mm，最外侧两组中心距离 300 mm，三组中心等距排列，因此相邻组中心距为 150 mm。圆环线宽 1.5 mm；以物料最大直径 φ=50 mm 为例，六层外径为 53、58、65、75、85、95 mm。

```text
灰度图 → 自适应二值化（深色环线为白）→ 提取轮廓
       → 完整轮廓拟合椭圆 / 边界残弧去直边并补全 → 按同心位置和不同半径合组
       → 三组共线、近似等距、尺度相近检查 → 选几何中间组
       → 连续确认 → 跟踪该组 → 屏幕中心误差/对齐标志/串口
```

不靠数字 2 的 OCR，也不把“屏幕附近的圆”直接当作中间组。`id=2` 表示规则布局中的几何中间组，不表示算法识读了纸面数字；该编号也不能唯一标识不同工位的地图位置。

首次需要三组有效中心证据，可以由完整圆环或可见残弧补全得到，不要求三组圆周全部入镜。连续 3 帧一致后锁定中间组；锁定之后，即使两侧退出画面，只要原中间组仍处于合理的连续位置/尺度范围内，仍可跟踪。无法唯一关联时立即发送无效状态，不继续用旧坐标。身份关联记忆按帧周期自适应，最低 0.35 秒、最高 1 秒；超过关联期限清除身份，再次要求三组重新确认。低帧率时避免仅因一帧耗时过长反复回到 ACQUIRE，但丢失的当帧仍立即输出无效，不复用旧坐标。按 `Reset lock` 也会清除锁定。

状态 `MIDDLE_PARTIAL` 表示利用残弧补全后确认了三组；`MIDDLE_LOCKED` 表示三组由完整轮廓确认。`TRACK_MIDDLE` / `TRACK_PARTIAL` 表示继续跟踪已锁定的完整/残弧中间组。`SHOW_ALL_3` 表示首次只有 1–2 组可靠中心证据，需要更多视野；三组均检出但排列检查未通过时显示 `CHECK_ROW`。

锁定后默认启用原分辨率局部窗口（ROI），状态为 `ROI_MIDDLE` / `ROI_PARTIAL`，此时 G=1 是正常现象。每帧重新测量圆心，并核对中心印字的外观模板，避免车子移动后把相同外圈的邻组误认为原中间组；模板只由全图三组确认刷新，不用于 OCR 编号。每秒全图复核一次；局部定位失败、印字被遮挡或不匹配时当帧回到全图。半环补全路径保留。ROI 帧只提供新圆心；全图检出有效三组时才提供新的行方向。方向和av只保留在本地观察，位置串口不发送未经车体标定的图像角度。

每组至少要有 3 个不同半径层级，且半径跨度足够，防止把单个圆、数字孔洞当成工位。默认不做高斯模糊，避免细环层在低分辨率下粘连。不使用全图 Hough 圆搜索。

完整闭合轮廓默认用 OpenCV 面积矩计算中心、方向和椭圆轴长，省去逐圈通用椭圆求解。面积填充率和边界残差检查继续保留，不把所有闭合轮廓直接当圆。半环仍使用原归一化残弧拟合。`MOMENT_ELLIPSES_ENABLED=False` 可切回完整轮廓的旧拟合路径进行对照。

### 半圆如何补全并确定中间组

补全指利用可见圆弧估计完整圆环的几何参数。程序只对触及画面边缘的轮廓做该处理：去掉裁切形成的直边，并分离连续弧段；用完整圆环的椭圆比例将弧段归一化，在该平面拟合圆，再映射回图像。这样半圆不必自由估计整个椭圆的 5 个参数。没有完整参考组时，按用户确认的俯视条件使用圆形模型。

每段可见弧须覆盖至少 100°、平均归一化拟合误差不超过 4%、95% 点误差不超过 8%，拟合曲线也必须真正跨过对应画面边缘。每组仍须通过多层同心和半径跨度检查，而且不能把同一裁切轮廓的多段弧当成多个环层。最后使用三组中心的共线、等距、尺度关系选择中间组，连续确认后输出坐标。

支持左/右外圈只露半边、两侧都被裁切，以及锁定后中间组逐渐移动到边缘只露半圈。补全中心可以位于画面边缘略外侧；坐标仍相对屏幕中心，本地q形状评分对残弧估计略减分，完整/残弧统一使用RING_PX位置帧。

如果第三组完全不可见，首次仅看到两个相同圆环，不足以唯一确定它们是 1/2 还是 2/3，程序不会凭位置猜身份。若此前已锁定中间组，则可用连续关联继续跟踪。只露四分之一、太短的弧、细环层无法分开、强透视且缺乏参考或多个排列同样可信时，仍输出无效。

## 对齐与串口协议

界面误差 `x_screen = 圆心屏幕X - 屏幕宽/2`、`y_screen = 屏幕高/2 - 圆心屏幕Y`，右/上正。目标偏置 `TARGET_OFFSET_SCREEN_PX=(0,0)` 对应用户指定的屏幕中心。

相机本地两轴±5屏幕像素、连续5次新有效观察后显示ALIGN，丢失/超限立即取消。**该计数不再作为线协议字段发送**；主控须按新图像/时间建立自己的稳定计数、标定位置容差并确认停稳。

UART0 `/dev/ttyS0`、A16/TX→主控USART2 PA3/RX、共地，115200 8N1，3.3V TTL。A17/RX←PA2/TX预留，当前程序仅发送位置。换串口须同时核对设备路径/引脚，不在上电时拉低A16。

现在采用工程[统一8字节协议](../../docs/electrical/MaixCAM_STM32_统一8字节串口协议_v0.1.md)，中间组为 `TYPE=0x03 RING_PX`、`ID=2`：

```text
6B 03 META X_LO X_HI Y_LO Y_HI CRC8
META = VALID<<7 | (图像SEQ模16)<<3 | 2
XY = int16、小端、0.1图像像素
CRC8覆盖前7字节，poly07/init00/不反射/xorout00
```

**线上坐标右正、下正，单位为相机图像像素**。程序将界面X/Y除以FIT_CONTAIN显示比例并反转Y。480×360图像、552×368屏幕时比例为368/360。编码器缩放比例1、界面(+30,-20)、SEQ12的完整示例为 `6B 03 E2 2C 01 C8 00 E4`，即dx=+30、dy=+20。无目标/未确认/歧义/超范围/非有限数为VALID=0、XY=0，ID仍2。有效中心处XY=0且VALID=1。

a_deg/av/align/q留在本地显示/观察结构，未经车体标定的图像连线角不能冒充ALIGN_YAW。只发送像素，不发送假毫米或假已知图像年龄。当前为手动启动自动位置流；此独立文件不接收SET；需要串口切换时使用新增[统一服务](../maixcam_service/README.md)。

正常最高20Hz，受实际检测帧率限制；每次新图像编号递增，即使限频跳过。只保留一个短写帧，50ms没写完则丢弃；失效/强制中断时异步等待55ms让接收器半帧超时后发送当前新帧，不再用CRLF重同步。正常完整写入失效可立即发送；退出/掉电不能保证最后帧，主控超时必须保留。

**STM32已接入接收**：`Vision_GetPixel(2,VISION_TYPE_RING_PX,&p,&age_ms)` 读取对应端口，检查p.valid后使用p.dx_px/p.dy_px。200ms无新观测自动无效、坐标清零；相同有效SEQ重复帧在50ms窗口内不刷新年龄。类型/目标切换、DMA溢出/错误使旧像素失效。像素不会进入旧vision_ring_t.x_mm/y_mm接口；本次未触发车辆运动。

默认相机两端口均为binary8；需要旧ASCII相机时显式选择legacy模式，不自动混用。三套相机脚本保持独立单文件运行，协议实现由同一源码嵌入；部署须同时更新相机程序和主控固件。

## 主控怎样走过去并做纠偏

按项目既有设计：里程/IMU 粗走到能看见三组的捕获区 → 确认中间组 → 使用新有效帧低速纠偏 → 主控位置稳定后发零速度并确认车体停稳。valid=0、错误工位或接收超过约 200 ms 无更新时，立即停止，不能沿用旧误差。重复读取同一接收快照不应增加稳定计数；4位SEQ会回绕，不能仅凭SEQ永久判重。

像素到车体运动的符号/比例必须实测，俯视不能自动确定相机在车体上的旋转方向。脚本里的 `correction_velocity(error, pixel_to_body_mm)` 提供已标定后的 P 纠偏计算和合速度限幅（默认 30 mm/s）；无目标或没提供标定矩阵时返回零速度、控制建议无效。该函数不直接发电机指令，运行循环发送 RING_PX，由主控决定实际车速。

标定方法（本地函数按屏幕右/上正；主控应直接按线上图像右/下正重新标定，不能混用两套矩阵）：

1. 固定相机高度/姿态及 IMU 航向，对准同一个静止圆环，记录初始误差 e0。
2. 车体向前移动已知距离 d_f，记录误差 e_f，得到 J 的第一列 `(e_f-e0)/d_f`。
3. 回到原位置，向车体左侧移动 d_l，记录 e_l，得到第二列 `(e_l-e0)/d_l`。
4. 若 J 可逆，设置 `C=-inverse(J)`，使用 `v_B=limit(Kp*C*e)`；低速验证车体移动后误差确实减小。

车体建议坐标：X 向前、Y 向左；本仓库底盘 vy 约定曾记录为向右，主控适配必须核对并转换该符号。两个像素误差只能用于局部位置纠偏；单个圆中心不能确定全局 x/y/yaw。三组连线提供局部方向，但有 180° 歧义，需要工位方向/IMU 先验和相机安装标定，不能直接把 a_deg 当机器人地图航向。

## 卡顿诊断与性能版本

截图中的 F 是相机程序的整体循环帧率，不是 MaixVision 界面的独立刷新率。F=2.1 表示每轮平均约 0.48 秒；取帧、检测、串口、显示/图传都可能贡献这个耗时。用户当前使用 Wi-Fi，SDK 的 disp.show 也会向 MaixVision 送图，因此网络/编码开销可能阻塞程序，不能仅凭截图认定是电脑或某一算法。

用户随后提供的设备日志已定位当前主要瓶颈：低帧率阶段 D=315–328 ms，C=约 1–4 ms，U=约 0.5–1.1 ms，V=约 29–40 ms，F=约 2.7–2.8。检测占循环大部分时间；Wi-Fi 显示有开销，但不能解释主要下降。曝光约 13–18 ms，也不足以解释 300 ms 的识别耗时。最新版本针对全图轮廓和残弧运算减负，并加入局部跟踪；设备改善幅度仍须重新运行测量。

用户复测确认局部跟踪版本已达 11–12 FPS，D=约 63–72 ms。ROI 中 E=约 33 ms 是最大子阶段；周期全图 E=105.8 ms，P=38.5 ms，全部子阶段合计约 191 ms，会造成短暂停顿。当前进一步改为面积矩路径，并在三组完整排列成立时跳过无须进行的边界补全。新改动的设备耗时待下一次复测；不能将上一版本的 11–12 FPS 归为此改动后的结果。

新版本新增以下分段计时（毫秒），屏幕显示最近统计，控制台每两秒打印 `[PERF]`：

| 字段 | 含义 | 数值较大时的排查方向 |
|---|---|---|
| C | cam.read 取帧耗时 | 采集等待、长曝光、驱动/格式；日志 exp_us 为曝光微秒值，-1 表示无法读取。 |
| D | 图像转数组、识别、身份跟踪和误差计算 | 算法/相机 CPU 运算占用。 |
| U | UART 写入 | 串口阻塞、配置或驱动。 |
| V | 绘制、图像封装、SDK 显示及图传 | 包含显示/压缩/发送，不等于纯网络时间。 |
| O | 其他时间 | 触摸轮询、日志/曝光查询和调度等；计入 F，避免漏掉卡顿。 |
| PV | 该日志窗口的预览次数 | 只统计预览，并非识别帧数。 |

V 的平均值只除以真正显示的帧数，跳过的预览不会把慢图传“平均成零”。F 包含完整帧周期及上轮日志/调度时间；预览限频后，识别与 UART 仍每个新相机帧运行。

紧随 PERF 的 `[DET last]` 是最近一次检测的细分耗时，不是整个日志窗口的平均值：B=二值化，K=找轮廓/过滤/排序，E=完整椭圆拟合和首次同心分组，P=边界残弧补全，G=最终分组/三组排列。模式 `FULL`=全图，`ROI`=局部成功，`FULL_R`=局部失败后全图重试；R 为失败局部尝试额外耗时。M 为中心外观相似度，-1 表示未取得可用匹配；N=原始轮廓数>保留数，A=通过拟合的残弧候选数量。

诊断步骤：

1. 重新运行新版，记录 C/D/U/V/O 或 `[PERF]` 一行。
2. 在 MaixVision 暂停图片传输，再看**控制台日志**中的 F/V 是否改善；已冻结的预览画面上的数字不会再更新，不能用它判断。若变化明显，图传确有影响；若 D 仍很高，主要处理瓶颈在设备运算。
3. 要完全排除显示与图传，临时设置 `PREVIEW_ENABLED=False` 重跑；这会停止设备/电脑画面更新，但识别、UART 和 PERF 日志继续。确认完恢复 True。
4. C 特别大时结合 exp_us 检查光照/曝光，不能把全部时间归到识别。不要凭未测数据随意更改影响图像质量的曝光参数。

已实施的减负：

- 首次三组确认后，大多数帧仅处理原分辨率中间组局部窗口，保留每秒全图复核和失败回退；外观核对防止邻圈替代原位置时误跟踪。
- 完整椭圆由面积矩和标量 2×2 特征值公式求得，避免通用拟合求解；残差抽样真正限制到 64 点。
- 缓存轮廓边界框/面积，内部轮廓不进入边界补全；恰好三组完整圆环且排列检查通过时直接选中间组，跳过背景残弧计算。
- 排序前滤除小碎片，拟合前排除明显细线/大背景轮廓，避免无用候选进入高成本计算。
- 残弧每段真正限制到最多 100 个采样点，逐点计算改用 float32；单调弧角跨度使用端点计算，折返弧保留排序检查。
- 残弧拟合用等价的中心化解析最小二乘，取消热路径里的 NumPy 小矩阵 inverse/SVD；每帧只计算一次参考形状变换。
- 小型分组和三组排列计算使用标量，未发生残弧补全时不重复分组。
- 保留 480×360 原始识别分辨率，以及同心层、可见角、拟合误差和身份检查。
- 输出原生 RGB 图，避免 BGR 预览交给 SDK 再做一次通道交换；颜色标记保持原样。
- 预览最多 10 Hz，并从显示完成后留出刷新间隔；JPEG 预览质量从默认 95 调到 75，仅影响发送的预览，不影响原始识别输入。
- 修复 2 FPS 时旧 0.35 秒身份记忆短于帧周期造成反复确认的问题；主控建议的 200 ms 数据超时没有延长。

`PREVIEW_FPS` 可调整预览上限，`PERF_LOG_INTERVAL_S=0` 可关闭周期日志。若 V 本身很大，同步显示调用仍会造成单次阻塞；限频不能保证任何 Wi-Fi 条件下达到实时要求，需要实际计时或关闭预览。

电脑前后对比记录显示两张实拍的中间圆心变化小于 1e-6 像素，检测耗时有所降低。这是桌面 OpenCV 测量，不能用来宣称 MaixCAM 已恢复到某个 FPS；设备实际结果要看新 PERF 数据。

局部跟踪对比记录：两张实拍在电脑上的检测中位耗时，全图/局部分别约 2.01/0.66 ms、4.51/0.91 ms，圆心差异为 0。该记录仍是桌面 OpenCV 5.0.0 的测量，不是设备帧率。重跑时应观察锁定后的 `ROI_MIDDLE`、D 是否降低，以及周期全图复核/失败重试的 DET 子阶段。

最新面积矩对比记录：两张实拍的中间圆心相对上一版本变化约 0.0024/0.0025 像素；同一次桌面比较中，全图耗时分别从 2.03/5.13 ms 降至 1.18/3.42 ms，ROI 从 0.68/1.01 ms 降至 0.49/0.72 ms。设备启动应打印 `[RING] native moments=True + ROI`；请使用新的 E/P/D/F 日志评估实际改善，不按电脑耗时推算设备帧率。
