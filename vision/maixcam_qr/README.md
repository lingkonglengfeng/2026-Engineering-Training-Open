保持640×480、30FPS请求的完整取景，优先将新帧缩放到480×360用ZBAR解码；像素数减少43.75%，不裁切二维码搜索区域。连续3次快速解码无合法任务，回退640×480。若原分辨率找到合法任务，后两帧继续用原分辨率完成连续3帧确认，避免“小尺寸扫不到、只有单帧回退找到”的情况永远无法锁定。任务格式、颜色映射、歧义拒绝、会话、完整四组和STOP机制保留。

二维码直接在倒装原图上解码，180°仅作用于最高5Hz的320×240预览，屏幕文字仍正向；不再为每次识别旋转640×480整图。官方说明ZBAR在较低分辨率上通常更快，见[find_qrcodes API](https://wiki.sipeed.com/maixpy/api/maix/image.html#find_qrcodes)。实际提升仍需相机验证。

`[CAM2 PERF]`新增 `fps`（真实读取帧率）、`scan_fps`（真实参与识别帧率）以及当前 `decode` 尺寸；C/R/D/V仍为取帧、上次预览旋转、解码、预览耗时。30FPS是相机请求值，不是承诺的识别帧率。扫码锁定后scan_fps下降属于停止重复识别，不能据此判断识别卡住。

29项单元检查和8张冻结二维码的实际离线图片/模拟SDK流程通过，覆盖倒装原图、小预览方向、原分辨率回退三帧、歧义拒绝和原有UART/任务隔离。实机原生ZBAR及FPS尚未测量。安装包与验证文件在 `output/cam2_qr_fast_v4_2026-10-13`。

## 倒装与安装包

### v3：设备桌面启动入口兼容

针对“MaixVision直接运行正常，设备桌面启动退出code2”的现象，设备环境（存在/maixapp目录）直接调用run_device，不再让桌面照片检查器解析设备启动参数。电脑仍支持 `--image` 离线检查。27项测试覆盖空参数、模拟launcher附带参数、缺少image值及help参数在设备上均不会进入argparse，并保留原扫码/串口回归。本修正排除了入口参数导致的code2，但尚未拿到失败时last_run.log，不能据此断言现场根因已经确认；需断开MaixVision后从桌面实测。

CAM2默认倒装：每张640×480图先调用Maix原生 `Image.rotate(180)`，再使用旋转后的同一图像解码、缩放预览；不是单轴镜像。预览文字在旋转之后绘制，保持正向。旋转失败或尺寸异常会清确认状态，不用错误方向的图像继续解码。锁定任务后仍旋转预览图，但跳过重复解码。`[CAM2 PERF]`新增R旋转耗时；实际开销需设备测量。[官方旋转接口](https://wiki.sipeed.com/maixpy/api/maix/image.html)。

安装包：`dist/maix-cam2_qr-v1.0.2.zip`，独立应用ID `cam2_qr`，根目录包含app.yaml、app.png、main.py。把该包安装到**第二台相机**；也可在MaixVision打开本目录、使用打包安装功能，或直接运行main.py。包内已经内嵌协议，无需另外上传service.py、protocol8.py或CAM1算法。启动显示WAIT SET6，等待主控命令是正常行为。如改为正装，将service.py的 `CAMERA_ROTATION_DEG` 改为0后重新生成/打包。

## 接线与运行

| 第二台MaixCAM | STM32H723ZG主控 |
|---|---|
| A16 / UART0_TX | PA3 / USART2_RX |
| A17 / UART0_RX | PA2 / USART2_TX |
| GND | GND |

串口 `/dev/ttyS0`、115200、8N1。相机由USB/既定供电供电，UART是3.3V逻辑；两相机的TX不能并接同一个主控RX。CAM2不初始化第一相机的A19灯控；本程序不需要上传第一相机的检测器、协议辅助文件或安装额外Python库。固件自带Maix图像解码接口即可。

默认STOP，只发回执/心跳，不主动发布任务。停车调试用 `&qrscan start`；自动比赛流程的开关、扫码点(2000,1200)、朝向0°和任务执行由主控版本管理，见电控更新说明。相机不导航、不控制机械臂；收到扫码SET后才开始解码，主控收到完整任务后STOP CAM2，随后使用锁存任务调度CAM1。

相机固定RGB640×480，预览320×240、最高5Hz显示，模式切换不重建相机通道。原生`find_qrcodes`优先ZBAR；老SDK不支持decoder_type参数时自动使用默认接口。连续3帧相同合法任务才锁定，同一扫码请求内首个确认任务锁定，不会在后续画面跳到另一张二维码；按请求Hz重发相同完整组，直到STOP。码缺失/歧义/非法/解码异常在确认前不发送QR结果。锁定后重发的是已经确认的任务，并不表示每次重新解码。

STOP清发包、临时确认/活动任务，LCD保留最后确认的**原规则码**并标`STOP / LAST TASK`，满足任务码显示要求。新扫码SET清旧显示和旧锁定。仅重复同一请求字节（2秒内）回缓存ACK，不能重复清状态。程序退出释放相机/串口/显示，没有车辆控制代码。

## 规则与统一数据

规则PDF第3页：黑色障碍φ50×100mm（本轮未实现）；第6页：A4横放垂直二维码板，码80×80mm含边框，四组三位数以`+`相连。第7页要求显示已读任务码。

`156+123+516+231`的四组分别是：第一批颜色顺序、第一批放置位置、第二批颜色顺序、第二批放置位置。每颜色组为三个互不相同1..6，每位置组是1/2/3排列。例子中的两批颜色集合相同，但未额外强制两批同集合；只采用规则中已明确的组语义。

| 组ID | 内容 | 线上转换 |
|---|---|---|
| 1 | 第一批颜色 | 规则5黑→工程6黑；规则6浅蓝→工程5浅蓝 |
| 2 | 第一批位置 | 原样1/2/3，不做颜色映射 |
| 3 | 第二批颜色 | 同组1 |
| 4 | 第二批位置 | 原样1/2/3 |

LCD一直显示原规则码156…，不能把线上165…当比赛原码。MCU还原原码打印/旧Vision_GetQR，同时另存工程颜色数组与位置数组。

沿用固定8字节 `6B TYPE META D0 D1 D2 D3 CRC8`，CRC-8/SMBUS。模式6、station4、target0、hz1..50、flags0；STOP模式0、hz0、target0。SET/ACK/HEARTBEAT与第一相机格式一致，CAM2只接受0/6，未知模式失败ACK。ACK仅表示配置成功，扫码完成由四组任务结果决定。

QR_GROUP类型0x07，META.VALID=1、META.ID=1..4、META.SEQ=**当前成功SET请求SEQ**，作为一次性扫码会话号（与其他像素流图像计数不同）。D0/D1/D2是本组三值，D3固定4。四帧32字节整组写入，组内不插ACK/心跳；半组50ms超时放弃，55ms恢复间隔后重发完整组；新SET/STOP丢旧尾，恢复后ACK，ACK后不补旧组。主控只接受CAM2、已确认mode6/station4、同SET会话、50ms内完整一致四组；完整发布后同会话重发不刷新/覆写任务。部分组不会触发搬运。

本轮没有0x08距离/自动避障输出，也没有凭单目大小冒充距离；QR原始参数和解码结果不能作为避障授权。

## 验证与排查

本次CAM2的27项检查通过，包括真实QR离线解码、模拟Maix设备入口、倒装180°纠正后逐像素一致/同图预览/文字正向、旋转失败拒绝解码、锁定后不重复解码，以及原有CRC/会话/短写/STOP隔离。记录：validation.json。这是电脑/模拟SDK检查，**尚未上传相机、烧录主控或实车验证**；OpenCV离线解码不证明Maix原生实际识别速度。CAM1文件没有改动。

另外使用电控生成的8张实际随机码逐张验证：正向/180°原图共16次解码，以及8次倒装相机输入→MaixQrBackend→QrService三帧确认→四组07帧→STOP的模拟流程，全部通过。对每张图比较旋转后像素与预览方向，并核对颜色5/6映射、位置组、SET会话号和CRC。二维码样例文件夹。这些是离线验证，不代替实车测试。

`[CAM2 PERF]`每2秒显示累计frames与C取帧/R旋转/D解码/V上次预览耗时。扫码后LATCHED停止重复解码，只保留画面/重发任务。30FPS是相机请求值；真正扫码速度、焦距和80mm码的可见像素需要现场确认。相机应朝向二维码板并保证清晰，二维码完全不入镜时程序不会猜任务。

上传后画面`WAIT SET6`是正常待机。若一直CONFIRM1/3或SCANNING，核对相机焦距/视野、任务四组格式与光照；若AMBIGUOUS，只保留一个有效任务码在视野内。未知任务字符串不会作为控制指令执行。
